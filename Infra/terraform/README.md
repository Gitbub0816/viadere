# Infrastructure as code (ADR-09)

OpenTofu (Terraform-compatible) for the three managed platforms that are not Fly machines:

| File | Manages |
|---|---|
| `cloudflare.tf` | zone TLS settings, HSTS, DNSSEC, CAA, DNS (apex, www, api, status), WAF managed rules, edge rate limits, Authenticated Origin Pulls, origin shared header, site hostnames |
| `kms.tf` | Google Cloud KMS key ring, HSM keys per purpose, a dedicated least-privilege service account, workload identity, audit logging and alerts |
| `neon.tf` | Neon project (PostgreSQL 18), roles, database, daily snapshot schedule |
| `backend.tf` | remote state **placeholder** (GCS); `backend.example.hcl` lists the keys |
| `versions.tf` | provider pins |

Fly machines are configured by `Infra/fly/fly.*.toml` and deployed by `flyctl` in CI (no Fly Terraform provider is used: the
community `fly-apps/fly` provider, 0.0.23, is experimental).

## Use

```bash
cd Infra/terraform
cp terraform.tfvars.example terraform.tfvars          # fill in ids; gitignored
export CLOUDFLARE_API_TOKEN=... NEON_API_KEY=...       # CI: from the protected `infrastructure` environment
export TF_VAR_edge_token="$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')"
tofu init -backend-config=backend.production.hcl
tofu validate && tofu plan -out plan.tfplan            # a human reviews the plan (OPS-002: infrastructure-as-code review)
tofu apply plan.tfplan
```

Staging and production are separate workspaces/state with their own tfvars (`environment = "staging"`), their own Cloudflare zone
or child zone, KMS key ring, and Neon project. Nothing is shared, so a staging mistake cannot touch production data or keys.

## Notes and decisions

* **Zones are created out of band** (registrar delegation is a manual, reviewed step); the module takes `cloudflare_zone_id`.
* **TLS (SEC-TR-001).** `tls_1_3 = on`, `min_tls_version = 1.2` under the compatibility policy in
  `docs/ops/TLS-COMPATIBILITY-POLICY.md`, TLS 1.2 limited to six ECDHE + AEAD suites, SSL 3/TLS 1.0/1.1 refused, HSTS with
  `includeSubDomains` (preload off until reviewed), Always Use HTTPS, SSL mode Full (strict). Flip `min_tls_version = "1.3"` when the policy's
  telemetry gate is met.
* **Rate limits.** Six edge rules (auth, device enrollment, recovery, SMS link/OTP, dashboard auth, redemption) as a coarse first layer.
  Cloudflare rate-limit features and counting periods depend on the plan (Free allows one rule and a 10 s period); if `tofu apply`
  rejects a rule on a lower plan, upgrade the plan rather than dropping the rule. Precise limits stay in the server (`docs/SECURITY.md` §2.23).
* **WAF.** Managed ruleset ids are variables (plan dependent). Start with `log` if false positives are expected, then `block`.
* **Site.** Workers Static Assets scripts are uploaded by `Site/deploy/upload.py` through the REST direct-upload API (ADR-04), so the
  script is *not* a Terraform resource (a state-managed upload would fight the uploader). Terraform only binds the apex and `www`
  hostnames (`manage_site_custom_domain = true`) after the script exists. `cloudflare_workers_script` is available in 5.28.1 if you
  later decide Terraform should own the script.
* **Authenticated Origin Pulls and the shared header.** Enabled here; enforcement at the origin is a gap (G-10, G-11 in
  `docs/ops/KILL-SWITCHES.md`) described in `Infra/fly/README.md` step 6.
* **KMS.** HSM `EC_SIGN_P256_SHA256` keys `audit-head`, `connect-link`, `webhook` (signing; no auto-rotation exists for asymmetric
  keys, rotate by runbook) and symmetric HSM key-encryption keys `data-kek`, `hpke-kek` (90-day automatic rotation). HPKE
  (RFC 9180) is not a Cloud KMS operation, so HPKE private keys are generated by the server and stored wrapped by `hpke-kek`
  (envelope encryption). The server's service account gets `cloudkms.signer` + `publicKeyViewer` on signing keys and
  `cryptoKeyEncrypterDecrypter` on KEKs only; key administration is a different, human principal (not in code). Data-access audit logs are
  on, exported to a log bucket, and two alerts fire on key administration changes and on use by any other principal.
  The server does not call KMS yet (`KeyManagementService` is WP1; the keys are provisioned ahead of it).
* **Neon.** Production never suspends compute, history retention (PITR) 7 days by default, daily snapshots kept 30 days. Roles:
  `viadere_migrator` (owns schema, used by the release command), `viadere_app` (runtime), `viadere_readonly` (restore tests).
  Privilege grants to `viadere_app` are SQL and belong in the migration bootstrap (see `docs/ops/RUNBOOKS.md`). Whether the provider
  accepts `pg_version = 18` on your plan is checked by `tofu plan`; it could not be verified offline.
* **Secrets.** None in code. State contains Neon role passwords: protect the backend. `edge_token` is a sensitive variable.
