## Verdict: APPROVE WITH CONDITIONS

Every flow in the matrix is feasible with public APIs, and the design is consistent with platform rules: confirm-before-open, no silent browser launch, no Approve action on notifications, a watch that can only reduce, and a customer-originated SMS that the user must send. No finding blocks Stage 1.

Five findings are **high** and must be fixed in the design documents (or the matrix cell removed) before Stage 4/7 work starts: 1, 2, 3, 4, 5. Several matrix cells are claims the platforms do not make true as written.

## Findings

Severity: High = a documented behavior is infeasible or contradicts a security rule and must change before implementation. Medium = feasible but under-specified or with a real device risk. Low = note.

### 1. Deny and Report actions currently require device unlock (High, iOS; same pattern on Android)
- **Location:** `ChannelRenderer.notification` (`action(... auth: Bool = true ...)`, all actions including `deny`/`report` get `.authenticationRequired`); contradicts FLOW_MATRIX F9 "Deny works without Face ID", UX_COPY §0 rule 5, ADR-0022 §5.5 ("Deny (no foreground needed)").
- **Issue:** `.authenticationRequired` makes iOS demand an unlocked device before the action runs. With the current default, Deny from a locked Lock Screen needs a passcode or Face ID unlock, and the F9 "Locked" cell is false. Report ("This wasn't me") is not in the new ADR-0022 §5.5 category at all (only Review/Deny).
- **Required change:** In the new `viadere.approve` and `viadere.auth.link` categories, Deny and Not me use `auth: false`, no `.foreground`. Review/Open use `.foreground`; iOS then unlocks first, so say that Review always needs unlock. Add a Core test asserting the option sets per action. Android has no equivalent flag: a notification action is a `PendingIntent` that the system runs even while the keyguard is showing unless the action sets `setAuthenticationRequired(true)` (API 31+), so state it explicitly there (Deny: not required).
- **Citation:** Apple `UNNotificationActionOptions.authenticationRequired` and `.foreground` ("foreground" actions launch the app and force unlock); Android `Notification.Action.Builder.setAuthenticationRequired` (API 31).

### 2. "Queued deny sent when online" (F9 Offline) has no platform mechanism (High, iOS and Android)
- **Location:** FLOW_MATRIX F9 Offline cell; F7 Offline "submission retried while unexpired"; no queue exists in `Notifications/*`.
- **Issue:** A notification action wakes the app for a short background window (tens of seconds; the system suspends it afterwards). No retry survives unless the work is handed to the OS. The body a device signs also has a freshness window, so a plain retry with a re-signed body needs the app running.
- **Required change:** Specify one of: (a) pre-sign the deny and upload it with a background `URLSession` (iOS) or expedited WorkManager (Android), with the signed body valid for the request lifetime; or (b) drop the claim and show locally "Deny not sent yet. Open Viadere." and keep the item in the inbox. State that the business sees `pending` until expiry in either case. Remove "retried when online" from the F7 offline cell for Approve (Approve is always foreground and needs the network at the screen).
- **Citation:** Apple "Downloading files in the background" and "Handling notification responses"; Android "Schedule tasks with WorkManager" (expedited work).

### 3. Android push pipeline is unspecified; FCM message type decides whether the design works (High, Android)
- **Location:** FLOW_MATRIX F1/F7 Android cells ("FCM tap → PendingIntent"), ADR-0020 §6 (payload carries only the delivery id), UX_COPY N-01..N-08.
- **Issue:** There is no Notification Service Extension on Android. If the server sends an FCM *notification* message (or a mixed `notification`+`data` message), the system displays it itself while the app is in the background and `onMessageReceived` is never called, so the app cannot fetch the display object, show {Business}, or attach Deny/Review actions. If it sends a *data* message, the app must build the notification inside `onMessageReceived` (about 10 s; use expedited work for the fetch), at **high priority**, and high-priority messages that do not produce a user-visible notification are demoted, which delays later ones. Data messages are not delivered to force-stopped apps, and OEM battery managers can delay or drop them.
- **Required change:** Add an Android section to ADR-0020 §6 and ADR-0022: data-only, high-priority FCM; the app renders N-01 (generic) immediately, then updates the same notification id with the enriched content; if the fetch fails, N-08 stays. Do not include a `notification` block. Request `POST_NOTIFICATIONS` (Android 13+) with the same priming screen as iOS and create a dedicated high-importance channel for security items (channel importance cannot be raised by the app after creation, so choose it now). Document the OEM fallback (inbox, E-06 banner) and add a "battery optimization" help item. Add FLOW_MATRIX columns for "force-stopped" and "Doze/standby bucket restricted".
- **Citation:** Firebase Cloud Messaging "Message types", "Set and manage Android message priority"; Android "Notification runtime permission", "Create and manage notification channels".

### 4. Android notification tap and actions: trampoline and PendingIntent rules must be written into the design (High, Android)
- **Location:** FLOW_MATRIX §4 note 5; ADR-0021 §4.3; spec §7.1.
- **Issue:** Note 5 correctly says "immutable PendingIntent to an exported-false activity", but the actions are not specified. Facts checked against the Android docs fetched in this review: apps targeting Android 12 (API 31) and above cannot start an activity from a notification tap routed through a `BroadcastReceiver` or `Service`; the notification must use `PendingIntent.getActivity` directly. On Android 14 (API 34) senders of a `PendingIntent` opt in to background activity starts, and `FLAG_IMMUTABLE` is mandatory for new targets and also required for any mutable-looking intent that is not an inline-reply. Deny, however, is a background action with no UI, so it correctly uses `getBroadcast` or `getService` and does the signing in `goAsync()` (receiver limit around 10 s) or expedited work; that is allowed (it starts no activity).
- **Required change:** Specify per action: Review/Open/Continue = `PendingIntent.getActivity(... FLAG_IMMUTABLE | FLAG_UPDATE_CURRENT ...)` to an `exported="false"` activity, with explicit component and only the opaque delivery or request id as extra (no URL); Deny/Not me = immutable broadcast to an `exported="false"` receiver doing background work as above. The link screen's Continue calls `startActivity(ACTION_VIEW)` from a foreground activity after the user taps, which is permitted; never start the business URL from the receiver. Add a lint or CI check for `FLAG_MUTABLE` and exported components.
- **Citation:** Android "Notification trampolines", "Restrictions on starting activities from the background", "Behavior changes: Apps targeting Android 12", "PendingIntent mutability".

### 5. ADR-0027 spoofing analysis misses the victim-induced text (Medium-High, iOS and Android; severity high for UX copy)
- **Location:** ADR-0027 §3.1; UX_COPY S-PH-02, SMS-02.
- **Issue:** The ADR analyses forged From headers. The platform facts, however, mean the nonce text is a plain, user-sent SMS: neither `MFMessageComposeViewController` (iOS) nor `ACTION_SENDTO smsto:` with `sms_body` (Android) can send silently (see "Compose-sheet findings" below), so the person always decides to send, and the body is editable. The more likely attack is social: an attacker begins a link for the **victim's** number from the attacker's own trusted device, then tells the victim "text this to confirm your delivery/verify your account". The victim's own phone sends the MO from the right number, so the From check passes and the number links to the attacker's account. The nonce text "Link my number VDR-XXXXXXXX" tells the victim nothing about which account receives the link.
- **Required change:** (a) Add this case as a named risk (R-13b) in ADR-0027 §3 and THREAT_MODEL. (b) The gateway reply to a **valid** MO must state the effect in plain words, not only SMS-02 after the fact: "Viadere: Someone asked to link this number to a Viadere app. If you sent this text yourself, no action is needed. If not, reply UNLINK." (c) Keep the 24 h/72 h cool-down and the per-number begin budget; add a per-**number** daily cap on *verified* links, so a victim cannot be re-targeted repeatedly. (d) Nonce text stays human-readable and fixed, but S-PH-01 should say who it is for ("your Viadere account on this phone"). (e) Nothing changes the rule that `phone_control_mo` is never a factor; the review accepts the ADR's limitation of impact.
- **Citation:** Apple `MFMessageComposeViewController` ("the message is not sent until the user taps Send; apps cannot read or alter the message"); Android "Intents and intent filters: send a text message", `Intent.ACTION_SENDTO`.

### 6. Compose-sheet availability, content integrity and carrier path (Medium, iOS and Android)
- **Location:** ADR-0027 §1.2, §3.3; FLOW_MATRIX F12; UX_COPY S-PH-01..04.
- **Answer to the review question:** Neither platform lets an app send an SMS silently without a privileged permission. iOS: `MFMessageComposeViewController` is a system-hosted sheet; the app sets `recipients` and `body` and receives only `.sent`, `.cancelled` or `.failed`, never the final text; `.sent` means queued by the system, not delivered. The `sms:` URL opens the Messages app (leaving the app, no result callback) and its body parameter is less reliable; use the view controller. `canSendText()` is false on iPad without a cellular line or iPhone relay, on Mac Catalyst, in the Simulator and without a SIM; the ADR already adds copy-and-paste. Android: `ACTION_SENDTO` with `smsto:` and the `sms_body` extra opens the default messaging app prefilled; sending needs the user's tap, and sending without it needs `SEND_SMS`, which Play policy restricts to default SMS handlers, so Viadere must not request it. `sms_body` is honored by Google Messages and Samsung Messages but is an informal extra; on some OEM or third-party apps it may be dropped (**verify** on the Stage 7 device set). Dual SIM: the user, not the app, picks the line; the From check handles a wrong one.
- **Issues:** (1) On Android and on iOS 18+ the default messaging app can send the text as **RCS or chat** instead of SMS if the destination is RCS-capable; the Viadere number's inbound path must accept it. The ADR says "not iMessage-enabled" but does not cover RCS agents, MMS, or a long-text split; the Stage 5 provider test must send from RCS-capable Android and iOS phones. (2) Because the user can edit the body, the pattern match must stay tolerant (it is: anywhere in the body, whitespace-tolerant). (3) The app has no way to know the text was sent, so S-PH-03 "Waiting for your text…" must keep polling and show S-PH-04 only at expiry. (4) The Android `ACTION_SENDTO` should use `resolveActivity`-style handling via `PackageManager.queryIntentActivities` with the `<queries>` declaration (package visibility, API 30+), or `try/catch ActivityNotFoundException` to fall back to copy.
- **Required change:** Record these in ADR-0027 §1.2 and the Stage 5/7 test list; state "iOS: `MFMessageComposeViewController` only, never `sms:`".

### 7. watchOS notification action routing and copy (Medium, watchOS)
- **Location:** ADR-0022 §8; UX_COPY W-01..W-04; `App/ViadereWatch/*`; `WatchRootView` ("No, it isn't me" sends `.deny`).
- **Issue:** (a) The watch app has no `UNUserNotificationCenterDelegate` today. An iPhone-originated notification mirrors to the watch with the iPhone's category actions; responses to mirrored notifications are delivered to the iPhone app, but behavior differs once a watchOS app is installed and may deliver to the watch app instead (**verify on device**, Stage 4). The matrix assumes Deny works from the wrist; if routed to the watch app it must forward via `WCSession.sendMessageData` (needs a reachable iPhone) or `transferUserInfo` (queued, no immediacy) and must not sign locally (the watch has no key). (b) `.foreground` "Review" on a mirrored notification cannot bring the iPhone app forward; on the watch it opens the watch app. The matrix F7 cell "Review →App" is only true on the phone. (c) N-03's wording "Approve sign-in to {Business}? Only approve if you started this." appears on the wrist where Approve does not exist; W-02 is only in the watch app. (d) The watch UI has only "No, it isn't me", no separate "This wasn't me"/report, so F-25 is not yet fixed; ADR-0022 §8 requires both.
- **Required change:** Define in UX_COPY a watch-specific line for the notification (via the content extension for the watch interface or a category variant, or accept the phone wording and add W-02 as the first long-look line); add a Report action and `report` decision on the watch with signed `deny_reason: not_me`; specify the watch-to-phone relay and its failure copy (E-02-style, "Open your iPhone"); keep the "no key on the watch" invariant with a test that `WatchSync.handle` refuses approve for `authenticate`/`authorize` (this already holds in `inlineAssurance`).
- **Citation:** Apple "watchOS: Notifications" and "Sending and receiving data with WatchConnectivity".

### 8. Wear OS (Low, Android/Wear)
- Wear OS bridges phone notifications and shows their actions; action responses run on the **phone** for bridged notifications, and a notification action there can be a Deny on the phone. A standalone Wear OS app would need its own FCM registration and has no `BIOMETRIC_STRONG` on most watches. ADR-0022 §8's rule "same as watchOS, view/deny/report only" is feasible; add to the Android design that bridged notifications must use the same `auth: false` Deny and `setLocalOnly(false)` explicitly, and that no Approve action is ever defined (including as a wearable extension). Defer standalone Wear to a new ADR as ADR-0022 already says.

### 9. Notification privacy on the Lock Screen is a default, not a guarantee (Medium, iOS and Android)
- **Location:** UX_COPY N-02..N-05 and §0 rule 4; FLOW_MATRIX Locked column.
- **Issue:** The NSE sets `title`/`body` with the business name and sentence. Apple's default preview setting is "Always" for most users, so the business name and "Approve sign-in to X?" display on a locked phone; "hidden previews" is a user choice. The category sets `hiddenPreviewsBodyPlaceholder` ("Viadere needs your attention") but not `.hiddenPreviewsShowTitle`, which is right. Android's default is to show content on the Lock Screen; the app should set `setVisibility(VISIBILITY_PRIVATE)` with a `setPublicVersion` generic notification so the user's Lock Screen setting is respected, and lock-screen visibility is per channel, user-overridable.
- **Required change:** State in UX_COPY §0 rule 4 that the business name may appear on a locked device unless the user hides previews, and that no code, number, amount, payee or URL is ever in the payload or the notification (already so). Android: specify `VISIBILITY_PRIVATE` plus a generic public version. Time Sensitive: the entitlement exists; restrict `.timeSensitive` to `push_approval` and `payment`, use `.active` for links and codes, so Focus is not bypassed for low-value items.
- **Citation:** Apple `UNNotificationCategory.hiddenPreviewsBodyPlaceholder`; Android `Notification.Builder.setVisibility` and `setPublicVersion`.

### 10. Live Activities must not carry auth or payment content (Medium, iOS)
- **Location:** `Push/LiveActivityManager.swift`, `ViadereDecisionIntentBridge`, spec silent; ADR-0022 silent.
- **Issue:** The Live Activity widget and its decision intent exist for non-security flows. Live Activities are visible on the Lock Screen and Dynamic Island, run up to 8 h active and then up to 4 h on the Lock Screen, accept updates via ActivityKit push with a small payload and a budget, and their button intents run in the app process. The intent bridge already refuses protected-data-unavailable and security approvals (`inlineAssurance` returns nil for Approve), which is right.
- **Required change:** Add a rule: no Live Activity is started for `push_approval`, `payment`, link or code deliveries; a Core test asserts `LiveActivityPolicy` returns not eligible for method kinds in the new auth taxonomy. A Live Activity may exist for non-security statuses only.
- **Citation:** Apple "Displaying live data with Live Activities".

### 11. Cold launch, locked-since-boot and NSE availability (Low-Medium, iOS)
- **Location:** FLOW_MATRIX §4 note 4; `AppDelegate`, `AppModel.enqueueWhileLocked`; `KeychainSecretStore` (`AfterFirstUnlockThisDeviceOnly`).
- **Observed correct:** the delegate is set in `didFinishLaunching`, which iOS requires for a cold-launch response to be delivered; categories are registered at launch; an app-lock queue exists (`enqueueWhileLocked`).
- **Issues:** (a) After a reboot and before first unlock, `AfterFirstUnlock` items are unreadable by the NSE too, so the push will show N-08/N-01 only; the matrix note covers the app but not the NSE. (b) The NSE must not be the only path: ensure the app re-fetches on foreground, as the design says. (c) `UNNotificationServiceExtension` runs only for pushes with `mutable-content: 1` and an alert; ADR-0020 §6 should state that explicitly and that `apns-push-type: alert` is used, with `apns-collapse-id` = request id. (d) Silent pushes (`didReceiveRemoteNotification`) are throttled and not delivered after the user force-quits the app; no auth flow may depend on them.
- **Required change:** Add these as matrix notes and Stage 4 test cases.

### 12. Universal links, `UIApplication.open` and the `/l/`, `/h/` AASA paths (Low-Medium, iOS)
- **Location:** ADR-0021 §4.3; FLOW_MATRIX §4 note 2; `ViadereApp.swift` (`onOpenURL`, `onContinueUserActivity`); AASA components `/c/* /l/* /h/* /a/* /k/*`.
- **Observed correct:** Opening a business HTTPS URL with `UIApplication.open` (no `universalLinksOnly`) lets iOS open the business app if its AASA claims the path and the app is installed; otherwise it opens Safari. There is no silent background browser launch: `open` works only from a foreground app, and the confirm-before-open screen is a user tap, which satisfies spec §21. No `Referer` is sent from an app-initiated open. No in-app web view is used.
- **Issues:** (a) The Viadere link-service `return_url` with `vdr_code` as a **query** parameter puts the bearer into Safari history, the business's access logs and any third-party loads on that page; ADR-0021 §4.5 already requires no-referrer and no third-party assets, but also prefer the **fragment** (`#vdr_code=`) so it is not sent to the server on the first request and the page's script posts it; the authority and SDK vectors must follow whichever is chosen. (b) A universal link for a path on Viadere's own domain tapped inside Safari on the same domain does not open the app; irrelevant to business links but relevant to `/get`. (c) AASA `/l/*` and `/h/*` kept one release (ADR-0027 §4) is fine, but the "This link is no longer used" screen must never call `redeemHandoff`; add a test. (d) The F-08 fix (confirm before `redeemHandoff`) is a Stage 4 task; confirm `AppModel.open(url:)` does not redeem on handling.
- **Citation:** Apple "Supporting universal links in your app", `UIApplication.open(_:options:completionHandler:)`, `universalLinksOnly`.

### 13. Android App Links, Credential Manager and deferred verification (Medium, Android)
- **Location:** FLOW_MATRIX §4 note 5; ADR-0021 §4.3; spec §8.
- **Issues:** (a) App Links verification (`android:autoVerify`, `assetlinks.json` on the host) applies to Viadere's own host; business hosts are the business's. For a business URL opened with `ACTION_VIEW`, the system opens the business app only if the business app is verified for that host (or the user chose it); otherwise the default browser (or a chooser, since Android 12 unverified web links always open in the browser). Viadere cannot force either; document it as business guidance and as a harness check. (b) Passkeys on Android are used through Credential Manager (`androidx.credentials`) in the **business's** app or browser, so Viadere's app does not need it for push MFA; the Viadere authorize page (ADR-0024) uses the browser WebAuthn ceremony. If Viadere wants Credential Manager for its own account passkeys, that is Stage 7 scope; spec §8's row lists it, so say "not required for push MFA" in ADR-0030. (c) Keystore: `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)` with timeout 0 means per-use authentication with a `BiometricPrompt.CryptoObject`; the key must be created with `setInvalidatedByBiometricEnrollment(true)` for the payment key; combining `DEVICE_CREDENTIAL` with `BIOMETRIC_STRONG` for a `CryptoObject` works from API 30; the minimum Android version for the app must be stated (API 30 is a practical floor). StrongBox is optional; attest the key with `setAttestationChallenge` and send the chain at enrollment so the server can record the security level (this is the equivalent of the iOS App Attest and Secure Enclave facts). (d) Play Integrity is the App Attest equivalent and should be named in ADR-0030 or the Android design.
- **Required change:** Add the Android minimum API level, key attestation and invalidation settings to the Android design section.
- **Citation:** Android "Verify Android App Links", "Authenticate to Credential Manager", "Show a biometric authentication dialog", "Android Keystore system".

### 14. ADR-0030 packaging (Low-Medium, A6/A7)
- **Swift:** SwiftPM mirror repositories with signed tags is the standard approach and is feasible; `ViadereConnectKit` using `UIApplication.open` for "open Viadere for enrollment/approval" needs the Viadere URL scheme or universal link and `LSApplicationQueriesSchemes` only if it calls `canOpenURL`; prefer universal links and no `canOpenURL` probing (privacy). Partner apps cannot read Viadere's keychain, so the kit must be launch-only; the ADR says so.
- **Android:** The split `viadere-android` (core) and `viadere-android-fcm` is sound; Firebase Messaging is a hard requirement for FCM, as noted. Add: the core artifact must not declare `POST_NOTIFICATIONS`, `SEND_SMS` or exported components in its manifest; partner apps merge manifests, so any exported component in the library is an attack surface for the partner. Declare `<queries>` entries only in the app, not the SDK.
- **Kotlin package review:** **not performed**; no Kotlin source is present at this commit. Reopen when the package merges (A7).

### 15. Number entry UX and same-device flows (Low-Medium, iOS and Android)
- **Location:** ADR-0022 §2.3, §2.6; UX_COPY S-MFA-01, S-MFA-10.
- **Feasibility:** A numeric field with `keyboardType: .numberPad` (iOS) or `inputType=number` (Android) is trivially feasible. Notes: (a) set `textContentType` to none and disable autofill suggestions so the keyboard does not offer a pasted code; (b) the field must not accept pasted text from a notification or clipboard in the same-device case, because an attacker's overlay or a clipboard hijack defeats number matching; (c) mark the screen secure on Android (`FLAG_SECURE`) so screenshots or screen sharing do not expose the number in the field and so overlay attacks are harder; hide-overlay-windows is also available (`setHideOverlayWindows`, Android 12+); (d) iOS lacks overlay risk but Screen Recording shows the field, so the 2-digit entry must not be prefilled; (e) the same-device S-MFA-10 hint relies on app switching; on iOS the business app can be shown in Split View on iPad only, so the cost is real and the passkey recommendation (ADR-0022 §6) is the right mitigation.
- **Required change:** None to the design, but add (a)-(c) to the Stage 4/7 acceptance list.

### 16. Biometric prompts and key policy on iOS (Low, iOS)
- Existing: `AppleVaultKeyProvider` and the approve v2 keys use Secure Enclave keys with `.userPresence` / `.biometryCurrentSet`; `NSFaceIDUsageDescription` is present. The UX_COPY S-MFA-04 `localizedReason` is shown through the `LAContext` or `kSecUseOperationPrompt`; it must be set on the context used for the signing operation (it is set in the vault; confirm in `AppleApprovalKeyVault`).
- `.userPresence` (used for the link-service factor, ADR-0021 §5.3) allows the device passcode as fallback; this is intended ("user presence required") but the evidence `uv` value must say passcode, not biometric, which ADR-0022 §3 and ADR-0024 §5 already track as `amr: pin`. Adding or removing a face or fingerprint invalidates `.biometryCurrentSet` keys, so payment re-enrollment must have a documented path (S-PAY-02 covers cool-down). The state `keyInvalidated` exists in `ApprovalError`.
- **Citation:** Apple "Protecting keys with the Secure Enclave", `SecAccessControlCreateFlags`.

### 17. Key-log head verification in the app (Low, iOS and Android)
- Pinned keys as a build setting and a 15-minute freshness window are feasible on both platforms. On Android the keys go in `BuildConfig`/resources, and the network layer must use a Network Security Config that blocks cleartext and pins the API host. iOS has `PinningSessionDelegate` already. On a mobile network with background restrictions the head check can fail; the design says fail closed for sensitive actions only, which is feasible; state that Deny and Report never wait for a head check.

## Spec §7 / §21 compliance

- "No arbitrary background browser launch": satisfied by ADR-0021 §4.3 (explicit Continue, system open, no web view).
- "No assertion that watchOS is a generic FIDO2 authenticator": satisfied by ADR-0022 §8, which goes further than the spec.
- Spec §7.1 and §19.1: consistent with the platform rules; the statement "validate task and intent behavior across versions" is the Stage 7 matrix requirement (Android 12, 13, 14, 15 and at least one Samsung and one Xiaomi/Oppo device).
