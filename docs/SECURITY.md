# Viadere Security

Security is the top priority. This document has two parts:
1. A STRIDE threat model for each component.
2. The **normative wire formats**. The server (Vapor) and the app (ViadereKit) must implement them byte-for-byte. ViadereCore is the reference implementation.

## 1. Threat model (STRIDE)

| Component | Threat | Mitigation |
|---|---|---|
| **Business identity / registry** | S: impersonating a merchant with a look-alike handle or code | Handles are ASCII-only. Reserved words and reserved-word confusables are blocked. The server rejects any new handle whose `confusableSkeleton` matches an existing one. Codes are unique on `canonical` (I→1, O→0) and never reassigned. Only `verified` businesses appear in discovery or routing, and verification is re-checked when routing starts. |
| | T: altered QR or link | `ConnectLink` parsing is strict: https only, exact hosts, no userinfo, port, fragment or extra query. The context is HMAC-bound to the code. |
| | E: buying priority | `Interaction.effectivePriority` clamps it: marketing and rewards are at most normal, and only `security` may be urgent. |
| **Consumer app / devices** | S: stolen bearer token | Every sensitive route is `deviceSignedBearer`: it needs the bearer token **and** a Secure Enclave signature. Devices can be revoked. A session (token family) is **bound to the device it enrolled**: its bearer token is refused with any other device's key. |
| | E: a stolen bearer or refresh token enrolls a new device whose key approves payments (or re-enrollment after a thief re-registers biometrics) | A bearer token alone never creates a device. `POST /v1/devices` needs a fresh, user-verified **passkey assertion over the enrollment challenge** (§2.5), or the single use of a session a passkey ceremony created less than 5 minutes ago. Revoking a device revokes the sessions bound to it, and refresh-token reuse revokes the family **and** the devices enrolled through it after the reused token was issued (not the device the session already belonged to). A rotated refresh token presented again within 60 s returns the same new pair (lost response, app/extension race); logout ends the session only. `hardwareBacked` is a client claim, so keys are `attested = true` only when Apple **App Attest** verified them (§2.5): with `APP_ATTEST_MODE=require` (the production default) an enrollment without a valid attestation bound to this challenge, account and key list is refused. |
| | E: a copied refresh token (or the 60 s grace replay) mints a session | When a session is bound to a device, `POST /v1/auth/refresh` must carry that device's `VIADERE-SIG-V1` signature (§2.8): without it the token is refused before anything changes, so a thief can neither obtain the grace pair nor trip reuse detection against the owner. |
| | E: the new (attacker) device approves high-risk requests at once | New-device **cool-down**: a device enrolled by an account that has **ever** had an app device (revoked or expired ones included, however long ago, so neither deleting the owner's devices nor waiting resets it; only a brand-new account's first device is exempt) cannot approve `high`/`critical` requests for 24 h (72 h when it could not be attested in `report` mode) unless a trusted device confirms it with a biometric signature (§2.17). In `require` mode a lapsed account's new device must attest as well. It is also not a **trusted device** (`DeviceTrust`, §2.5): it cannot invite to a household, accept an invitation, link a phone by code, revoke other devices or sessions, delete the account or dismiss notices. Every enrollment (App Clip too) is an in-app security notice plus a push to the other devices. Deny and report always work. |
| | E: App Clip enrolls a full device that is never cleaned up | `clientKind: appClip` devices get a request key only, live 7 days (session capped to match), and **can never decide** an interaction. In `require` mode they must attest too (against the Clip's own app id). |
| | E: "Set up again" swaps a stolen session's way into the owner's account | A **live** device named by `replacesDeviceId` is not revoked: it is marked pending, keeps working, and is told (notice + push, "Not you? Cancel") while the new device cools down; it is revoked only when the new device is confirmed or its cool-down ends, and the owner can cancel from it at any time, which revokes the NEW device (§2.5). |
| | E/S: the account is lost with every device and the passkey | **Account recovery** (§2.26): 10 single-use recovery codes issued at registration (peppered HMACs only) plus a recovery ID; a recovery registers a NEW passkey that cannot sign in for **72 h**, during which every existing device is notified and any trusted device can cancel; afterwards old devices, sessions, passkeys and codes are revoked and new codes issued. Rate-limited per IP, per recovery ID and globally (malformed input never touches the shared budgets), and an account locks for 24 h after 5 wrong codes. **At most one recovery is open per account**, enforced by a partial unique index; cancelling (or making new codes) closes every open one. Activation also **ends household grants in both directions** (counterparts are notified) and puts **every phone link back into a 72 h cool-down**. Regenerating codes needs a trusted device **and** a fresh passkey assertion. |
| | T: modified request | `VIADERE-SIG-V1` covers the method, path and query, timestamp, nonce, and body hash. |
| | R: "I never approved that" | Decisions are device-signed canonical JSON that includes the challenge **and a digest of the context that was shown** (v2, §2.4), and Viadere stores the signed decision. Businesses receive a per-business device pseudonym and the server's attestation, never the raw signed decision (it names the global device id); Viadere exports it for a dispute (`export-dispute`). Audit events are append-only and chained with a keyed MAC (§2.22). |
| | T: the approval screen shows one thing and the device signs another / hostile business text on the screen | A v2 decision carries `contextDigest = SHA-256` of the canonical `{businessId, kind, payload, expiresAt}`; the server recomputes it from the stored interaction and refuses a mismatch (`409 context_mismatch`), and refuses an approve/confirm/select/reply without one (`400 context_digest_required`). The server rejects business text with bidi, zero-width, control or line-separator characters, over-long (graphemes, scalars, UTF-8 bytes) text, and text that starts with or (for names) mentions "Viadere" (§2.19); clients sanitise again before display. |
| | E: weak approval for a high-risk action | `AssurancePolicy` requires a biometric-gated key (`approvalBiometric`, `.biometryCurrentSet`) for high and critical authorize or authenticate. A passkey or passcode is not enough. |
| **Approvals (MFA / authorize)** | Replay or staleness | Each interaction has a single-use `ChallengeNonce`, consumed through `ReplayGuard` (`decision:{interactionId}`). Also enforced: `expiresAt` (≤ 15 min for security kinds), `signedAt` age ≤ 300 s, and future skew ≤ 60 s. |
| | Phishing via SMS YES/NO | Never allowed. Security kinds cannot be satisfied over SMS, RCS or AMB, and `ChannelRenderer` renders a secure handoff with no transaction details. Copy states that Viadere never asks for approval by text. |
| | I: lock-screen disclosure | Notification content is single-lined, length-capped and spoof-stripped. The app decides whether to show previews. |
| **Credential vault (Authenticator)** | S/E: an attacker who has the account (stolen session, passkey-enrolled device) reads or changes the vault | The vault key never reaches the server and is not derivable from account credentials. Every write is a signed manifest the server verifies with the same chain rules as clients; the calling account device must be **bound** to the signing vault member (binding happens only at creation, through a join an existing vault device approved, or a recovery-key restore). A new account device sees ciphertext and public keys only (§2.40). |
| | E: account recovery or an identity check restores the vault (SEC-DEV-005, §5.1, acceptance 7) | Account recovery (§2.26) yields an account session only. The vault opens only with an enrolled device's key or the separate vault **recovery key**; a restore replaces the vault key, retires the used recovery key and removes every other device (§2.40). |
| | T: server rolls back, forks or reorders the vault | Signed, hash-chained manifests; clients verify onward from the newest manifest they already trusted and refuse older, forked or gapped chains. Items carry monotonic revisions; blobs and envelopes are pinned by hash in the manifest. |
| | I: passkey private keys or TOTP secrets in the shared container, the identity store, logs or backups | Items are AES-256-GCM under per-item keys wrapped by the vault key; the vault key exists only in memory while unlocked and as HPKE envelopes sealed to device keys that need Face ID / passcode. The container is excluded from backup and holds ciphertext only; the system AutoFill store gets site and account name only (opt-out). |
| **SMS gateway** | S: sender ID is not identity | The phone number is treated as a routing identifier only. Linking requires the signed-in **device** and explicit confirmation of the masked number shown by a read-only preview. Unlinked numbers cannot route. |
| | S/E: account-link fixation (an attacker texts Viadere, then lures the victim into redeeming the attacker's link) | `GET /v1/sms/link-tokens/{token}/preview` (device-signed, rate-limited, does not consume) shows the full masked number; redeem is device-signed, echoes the confirmation, checks the live thread (contextRevision, not opted out), notifies the account's other devices, and the new link is **not an interaction target, RCS/SMS decider or SMS routing identity** for 24 h (72 h when the account has no other trusted device that could confirm it) unless a trusted device confirms it (§2.8). The SMS gateway treats a cooling-down link as no link: the number cannot open a session, forward text or list recent businesses. The account gets an in-app notice and an audit event even with a single device. |
| | E: OTP toll fraud / SMS pumping | Destination-country allowlist (default US, CA; Caribbean +1 regions separate), a platform-wide and a per-prefix verification-SMS budget with alert-level logging, per-consumer/per-phone limits, and an App Attest/DeviceCheck hook (stub until Apple credentials exist). |
| | I/E: one business's text answered by another business | The SMS thread is shared. While it is connected to business B, an interaction SMS from business A is replaced by a content-free notice, so the person's reply is never forwarded to B as an answer to A. Business-originated text is a single line (§2.10), so it cannot forge `Viadere:` lines, menus or other attributions. |
| | T: stale or duplicate provider webhooks | Provider signatures are verified. The server dedups by provider message id, and the engine is also idempotent (`recentProviderMessageIds`). Menus are versioned, expire, and are checked against `receivedAt` versus `issuedAt`. The context is persisted with CAS on `revision`. |
| | I: cross-tenant leakage | Each business has its own `SessionID`. `deliverBusinessMessage` renders only the active session (business id **and** session id must match); everything else is held. A switch never forwards to the previous business. |
| | D: spam or floods | Per-phone and per-business rate limits (server). Dedup memory is capped. The in-memory limiter keys IPv6 clients by /64, has one capped table per namespace (a flood in one cannot starve the global per-IP limiter) and evicts least-recently-used buckets (§2.23). |
| | T: a digit meant for the previous menu is applied to the new one | A digit within a few seconds of a menu change re-shows the menu instead (SMS has no sender timestamp); RCS uses the provider timestamp. |
| | Carrier compliance | STOP-family keywords and HELP/INFO work in every state and cannot be escaped. START, UNSTOP and YES opt back in only from `OPTED_OUT`. Opted-out numbers receive nothing except HELP replies and START handling. |
| **Account-link and handoff tokens** | Replay, guessing, open redirect | 256-bit tokens. Only `SHA-256` is stored. Tokens are single-use, have a short TTL (15 min link, 10 min handoff), and are bound to phone + conversation. Fixed paths `/l/{token}` and `/h/{token}`, with no redirect parameters. |
| **Business API** | S/E: tenant crossover | API key → businessId. Every query is tenant-scoped. Idempotency keys are required on POSTs, including webhook create, secret rotation and interaction cancel (§2.27), so a retry cannot create a second endpoint or rotate a secret twice. |
| | E: test-mode keys reach real people, bypass quota/abuse/billing | A test key can address only **sandbox** relationships (consumers with status `sandbox`: no passkey, device or phone); a live key cannot address one. This holds on every business path: interactions, statuses, messages, rewards, points, redemption codes, reward revocation, interaction outcome and cancel (a test key sees only test interactions); business-wide state (the loyalty program, broadcast rewards) is live-only; an activity key supersedes only the same relationship and mode. Consumer routes only ever show live interactions. Test traffic never pushes, texts or counts. |
| | E: a compromised **messaging** key approves a payment or runs a verification (acceptance 1) | API keys carry an explicit **capability scope set** (§2.28): `message.send`, `auth.challenge`, `transaction.approve`, ... Every request goes through one policy function (`PolicyService`, §2.29) that needs the capability in the **key's scope and in the business's current entitlements**. An interaction of kind `authorize` needs `transaction.approve`, `authenticate` needs `auth.challenge`, everything else `message.send`; the check runs before an idempotent replay can answer and before any customer data is read. A messaging-only key gets `403 insufficient_scope`, the attempt is audited (`policy.denied`, actor = the key). Cancelling or reading an approval needs the capability too. |
| **Approve v2 / key directory** | S: a relay binds its own key to a business at enrollment | The business verifies the device's statement and signs a confirmation over its digest with a **directory-published** key; the device activates only a key whose digest it signed itself, else deletes and revokes (section 2.53). |
| | S: a relay or attacker presents a fake business key (E2EE or request signing) | Every business key is signed by the business root, logged in a Merkle log with signed heads, verified with inclusion and consistency proofs and a pinned root on the device (sections 2.51, 2.52). |
| | T: root key swapped, rolled back or forked | Succession needs both roots' signatures and clears inherited keys; the device blocks and alerts on any root change; heads must be consistent with the last accepted one; the monitor flags unexpected entries. |
| | T: algorithm downgrade, `crit`/`jwk` tricks, non-canonical JWS | `alg == ES256` only, a three-member header, no `crit`, canonical payload re-serialized and compared (section 2.54). |
| | T: displayed amount differs from the signed one | `txn_digest` of exactly the displayed details, verified by the business against the transaction it holds. |
| | R: a result replayed or presented for another request, audience or customer | Audience, subject, request id, challenge and expiry are signed and checked; the business consumes each result once (`ReplayGuard`). |
| | I: the relay reads payment details or learns a decision | End-to-end HPKE envelopes with a business signature inside; webhooks v2 carry ids only; details are cleared at the terminal state (sections 2.54, 2.56). |
| | I: a customer is correlated across businesses | Pairwise approval keys, HPKE keys and `subject_ref`s per relationship; no shared device identifier (section 2.53). |
| | D: prompt flooding or fatigue | Per-relationship rate, warning, pause after repeated denials, local counter, freeze (sections 2.55, 2.57). |
| | E: a stolen device or relay unfreezes approvals | Unfreeze needs a trusted device and a fresh biometric proof; a business can lift only its own freeze (section 2.57). |
| | E: capability creep: a key, or a business, quietly holds more than it was approved for | Entitlements are a **ceiling evaluated at use time** (§2.29): revoking a tier or capability removes it from every existing key on its next request (`403 not_entitled`). Defaults are Tier M only (messaging). Grants are operator actions with a recorded purpose justification (and, for identity attributes, a heightened-review reference, AGE-007), a fresh passkey, and an audit event; a category label, a plan or a verified badge never grants anything. The dashboard only offers capabilities the organization holds. |
| | I/R: one business links a customer across businesses, or enumerates customers (acceptance 2) | The business-facing customer reference is `subject_ref` (§2.30): `sub_` + base64url HMAC-SHA256 under the dedicated `SUBJECT_REF_KEY` over `VIADERE-SUBJECT-V1 \n businessId \n consumerId`. Pairwise (one value per business and customer), non-enumerable without the key, stable per business, never the global consumer id. Business APIs resolve it **inside the calling business only**: another business's ref, a ref that does not exist and a mismatched `relationshipId`/`subjectRef` pair are the same plain `404`. |
| | E: a capability is abused platform-wide (or by one business) and cannot be stopped without suspending everyone | **Kill switches** (§2.29): an operator turns one capability off globally or for one business, with a reason and a fresh passkey; it is stored in the database, audited and cached for at most 5 s. Sensitive capabilities (sensitivity high or critical) **fail closed** when the switch table cannot be read. Law/policy rules block a capability by jurisdiction, or allow it only in listed ones (an unknown jurisdiction then fails closed). |
| | I: an identity disclosure justified by an old, broad consent (no blanket consent, §6.4) | `age.minimum` and `identity.*` need a **per-request receipt** (§2.29): the customer's confirmation of one disclosure, naming capability, purpose, recipient business, fields and expiry (at most 10 minutes), bound to one request id. It cannot be reused for another business, subject, capability, purpose or request, is spent atomically on use (concurrent requests: one wins), can be revoked before use, and every grant and every use is audited. Relationship-level consent never satisfies it. |
| | I: the "age only" result leaks a birthdate, name or document number (acceptance 6) | The catalog lists the **exact fields** each capability discloses (§2.28). `age.minimum` discloses `meets_threshold`, `assurance`, `issued_at`, `expires_at`, `audience` and nothing else; results are built by projecting onto that list (`CapabilityDefinition.project`), and a catalog self-check (`CapabilityCatalog.audit()`, run in the unit tests) fails if any capability other than `identity.name` / `identity.address` lists a personal-data field. |
| **Webhooks** | S/T: forged or modified events | `Viadere-Signature: t=…,v1=HMAC`, 300 s tolerance, constant-time compare, multi-secret rotation. |
| | S: SSRF through a business-supplied URL, DNS rebinding | https + public host only; the host is resolved **once**, every address is vetted (including IPv4 embedded in IPv4-mapped, NAT64 and 6to4 addresses, CGNAT, TEST-NETs, multicast, reserved) and the connection is pinned to the vetted address (`dnsOverride`) while TLS and `Host` keep the original name; redirects are never followed. |
| | I: message text kept in plaintext in the delivery queue | Delivery bodies are encrypted at rest (AES-GCM, row-bound), delivered and dead deliveries are purged after 30 days, and bodies mentioning a deleted consumer are scrubbed. |
| **RCS channel** | S/T: forged or replayed provider events | `X-RCS-Signature: t=…,v1=HMAC-SHA256("{t}." + body)`, 300 s window, constant-time compare; one `403` for every failure; provider event ids de-duplicated (§2.11). |
| | E: approving a sensitive request by tapping a suggestion | Suggestion taps are *unauthenticated replies*: `AssurancePolicy` never lets them satisfy `authenticate`, `authorize`, unknown kinds or `high`/`critical`, and deny/report are refused on a channel. Sensitive interactions are rendered as a secure handoff link, never as chips. |
| | S/R: forged, replayed, forwarded or stale postbacks | Postback data is an opaque, MAC-signed, single-use token (never an id); bound to the phone it was sent to; valid only while its menu version is the phone's active one and within the menu TTL (the SMS rules); consumed by compare-and-swap together with the decision. |
| | Silent downgrade | The same interaction falls back to SMS when the phone is not RCS-capable or the provider fails; a sensitive one becomes a handoff link on both channels. |
| **Apple Messages for Business** | Unapproved multi-merchant brokerage | The adapter is an inert placeholder behind a flag that defaults off: it never sends, never reports capability and rejects every inbound webhook. |
| **Business dashboard** | S: credential phishing, password reuse | Passkeys only (user verification required); separate credential store and RP-scoped origin; no passwords to steal. |
| | S/E: squatting an address by signing up with it | Sign-up creates an **unverified** account with no session and no organization; a 6-digit code (peppered hash, 15 min, 5 attempts, single use) goes to the address, and the organization application starts only when it is entered. An unverified sign-up is purged after 24 h and **never blocks** the address: a later sign-up or an invitation for it replaces the stale record. Answers are identical whether or not the address exists; sending is rate-limited per address and per IP, a pending sign-up younger than 15 minutes is **not wiped** by someone else's sign-up for the same address (and that attempt spends none of the address's budget; resend has its own), and wrong guesses are capped per address per day however many codes are issued (§2.24). |
| | S/E: taking over an account through an invitation | An invitation is emailed to the invited address (the inviter never sees the token) and only ever creates a **new** account, after the invitee also enters a code emailed to that address. An address that already has a *verified* account signs in and accepts from its own session; an unverified squatter does not count; `invite/begin` answers identically either way and `finish` is a generic refusal. A sign-up or invitation that ends in a session counts as a first sign-in. |
| | S/E: cookie theft or fixation, cross-site requests | `__Host-` cookie (Secure, HttpOnly, SameSite=Strict, no Domain), only the SHA-256 stored, a new session on every sign-in, idle + absolute timeouts, per-session CSRF token and Origin check on every state change (§2.12). |
| | E: a stolen session minting credentials | Passkey re-authentication (≤ 5 min old) for creating API keys or webhooks, rotating secrets, adding an owner and every operator mutation. |
| | E: role abuse and tenant crossover | Least-privilege roles checked server-side on every request against the *current* membership; every query scoped to the session's organization; admins cannot touch owners; the last owner cannot leave. |
| | I: leaking customer data to the business | Analytics and consent views are aggregates; webhook payloads are redacted in the delivery log; business views carry per-business pseudonyms. |
| | Script injection, exfiltration | CSP `default-src 'none'` with hash-pinned stylesheet (and one hash-pinned script on sign-in pages only), no inline event handlers or styles, no third-party assets, `frame-ancestors 'none'`; all output HTML-escaped. |
| **Operator console** | E: insider abuse | Separate realm and passkeys, shorter timeouts, re-authentication for every mutation, every action audited with actor kind `operator`; overrides can only restrict (throttle, suspend, downward priority ceiling) and never read the billing tier. |
| **Abuse by a business** | Spam, “I don't recognize this”, pestering | Per-business complaint and opt-out rates with automatic throttling; suspension takes effect on the next request and cancels pending interactions; operators review before any handle or code is issued. |
| **Embeddable button** | Third-party script risk | Immutable versioned files with SRI, no network access, cookies, storage or iframes; it can only link to `https://viadere.com/c/{CODE}`; the label is set as text, never markup. |
| **Rewards and redemption codes (P3)** | S/T: a client claims it is eligible, or reshapes the rules | Eligibility (`eligible`, `notToday`, `limitReached`, `notYetValid`, `insufficientPoints`, `redeemed`, `expired`, `revoked`) is computed **only** on the server from its own clock, the reward's rules in the business's time zone (DST-aware) and its own records. `redeem` re-checks it inside the reservation transaction (§2.13). |
| | R/E: double redemption, or racing past a per-day limit | A code reserves its slot and points when issued: unique `(reward, consumer, window, slot)` decides concurrent attempts, a compare-and-swap debits points, and an unused code's reservation is released when it expires. The business consumes a code with a single compare-and-swap (`issued → consumed`), so exactly one of any number of concurrent validations succeeds. |
| | S: guessing or reusing codes | 50-bit random codes valid ~2 minutes, stored only as a pepper-keyed HMAC, looked up within the calling business only (another business's code is the same `404` as an unknown one), validation rate-limited per business, and never logged or audited in clear. |
| **Wallet passes (P3)** | S/T: a forged or altered pass | The server signs passes (`manifest.json` SHA-1 per Apple's format, detached PKCS#7 with the Pass Type ID certificate and the WWDR intermediate; §2.14). Certificates and keys come from the environment, are validated at startup (parseable, matching key, unexpired) and never committed. |
| | S/E: reading or hijacking a pass's update channel | The PassKit web service needs the per-pass `authenticationToken`, derived as `HMAC(pepper, id ‖ salt)`, stored only as a keyed hash and compared in constant time; wrong token, wrong type and unknown serial are one `401`, and failures are rate-limited. A pass is bound to one consumer and one subject (loyalty account, reward or ticket). |
| | I: personal data in passes | Passes carry only what the person's own card shows (points, offer title, event details). No phone, email, name, member number or redemption code is embedded. |
| **Live Activities (P3)** | Unwanted or promotional activities | Pushes are sent only for `status` interactions whose purpose `LiveActivityPolicy` allows (`transactional`, `accountService`, `support`), never marketing, rewards or security; test-mode keys never reach devices; the start alert is generic. Tokens are per device, bound to a business the person is connected to, and dropped when APNs reports them invalid. |
| **Household / delegation (P3)** | S/E: granting access without the delegate's consent, or guessing a code | A grant exists only after the delegate accepts a single-use, 24-hour, pepper-hashed code in their own app; lookups are rate-limited per consumer and globally (only *failed* lookups spend those budgets, so valid previews cannot drain them), previews have their own per-account limit, and an invitation locks after 10 attempts (§2.15). |
| | E: a stolen session widening access | Sensitive scopes (security, account service) need a fresh `approvalBiometric` signature bound to the exact scope, device and time; each proof is single-use; such grants last at most 30 days. Sensitivity is recomputed from the purposes, never taken from the client flag. |
| | I: a delegate's push leaking, or pushing out-of-scope interactions | An interaction is pushed to a delegate only when an active grant covers its purpose **and** business (the same test as the scoped API); the payload is the grantor's generic one (opaque `iid`, no business, amount or name), and the delegate fetches details through the scoped API, which checks the grant again. Other purposes, other businesses, revoked or expired grants and deleted delegates are never notified. |
| | E: a delegate approving a sign-in or payment | Server-enforced: delegates can never decide `authenticate` or `authorize`; viewers decide nothing; managers may only confirm, decline and choose. Out-of-scope interactions are a plain `404`. Every use, denial, grant, acceptance, revocation and expiry is in the hash-chained audit and the grantor's household feed. |
| **Verify (WP3): Wallet IDs and Didit** | S: a forged or edited ID presentation (wrong issuer, edited element, swapped device) | The server trusts only certificates that chain to a **pinned IACA root** loaded from a directory (§2.60); the document-signer certificate needs the mdoc profile (`id-mdl-kp-mdlDS`, digitalSignature, EC key); the MSO signature (ES256/384/512 only), **every** issuer-signed item's digest, the MSO and certificate validity, and the **device signature over the session transcript** must all verify. Tested against Apple's sample and synthetic issuers (tampered digest, wrong issuer, expired, wrong key usage, unsupported algorithm). |
| | R/S: replaying a captured presentation, or answering one request with another's response | The Wallet nonce is a single-use value in a row (compare-and-swap before use), 5 minutes at most, bound into the HPKE `info` and the device-signed transcript with the merchant and team ids and the encryption-key hash. A replay finds a spent nonce; a response for another attempt cannot be opened. |
| | I: personal data from the document at Viadere | The DeviceResponse exists only in memory: it is verified, reduced to the **requested** elements (`WalletElementPlan`), reduced again to the capability's output fields (`ClaimsBuilder`, `CapabilityDefinition.project/violations`) and dropped. Age thresholds request `age_over_NN` and never the birthdate; a birthdate or `age_in_years` an issuer returns is used in memory only to answer the yes/no. Nothing is persisted or logged. |
| | I: biometrics and ID images at the provider | Images and the selfie go from the device to Didit; Viadere never receives them. The decision is re-fetched, read in memory, then the session and vendor user are deleted with `privacy_erasure` and the deletion is recorded; a failed deletion is retried by the background job and never forgotten (no foreign key ties it to a deleted request). `vendor_data` is an opaque attempt id. Biometric-template retention must stay off at Didit. |
| | S: a forged provider webhook | `X-Signature-V2` (canonical JSON) or `X-Signature` (raw bytes) plus `X-Timestamp` ±300 s, with the previous secret accepted during a rotation; the deprecated envelope-only `X-Signature-Simple` is never accepted. The body is only a hint: the decision is always re-fetched with the API key and must carry the attempt's `vendor_data` and session id. |
| | I: leaking the result (to another business, to a log, to a replay) | The result is retrievable only with the owning business's credential, once, for 15 minutes; a foreign reference is a plain 404. Payloads are sealed per row and erased at retrieval; identity attributes are sealed to the business's published HPKE key when it has one. The webhook carries `request_id` and `result_ref` only. |
| | I: learning whether a customer is under an age (AGE-005) | Under the threshold, declined, abandoned, expired, unsupported document, provider outage and withdrawn consent all end as the same `not_verified` with an empty result, the same webhook and the same timing class; the dashboard shows counts of the three outcomes the API itself shows. |
| | E: a compromised messaging key runs a verification (acceptance 1) | `POST /v1/verification-requests` needs the verification capability on the key **and** in the business's entitlements (tier V, a recorded purpose, a heightened-review reference for identity attributes); the disclosure is evaluated again with the creating key's current capabilities, so a revoked key, a withdrawn entitlement or a kill switch stops a request already in flight. |
| | E/R: disclosing more than the person agreed to | Consent is per request: the person consents to a SHA-256 digest of the displayed recipient, purpose, fields and expiry; the receipt is bound to the business, subject, capability, purpose and request, and **consumed** by the disclosure (one receipt, one disclosure). |
| **Server data** | I: database leak | Tokens and API keys are stored hashed. Phones are masked in logs. Audit `metadata` must be redacted. No message bodies in telemetry. Personal fields are AES-GCM encrypted with **row-bound** additional data (a ciphertext cannot be moved to another row or column, §2.21). |
| | T: rewriting the audit log with database access | Version 2 events are `HMAC-SHA256(AUDIT_CHAIN_KEY, …)` with the row id hashed; the key is not in the database; legacy unkeyed events are accepted only up to an operator-declared sequence; the chain head is exported to write-once storage (§2.22). |
| | I: personal data survives account deletion | Deletion also erases device names, signed decisions **that carry free text** (`reply`; the one permitted edit of the append-only `decisions` table; decisions with only ids, challenge and context digest are kept, §2.20), outbound SMS/channel rows and link tokens by phone, SMS thread state (an opt-out is kept as suppression only), delegation labels, stored outcome replies and webhook bodies; finished outbound rows, link tokens and deliveries are purged on a retention schedule. |
| | S: weak configuration in production | `ENVIRONMENT` is required (`development`, `test`, `staging`, `production`; no silent default). `staging` uses production rules. Any `DATABASE_URL` forbids ephemeral secrets. `RP_ORIGIN` must be an https origin of `RP_ID` outside development. Production secrets must be distinct values. |
| | D: unbounded input | Max lengths on every field (`InteractionValidation.Limits`). Payloads are capped (decision ≤ 8 KiB). |

**Residual risks:**
- A passkey that syncs (iCloud Keychain) is only as safe as that account; a thief holding it can enroll a device, but its high/critical approvals wait 24 h, it is not a trusted device, and the account gets an in-app notice and a push. A user who never opens the app and has no push token learns only from the audit log.
- App Attest proves a genuine, unmodified Viadere app on genuine Apple hardware **at enrollment**; it does not prove the person is the owner (the passkey, the cool-down and the notices do that), and the attestation receipt is not evaluated (no Apple fraud-metric). Assertions are verified and counter-checked (`AppAttestAssertions`) but no route requires one yet. `APP_ATTEST_MODE=off` or `report` (the non-production defaults; `report` is for rollouts) leaves the pre-attestation risk: a software key can be enrolled by anyone who completes the passkey assertion and then cools down for 24 h (72 h unattested in `report`). A brand-new account's first device is never cooled down, attested or not.
- Recovery codes are bearer secrets: someone who holds the recovery ID **and** one code can start a recovery, and if the owner has no trusted device that sees the notice (or never opens the app) it completes after 72 h and takes the account. Codes live on paper or in a password manager; the server cannot tell the owner's hand from a thief's. A thief who guesses nothing but triggers the 5-wrong-codes lock can lock the owner out of recovery for 24 h (availability only; the account's devices are notified). A recovery does not carry third-party trust over (household grants end, phone links cool down again, §2.26), but the person who recovered is trusted with the account itself: their new device cools down and must attest. Household members must be invited again; the recovered account's SMS/RCS number works again after 72 h or when a trusted device confirms it.
- During a pending device replacement both devices work, so a thief who enrolled the new device (stolen session + passkey) has a cooling-down device in the account for up to 24 h (72 h unattested in `report`) until the owner cancels; it cannot approve high-risk requests or act as a trusted device in that time. A legitimate "Set up again" whose old keys are gone cannot confirm the new device from the old one, so it waits out the cool-down.
- With a single device a phone link made from an SMS token waits 72 h (no confirmation possible); it can be removed from any trusted device meanwhile.
- DNS pinning for webhooks needs the vetted address to stay valid for the request; an address that is public at resolution and re-pointed afterwards is not an issue, but a malicious *public* endpoint is by definition reachable.
- A database writer who also holds `AUDIT_CHAIN_KEY` can forge the audit chain; only the exported heads in write-once storage detect that. Events before `AUDIT_CHAIN_LEGACY_THROUGH_SEQ` are protected only by the unkeyed legacy hash.
- A deleted account's decisions that contain a free-text reply lose their signed payload (they can no longer be re-verified); the others are retained, pseudonymous, for dispute handling (§2.20).
- Malware on a device that is unlocked and biometric-enrolled can still approve.
- Delegation can never approve authenticate or authorize (enforced by the server, §2.15).
- Wallet passes are reachable offline once added; voiding takes effect when the device next refreshes the pass.
- Verify: mdoc revocation (issuer status lists) is not consulted (`revocation: not_checked` in the provenance); a credential an issuer revoked after issuing is accepted until its MSO expires. Consent is bound to the request by a displayed-content digest and a device-signed request, but not by an Approve-style Secure Enclave signature; an attacker with an unlocked, signed-in phone could consent. The provider (Didit) sees the document, selfie and liveness video for the duration of a check; its own retention, residency and biometric-law posture is a contract and counsel matter (`docs/ops/DATA-INVENTORY.md`). Apple documents `pkRHash` only as "a SHA256 hash of the recipient public key": both the X9.63 and the SPKI hashes are accepted (the sample confirms X9.63).
- A redemption code shown on a screen can be photographed within its 2-minute life.
- The platform-wide household invitation budget is spent by *failed* lookups, so many accounts guessing wrong codes can still exhaust it for a while and temporarily block invitations for everyone (availability only; valid previews no longer spend it, and each account has its own failure and preview limits).
- Dashboard business accounts created before email verification existed are treated as verified (nothing proves their mailbox). Anyone who can read the mailbox of a pending sign-up (or who controls the mail provider) can verify it; sending is rate-limited per address and IP, so an attacker can at most make a victim's mailbox receive a few unsolicited codes per hour.
- While the shared rate-limit database is unreachable, security-critical limiters fail closed (the endpoint refuses) and the rest, including the per-IP limiter, run per instance until it recovers.

## 2. Normative wire formats

### 2.1 Common encodings
- **base64url**: RFC 4648 §5 alphabet with **no padding**. Decoders reject `+` and `/`.
- **hex**: lowercase on output. Input is case-insensitive.
- **Dates (JSON)**: `YYYY-MM-DDTHH:MM:SS.sssZ` (UTC, exactly 3 fractional digits). Parsers accept any fractional precision (truncated to ms) and `±HH:MM` offsets.
- **IDs**: lowercase canonical UUID strings.
- **Money**: `{"value":"285.28","currency":"USD"}`. The value is a decimal string with the currency's minor units, never a float.
- **ECDSA signatures**: P-256 / SHA-256, encoded as **raw `r‖s` (64 bytes)**, then base64url (86 chars). DER is rejected. Signatures are **canonical low-S**: `(r, s)` and `(r, n − s)` are both valid ECDSA signatures, and Secure Enclave output may use either, so encoders and decoders normalise `s` to `s ≤ n/2` (`ViadereSignatureEncoding`). Every verifier therefore accepts both encodings and sees one canonical byte string, and **no replay guard is ever keyed on a signature string**: request signatures use the nonce, decisions the challenge, enrollment the single-use challenge, step-up and confirmation proofs a hash of their signed content.
- **Public keys**: base64url of X9.63 uncompressed (65 bytes, `0x04‖x‖y`). Parsers also accept raw 64-byte `x‖y`.

### 2.2 Canonical JSON (used for signed decisions and link context)
- UTF-8, no whitespace.
- Object keys sorted by UTF-16 code units (equivalent to byte order for the ASCII keys we use).
- String escapes:
  - `"` → `\"` and `\` → `\\`
  - `\b`, `\t`, `\n`, `\f`, `\r`
  - other U+0000–U+001F → `\u00xx` (lowercase hex)
  - everything else is literal, including `/` and non-ASCII
- Integers in shortest form. **No floating point.** Absent optionals are omitted, never written as `null`.

### 2.3 Device request signing (`VIADERE-SIG-V1`)
Headers:

| Header | Value |
|---|---|
| `Viadere-Device` | device id (lowercase UUID) |
| `Viadere-Timestamp` | unix seconds, decimal |
| `Viadere-Nonce` | base64url, 16–64 chars (clients send 16 random bytes → 22 chars) |
| `Viadere-Signature` | base64url(raw r‖s) |

String to sign (LF-separated, no trailing LF):
```
VIADERE-SIG-V1
{METHOD uppercase}
{path?query exactly as on the request line, e.g. /v1/interactions?limit=20}
{timestamp}
{nonce}
{lowercase hex SHA-256 of the exact body bytes; empty body → e3b0c442…b855}
```
The signature is ECDSA P-256/SHA-256 over the UTF-8 bytes, made with the device's `request` key.

The server verifies the following and rejects the request otherwise:
1. The nonce is well-formed.
2. `|now − timestamp| ≤ 300 s`.
3. The signature verifies against the registered, non-revoked device key.
4. The nonce is fresh in `ReplayGuard` scope `req:{deviceId}` (TTL 600 s).
5. For `deviceSignedBearer`, the device belongs to the bearer's consumer.

`POST /v1/auth/refresh` has no bearer: the refresh token is the credential, and when its session is bound to a device the same headers and signature are required over that exact request (§2.8).

### 2.4 Signed decisions (`VIADERE-DECISION-V1`)
`DecisionPayload` canonical JSON members (optionals omitted):
`assurance` (`none|devicePasscode|biometric`), `businessId`, `challenge`, `contextDigest`? (v2 only), `decision` (`approve|deny|confirm|decline|select|reply|acknowledge|report`), `deviceId`, `interactionId`, `reply`?, `selectedOptionIds`?, `signedAt`, `v` (`1` without `contextDigest`, `2` with it; the version is implied by the digest, and the two must agree).

**Context digest (v2).** `contextDigest` = lowercase hex of `SHA-256("VIADERE-CONTEXT-V1\n" ‖ canonicalJSON)` where `canonicalJSON` is the canonical JSON (§2.2) of `{"businessId", "expiresAt", "kind", "payload", "schemaVersion"}`: `schemaVersion` is the interaction's integer version (the server bumps it whenever payload fields are added, so old clients refuse instead of mismatching; `Interaction` decodes a newer version leniently, keeps it, and clients refuse to approve it while deny/report still work; the server validates strictly on issue); `payload` is the interaction payload exactly as on the wire (absent optionals omitted; a non-integer number becomes the string `"n:<shortest decimal>"`), `expiresAt` ISO-8601 UTC with milliseconds, `kind` the kind's raw value. It also covers `schemaVersion`: **the server bumps `Interaction.currentSchemaVersion` whenever a payload field is added or changes meaning**, so a client that cannot display a new field sees a newer version and refuses to approve (`Interaction` decodes leniently and keeps the version; deny and report still work) instead of signing a digest the server will not recompute. It excludes everything the person never sees or that differs between app and business views (challenge, consumer reference, priority, channels, idempotency key). `Interaction.displayContextDigest()` in ViadereCore is the single definition: the app computes it over the interaction **as it displayed it**, the server recomputes it from the stored interaction. **v2 is required** for `approve`, `confirm`, `select` and `reply` on `authenticate`, `authorize`, `confirm` and `choose` (`400 context_digest_required` otherwise); v1 is still accepted for everything else (deny, report, decline, acknowledge, …). A digest that does not equal the stored interaction's is `409 context_mismatch`.

- Signed bytes: `"VIADERE-DECISION-V1\n"` followed by the canonical JSON.
- Key used: the device key with purpose `DeviceKeyPurpose.required(for: assurance)`:
  - `none` → `request`
  - `devicePasscode` → `approvalUserPresence`
  - `biometric` → `approvalBiometric`
- Wire format: `{"payload":"<base64url canonical JSON>","signature":"<base64url raw r‖s>"}`, sent in `DecideInteractionRequest.signedDecision`.

The server re-encodes the decoded payload and rejects it unless the bytes are identical. Then it checks all of the following:
- The interaction id, business id and device id match.
- The challenge matches, compared in constant time.
- The interaction has not expired.
- `signedAt` is no more than 60 s in the future and no more than 300 s old.
- The decision is allowed for the kind.
- `AssurancePolicy.canSatisfy`.
- The context digest is present where required and equals the stored interaction's (above).
- The signing device is an `app` device (App Clip devices can never decide), is not inside its new-device cool-down for a `high`/`critical` approval (deny, report and decline always work), and the interaction is a live (not test) one.
- `choose` selections are valid.
- The challenge is consumed once (`decision:{interactionId}`).

**What a business receives.** The business API and the `interaction.decided` webhook carry `deviceRef` = first 32 hex of `HMAC-SHA256(serverPepper, "device-ref\n" ‖ businessId ‖ "\n" ‖ deviceId)` (stable per business, unlinkable across businesses) and `verification {verified, keyPurpose, contextBound, verifiedAt, evidenceRef}` where `evidenceRef` = first 32 hex of `HMAC-SHA256(serverPepper, "decision-evidence\n" ‖ decisionId)`. The raw `signedDecision` is never sent to a business; the consumer's own `POST …/decision` response still returns it. For a dispute Viadere runs `ViadereServer export-dispute --interaction <id>` (audited `dispute.exported`), which prints the signed payload, signature, global device id and the device's public keys.

### 2.5 Device enrollment
Each key in `DeviceEnrollRequest.keys` carries `proof` = base64url(raw r‖s), signed by that key over:
```
VIADERE-ENROLL-V1\n{consumerId}\n{challenge}\n{purpose}\n{base64url X9.63 public key}
```
`challenge` comes from `POST /v1/devices/enroll/begin`. It is single-use, short-lived (5 min), and good only for the session (token family) that asked for it.

**Passkey-bound enrollment.** A bearer token alone never creates a device.
1. `POST /v1/devices/enroll/begin` (bearer) returns `{challenge, expiresAt, assertion, assertionOptional}`. `assertion` is `PasskeyAssertionOptions` whose `challenge` **equals** `challenge` (the same base64url string; the authenticator signs its bytes), `userVerification: "required"`, `allowCredentialIds` = the account's passkeys, `ceremonyId` = the enrollment challenge row.
2. The app performs the assertion and sends `POST /v1/devices` (bearer) with `{name, platform, challenge, keys, assertion, clientKind?, clipDevice?, appAttest?}`. The server verifies the assertion with WebAuthn (user verification required, RP id, origin, sign count) over `challenge`, with a credential owned by the calling consumer, then consumes the challenge.
3. **Exception.** `assertionOptional == true` when the session was minted by `register/finish` or `login/finish` less than 5 minutes ago, is not revoked and has not enrolled yet; then `assertion` may be omitted, **once**: enrolling binds the session to the device with a compare-and-swap on `device_id IS NULL`. Otherwise a missing or invalid assertion is `401 passkey_assertion_required`.
4. A re-enrollment (for example "Set up again" after the biometric key was invalidated) is an ordinary enrollment: it needs the assertion.
5. The challenge is consumed only after every other check (key proofs, the passkey assertion, the attestation policy) has passed.

**Session ↔ device binding.** Enrolling records the device on the token family. `deviceSignedBearer` requires the signing device to be the family's device (`403` otherwise); a family not yet bound binds to the first device that signs with it. Revoking a device revokes the families bound to it (`401 signature_invalid "This device has been revoked."` is still what a revoked device is told, so the app wipes its keys); revoking a family revokes the devices enrolled through it (user-revoked session), none (logout), or those enrolled after the reused token was issued (reuse).

**`clientKind`** (`app` default, or `appClip`; the app may instead send `clipDevice: true`). An `appClip` device registers a **request key only** (`422` otherwise), expires 7 days after enrollment (its session is capped to the same instant; the retention sweep revokes it), appears in `GET /v1/devices` with `clipDevice: true`, and the server refuses every decision from it.

**App Attest.** `appAttest {keyId, attestation}` carries Apple's attestation (`DCAppAttestService.attestKey(_:clientDataHash:)`). The app makes it over

```
clientData     = "VIADERE-APPATTEST-ENROLL-V1\n{consumerId}\n{challenge}\n{keyListDigest}"          (UTF-8)
keyListDigest  = lowercase hex SHA-256 of the lines "{purpose}:{base64url X9.63 public key}" sorted, joined with "\n"
clientDataHash = SHA-256(clientData)                                                                (passed to attestKey)
```

so the attestation names this enrollment challenge, this account and the exact set of keys, and cannot vouch for other keys or another enrollment (`AppAttestBinding` in ViadereCore is the reference). `keyId` is the identifier `generateKey` returned (base64, standard or URL alphabet); `attestation` is the CBOR object (base64url or base64). The server (`AppAttestVerifier`, Apple's documented procedure) accepts it only if all hold:
1. CBOR `fmt == "apple-appattest"`; `attStmt.x5c` = `[credCert, intermediate…]` (2 to 4 certificates) validates under RFC 5280 at the current time (a credential certificate issued up to 5 minutes "in the future" is tolerated) to **Apple's App Attestation Root CA**, the only trust anchor (embedded; source <https://www.apple.com/certificateauthority/Apple_App_Attestation_Root_CA.pem>, ECDSA P-384, valid 2020-03-18 to 2045-03-15, **SHA-256 fingerprint of the DER `1C:B9:82:3B:A2:8B:A6:AD:2D:33:A0:06:94:1D:E2:AE:4F:51:3E:F1:D4:E8:31:B9:F7:E0:FA:7B:62:42:C9:32`**, verified at startup; no configuration can replace it, tests inject a synthetic root through the `Overrides.integrity` seam);
2. `nonce = SHA-256(authData ‖ clientDataHash)` equals the credential certificate's extension `1.2.840.113635.100.8.2` (`SEQUENCE { [1] { OCTET STRING nonce } }`);
3. `SHA-256(credCert public key, X9.63)` equals `keyId`;
4. `authData`: `rpIdHash = SHA-256("{teamID}.{bundleID}")` (the Clip has its own bundle id), `counter == 0`, `aaguid` is `appattestdevelop` (development) or `appattest` + 7 zero bytes (production) for `APP_ATTEST_ENVIRONMENT`, and the credential id (32 bytes) equals `keyId`.
The receipt is ignored. Only on success are the device's keys stored `attested = true` (`DeviceKey.attested`, `devices.attestation_status = attested`) and the attested key id (hex), public key, environment and counter (0) stored in `app_attest_keys`; one App Attest key can back **one device** (unique key id; a reused key makes the new device unattested, `key_reused`). A failed or missing attestation is `unattested`/`rejected` and the reason (`not_provided`, `malformed_object`, `bad_format`, `bad_chain`, `bad_nonce`, `bad_key_id`, `bad_rp_id`, `bad_counter`, `bad_aaguid`, `bad_credential_id`, `key_reused`) is in the audit event.

**Policy (`APP_ATTEST_MODE`).** `require` (default in `production` and `staging`): an `app` **or** `appClip` enrollment without a valid attestation is `403 attestation_required` (audit `device.enroll_failed`, nothing created). `report`: it is accepted, flagged (`flagged: unattested` in the `device.enrolled` audit event, `attestation_status` `unattested`/`rejected`) and gets a **72 h** cool-down instead of 24 h (a brand-new account's first device still has none). `off` (the default elsewhere): attestations are verified and recorded when sent, never required.

**Assertions.** `AppAttestAssertions.verify` checks an assertion `{signature, authenticatorData}` (CBOR) made with a device's attested key over `clientData`: `authenticatorData` is `rpIdHash(32) ‖ flags(1) ‖ counter(4, big-endian)`; `rpIdHash` must match the app id, the ECDSA signature (DER) must verify over `SHA-256(authenticatorData ‖ SHA-256(clientData))` with the stored key, and the counter must be **strictly greater** than the stored one; the new counter is stored with a compare-and-swap on the old one, so a replayed or reordered assertion is refused (`401 signature_invalid`, audit `device.assertion_failed`). No route requires an assertion yet.

**Cool-down.** An `app` device enrolled by an account that has **ever** had an `app` device (active, revoked or expired, at any time: there is no lookback limit, so a lapsed account is not "new" again) gets `approvalsLockedUntil = now + 24 h` (72 h if it is unattested under `APP_ATTEST_MODE=report`); it is lifted by time or by a biometric confirmation from a trusted device (§2.17). Only a brand-new account's first device is exempt (nobody could confirm it). It applies whatever keys the device registers. Every enrollment (an App Clip too) creates an in-app notice (`GET /v1/security-notices`, dismissed with `POST /v1/security-notices/{id}/dismiss` from a trusted device; not shown to the device that caused it) and a push to the account's other app devices.

**Trusted device** (`DeviceTrust.isTrusted`): an `app` device that is not revoked, not expired and not cooling down. Required for: household invitation create and accept, phone-link OTP start and verify, revoking a device other than the caller's own, revoking a session other than the current one, account deletion, dismissing notices and the confirm endpoints. Others get `403 device_cool_down` (cooling) or `403`.

**Set up again.** `DeviceEnrollRequest.replacesDeviceId` names the device being replaced: this session's own device (the one the session is bound to, or enrolled through it) or a device of the account revoked in the last 30 days; anything else is `403`. It requires the passkey assertion (the fresh-session shortcut is refused), the new device still gets the cool-down above, and a device may have only one replacement pending (`409`).
* **Old device already revoked** (the normal biometric-change case): replaced at once. The new device is created and the caller's session is bound to it (`device.replaced`, `mode: immediate`).
* **Old device still live:** it is **not** revoked. It is marked pending (`devices.pending_replacement_by`; `Device.pendingReplacementBy` / `pendingReplacementAt` in `GET /v1/devices`) and keeps working with its sessions. The caller's session stays bound to it; the new device gets its **own** new session, already bound to it, in `Device.replacementSession` of the `POST /v1/devices` response (it is not tied to the caller's token family, so cancelling it never ends the old session). The account's other devices, the old one included, get an in-app notice (wire `kind` `devicePendingReplacement`, `action: cancelDeviceReplacement`, `subjectId` = the NEW device; ViadereCore exposes it as `SecurityNotice.topic`, while the older `SecurityNoticeKind` decodes it as `.unknown`) and a push (category `viadere.security.cancel`). The old device is revoked (with its sessions, `device.replaced`, `mode: pending_completed`) when the new device is **confirmed** (§2.17; completes immediately) or its **cool-down ends** (completed by the next request of the old device or by the background job). `POST /v1/devices/{newDeviceId}/cancel-replacement` (a trusted device other than the new one, normally the old device) revokes the **new** device and its sessions, clears the marker and leaves the old device untouched (`device.replacement_cancelled`); if the new device disappears some other way the replacement is abandoned and the old device stays.

### 2.6 Webhooks (Viadere → business)
```
Viadere-Signature: t={unix seconds},v1={hex HMAC-SHA256(key = UTF-8(secret), message = "{t}." + raw body)}
Viadere-Event-Id: {delivery id}
Viadere-Event-Type: {type}
```
- Secrets are `whsec_` + base64url(32 bytes).
- During rotation the header carries several `v1=` entries, and a match on any of them is accepted.
- Unknown schemes such as `v0=` are ignored.
- Receivers reject the event when `|now − t| > 300 s`, and must compare in constant time.
- Body: `WebhookEvent` (`id`, `type`, `createdAt`, `businessId`, `apiVersion`, `data`).

### 2.7 Connect links
- Form: `https://viadere.com/c/{CANONICAL_CODE}[?ctx={base64url canonical JSON}&sig={base64url HMAC}]`.
- `ctx` keys: `iat` (required), `cmp`, `act`, `exp` (all strings, dates in ISO form).
- Signature: `sig = HMAC-SHA256(serverKey, "VIADERE-CTX-V1\n{CODE}\n{ctx}")` (43 chars).
- `ctx` and `sig` must both be present or both absent.
- `ctx` is at most 512 chars, and no other query parameters are allowed.
- An expired or invalid context is ignored. The plain code still resolves.

### 2.8 Tokens
- `SecureToken.generate()` returns base64url(32 CSPRNG bytes), 43 chars.
- Stored value: `SecureToken.hash` = lowercase hex SHA-256 of the token's UTF-8 bytes.
- Comparison: constant time (`SecureToken.matches`).
- Account-link URL: `https://viadere.com/l/{token}`, 15 min, single use, bound to phone + conversation revision. The app (never the web page) handles it with two **device-signed** calls: `GET /v1/sms/link-tokens/{token}/preview` → `{maskedPhone, expiresAt}` (rate-limited; does not consume; the app shows the whole masked number with "This is my phone" and a warning) and `POST /v1/sms/link-tokens/redeem` with `{token, confirmPhoneLast4, confirmMaskedPhone?}`. Redeem checks the confirmation (a few wrong tries burn the token), that the live SMS thread still exists, has not been reset (`revision ≥` the token's) and has not opted out, consumes the token, links the phone, and notifies the account's other devices.
- **Linked-phone cool-down.** A phone linked from a token (or from an OTP started on a device that is itself cooling down) has `usableFrom`; before it (24 h, or 72 h when the account has no other trusted device; never earlier than the redeeming device's own cool-down) the phone is not an interaction delivery target, cannot answer an RCS postback and is **not a routing identity on the SMS gateway** (`loadContext` leaves the thread unlinked, so no session, forwarding or recents), unless `POST /v1/phone-links/{id}/confirm` carries a `ConfirmationProof` (§2.17) from a trusted device. `PhoneLink.usableFrom == nil` means usable.
- Phone verification by SMS code (`phone-links/start`, `verify`) needs a trusted device and is limited to the allowed destination regions (`OTP_ALLOWED_COUNTRIES`, default US, CA), a platform-wide and a per-prefix budget (alert-level log + audit `phone_link.budget_exhausted`), and the integrity hook.
- Secure handoff URL: `https://viadere.com/h/{token}`, 10 min, single use.
- **Signed refresh.** A refresh token whose token family is **bound to a device** is honoured only with that device's `VIADERE-SIG-V1` headers (§2.3) over `POST /v1/auth/refresh` and its exact body (no bearer header): the signing device must be the bound one, not revoked, with a fresh timestamp and a nonce not used before (`401 signature_invalid` for a missing, wrong-device or bad signature, `401 clock_skew`, `401 replay_detected`; audit `auth.refresh_unsigned`). The check runs **before** any state changes, so a copied token can neither mint a session nor obtain the 60 s grace pair, nor trip reuse detection against the owner. Families that have not bound a device yet (a fresh passkey sign-in, a legacy session) refresh without headers until they bind.
- **Session tokens.** Refresh tokens rotate on every use. A token presented again within 60 s of its rotation returns the same new pair (idempotent; the pair is stored AES-GCM-sealed on the old token's row and wiped after the window). Later it is reuse: the family is revoked and so are the devices enrolled through it after that token was issued. Expired tokens are simply invalid. `POST /v1/auth/logout` is device-signed and ends the current session only; it never revokes a device. A session from before token families existed gets its record on first use and is bound to the device of its first device-signed request.

### 2.9 Business codes and handles
- **Codes:**
  - Normalization: trim ASCII whitespace, strip `space - . _ / tab`, uppercase, map `I→1` and `O→0`, then require exactly 6 of `[0-9A-Z]`. `L` stays distinct.
  - Display form: `AF-2345`.
  - Issuance alphabet: `0-9` plus `A-Z` without `I`, `L`, `O`, generated with a CSPRNG. The server retries on collision of `canonical`.
- **Handles:**
  - ASCII only, lowercase, `[a-z0-9_]{3,30}`, starting with a letter, no trailing `_` and no `__`.
  - Registration additionally rejects reserved words, anything containing `viadere`, and confusables of reserved words. The skeleton maps `0→o`, `1/i/|→l`, `5→s`, `3→e`, `8→b`, `rn→m`, `vv→w`, `cl→d` and drops `_`.

### 2.10 SMS keywords
Matching is on the whole message after trimming, removing trailing `.`/`!`, and uppercasing:

| Keywords | Behavior |
|---|---|
| `STOP STOPALL UNSUBSCRIBE CANCEL END QUIT OPTOUT REVOKE` | Opt out in every state. Cannot be escaped (`\STOP` still opts out). |
| `HELP INFO` | Help text in every state, including OPTED_OUT (no re-subscribe). Cannot be escaped. |
| `START UNSTOP YES` | Opt back in, only from `OPTED_OUT`. Otherwise ordinary content. |
| `MENU`, `BACK` | Gateway controls. Send `\MENU` or `\BACK` to pass the word to the connected business. |

**Business text in SMS/RCS.** Business-originated text (`message` payloads and business replies) is rendered after `[Business Name]: ` as **one line**: LF, CR, NEL, U+2028/2029, VT, FF and tab become spaces, spoofing and control characters are removed, whitespace is collapsed, a leading `[` becomes `(` and a leading "Viadere" (after width/case/homoglyph/punctuation normalisation) gets a `- ` prefix (`SMSEncoding.businessLine`). **Menu race.** A digit received less than `SMS_MENU_RACE_SECONDS` (default 3) after a menu was shown is not acted on; the menu is shown again (`gateway.menu_race`). **Carrier opt-out** (provider error 21610) is written through the revision-checked thread context as well as the `opted_out` column.
**Shared thread.** If the thread is `CONNECTED`/`SESSION_MENU` to business B, an interaction SMS from business A is not sent; a content-free notice naming A and B (`GatewayCopy.newMessageNotice`) is sent instead.

### 2.11 RCS provider webhooks and postback tokens

Inbound (provider → Viadere), `POST /v1/providers/rcs/inbound`:
```
X-RCS-Signature: t={unix seconds},v1={hex HMAC-SHA256(key = UTF-8(secret), message = "{t}." + raw body)}
```
The secret is `RCS_WEBHOOK_SECRET` (base64url, ≥ 32 bytes; the HMAC key is the UTF-8 of its base64url text). Verification, tolerance (300 s) and constant-time
comparison are exactly §2.6. Unconfigured, unsigned, badly signed and stale deliveries are the same `403`. Events: free text, `suggestionResponse.postbackData`,
and `DELIVERED` / `READ` / `FAILED` receipts. Provider message ids are de-duplicated.

Postback token (Viadere → provider → Viadere), carried as `postbackData`:
```
vrp1.{base64url(32 CSPRNG bytes)}.{first 32 hex of HMAC-SHA256(serverPepper, "rcs-postback\n" + random part)}
```
* Opaque: it contains no interaction id, option id or decision; the server keeps `(interaction, target, phone, menu version, expiry)` keyed by the SHA-256 of the whole token.
* Structure and MAC are checked before any lookup; comparison is constant time.
* Single use: consuming it is a compare-and-swap in the same transaction that records the decision.
* Bound to the phone it was sent to, to the phone's **active menu version** (a newer menu supersedes older ones) and to the menu TTL.
* Authenticates nothing about the person: a reply on RCS is `ProvidedAssurance.unauthenticatedReply`.

### 2.12 Dashboard sessions and CSRF

* Session cookie: `__Host-vd_session` (operators `__Host-vd_operator`) = `vds_` + base64url(32 CSPRNG bytes); `Secure; HttpOnly; SameSite=Strict; Path=/`, no `Domain`. Stored: SHA-256 only.
* Created on every successful passkey assertion (a presented old session is revoked). Idle timeout 30 min / absolute 12 h (operators 15 min / 8 h). `reauthAt` is set at sign-in and by a re-authentication ceremony.
* CSRF token: first 43 hex characters of `HMAC-SHA256(serverPepper, "dashboard-csrf\n" + cookie value)`, sent as hidden field `_csrf` or header `X-CSRF-Token` on every non-`GET`; constant-time compare. A request with an `Origin` header must carry one of the configured origins.
* Passkey ceremonies use the dashboard's own credential table and a single-use ceremony row (5 min); registration and assertion require user verification.

### 2.13 Reward eligibility and redemption codes
* **Eligibility** is returned as `RewardEligibility {state, nextAction, checkedAt, nextEligibleAt?, pointsShortfall?}` and computed only by the server. Evaluation order: `revoked` → `redeemed` (single-use reward already consumed) → `expired` (`now ≥ validUntil`) → `notYetValid` → `notToday` (ISO weekday in the reward's IANA zone) → `limitReached` → `insufficientPoints` → `eligible` (`nextAction` is `claim` for coupons and offers not yet claimed, otherwise `redeem`). Day boundaries use the zone's calendar, so DST days of 23 or 25 hours are single days.
* **Limits:** recurring rewards allow `perDayLimit` redemptions per local day per consumer; coupons, offers and perks without recurrence allow one per consumer; points rewards are limited by balance only.
* **Redemption code:** `XXXXX-XXXXX` over `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (50 random bits). Input is normalised by upper-casing, removing spaces and dashes and mapping `I`,`L`→`1`, `O`→`0`. Stored as `HMAC-SHA256(serverPepper, "reward-redemption\n" + normalizedCode)`; valid 120 s (`RewardRedemption.validForSeconds`, `serverTime`, `expiresAt`).
* **Reservation:** issuing a code takes a slot in unique `(rewardId, consumerId, windowKey, slot)` (`windowKey` is the local `YYYY-MM-DD`, `once` or `open`) and debits points by compare-and-swap. Expiry (`issued → expired`) clears the slot and returns the points.
* **Consumption:** `POST /v1/business/redemptions/consume` flips `issued → consumed` with one compare-and-swap, scoped to the calling business. Results: `200` receipt, `404` unknown/malformed/other business, `409` already used, `410` expired or reward withdrawn, `429` rate limit.

### 2.14 Wallet passes (`.pkpass`)
* Content type `application/vnd.apple.pkpass`, a ZIP of `pass.json`, `icon.png`/`@2x`/`@3x`, `manifest.json` and `signature` (stored entries, flat names, fixed timestamps, < 5 MB).
* `manifest.json`: JSON object mapping each file name (all except `manifest.json` and `signature`) to its lowercase hex **SHA-1**, keys sorted.
* `signature`: DER **PKCS#7 / CMS `SignedData`**, detached (no `eContent`), digest SHA-256, `signedAttrs` = content type, signing time, message digest of `manifest.json`; the certificate set holds the Pass Type ID certificate and the WWDR intermediate. Equivalent to `openssl smime -binary -sign -signer pass.pem -inkey key.pem -certfile wwdr.pem -in manifest.json -outform DER`.
* `pass.json`: `formatVersion` 1; `passTypeIdentifier`, `serialNumber` (`VP-…`), `teamIdentifier` equal the issued `WalletPassMetadata`; `webServiceURL` = `{PUBLIC_BASE_URL}/wallet`; `authenticationToken` (43 base64url chars); `voided: true` once voided. Style key by kind: `storeCard`, `coupon`, `eventTicket`, `boardingPass`, `generic`.
* **Authentication token:** `base64url(HMAC-SHA256(serverPepper, "wallet-auth-v1\n" + passId + "\n" + salt))`; the database keeps the per-pass random `salt` and `HMAC(pepper, "wallet-auth-hash\n" + token)`. Wallet echoes it as `Authorization: ApplePass {token}`.
* **PassKit web service** under `/wallet/v1` (Apple's protocol): `POST|DELETE /devices/{device}/registrations/{passType}/{serial}` (token; body `{"pushToken"}`; `201` new, `200` repeat), `GET /devices/{device}/registrations/{passType}?passesUpdatedSince={tag}` (`200 {"serialNumbers","lastUpdated"}` or `204`), `GET /passes/{passType}/{serial}` (token; `If-Modified-Since` → `304`), `POST /log` (bounded: 20 messages × 500 characters, redacted, rate-limited). The update push is APNs with the Pass Type ID certificate (TLS client authentication), topic = pass type identifier, empty payload.

### 2.15 Household invitations and the delegation step-up
* **Invitation code:** `XXXX-XXXX` over the same alphabet (40 random bits), normalised like §2.13, stored as `HMAC-SHA256(serverPepper, "delegation-invite\n" + normalizedCode)`, single use (`open → accepted` compare-and-swap), valid 24 h. A lookup reserves a token from a per-consumer budget (10/hour, burst 5) and a global one (120/min) and **gives it back when the lookup succeeds**, so only failed lookups spend the budgets that bound guessing (an empty budget refuses even a valid code); previews also have a per-consumer limit of 30/hour (burst 15); each invitation locks after 10 lookups. When an interaction is issued, a push goes to the grantor's devices and to the devices of each delegate whose active grant covers the interaction's purpose and business (the grantor's generic payload: opaque `iid` only; nothing else is sent to delegates).
* **Scope text:** `DelegationScopePolicy.canonicalScope(of:)` = lines `role=…`, `purposes=` (sorted raw values, comma-joined), `businesses=` (sorted lowercase UUIDs, comma-joined), `expires=` (ISO-8601 ms UTC), `label=…`, joined with `\n`. `scopeDigest` = lowercase hex SHA-256 of its UTF-8.
* **Step-up proof** `{deviceId, signedAt, scopeDigest, signature}`: `signature` = base64url raw `r‖s` ECDSA P-256/SHA-256 by the device's **`approvalBiometric`** key over the UTF-8 of `"VIADERE-DELEGATION-STEPUP-V1\n" + deviceId + "\n" + signedAt + "\n" + scopeDigest` (`signedAt` ISO-8601 ms UTC). Required whenever the purposes include `security` or `accountService`. The server verifies: the proof's device is the calling device; the digest equals the digest of the request it rebuilds; `signedAt` is ≤ 60 s in the future and ≤ 300 s old; the signature verifies against that device's `approvalBiometric` key (a passcode or request key fails); and the proof has not been used before (`ReplayGuard` scope `delegation-stepup:{deviceId}`, key `sha256(deviceId|signedAt|scopeDigest)`: the signed content, not the signature string, because `(r, n − s)` is a second valid encoding). Errors: `403 insufficient_assurance` (missing, or no biometric key), `403` (device/scope mismatch), `400` (malformed), `401 signature_invalid`, `401 clock_skew`, `410 expired` (too old), `409 replay_detected`.
* **Limits:** sensitive grants last at most 30 days (others at most one year, at least one hour); only businesses the grantor is connected to; marketing and rewards purposes cannot be delegated.
* **Decisions:** a delegate's decision is accepted only through an active grant covering the interaction's purpose and business, from a `manager`, for `confirm`→`confirm|decline` and `choose`→`select|decline`. Everything else is `403` and audited as `delegation.denied`; an interaction outside every grant is `404`.
* **Audit actions** (subject type `delegation`): `delegation.created`, `.accepted`, `.revoked`, `.expired`, `.used`, `.denied`, `.stepup_rejected`.

### 2.16 Live Activity pushes
`apns-push-type: liveactivity`, topic `{bundleId}.push-type.liveactivity`. `event` is `start` (to a push-to-start token, with `attributes-type: ViadereActivityAttributes`, `attributes` `{businessName, businessId, interactionId}` and a neutral alert), `update` or `end` (terminal states) to the per-activity token registered for the same business and activity chain. `content-state` is `LiveActivityStatus` encoded with the default (non-ISO) `JSONEncoder` that ActivityKit's decoder expects. Sent only for `transactional`, `accountService` and `support` statuses of live (not test) keys.

### 2.17 Confirmation proofs (new device, new phone)
`ConfirmationProof {subject, subjectId, deviceId, signedAt, assurance, signature}` is made by a **trusted** device (`DeviceTrust.isTrusted`: an `app` device that is not revoked, expired, nor itself cooling down) with its **biometric** key: `assurance` must be `"biometric"` and the signature is made with the `approvalBiometric` key; a device passcode (`devicePasscode`) or a request key (`none`) never confirms (`403 insufficient_assurance`). `signature` = ECDSA P-256/SHA-256 (raw r‖s, base64url, low-S) over the UTF-8 of
```
VIADERE-CONFIRM-V1\n{subject: device|phoneLink}\n{subjectId lowercase uuid}\n{deviceId}\n{signedAt ISO-8601 ms UTC}\n{assurance}
```
The server checks: the proof's device is the calling device; subject and id match the route; `signedAt` ≤ 60 s in the future and ≤ 300 s old; the signature verifies; the proof is single use (`ReplayGuard` scope `confirm:{deviceId}`, key `sha256(signing input)`). Routes: `POST /v1/devices/{deviceId}/confirm` (lifts the cool-down of another device of the same account; the confirming device must differ from the target) and `POST /v1/phone-links/{phoneLinkId}/confirm`. Errors: `403` (not a trusted device / not yours / assurance too low), `401 signature_invalid`, `401 replay_detected`. Both are audited (`device.confirmed`, `phone_link.confirmed`).

### 2.18 Sandbox (test mode)
`POST /v1/business/sandbox/relationships` (test key, scope `interactions:write`, ≤ 50 per business) creates a consumer with status `sandbox` and an active relationship. `issue`, `statuses` and `messages` with a test key require a sandbox relationship (`403` for a real one); with a live key a sandbox relationship is `404`. Sandbox consumers cannot sign in; test interactions are `livemode = false`, are never pushed, texted or decided, are metered as test usage, and every consumer query filters `livemode = true`.

### 2.19 Business display text
`InteractionValidation` rejects (`422 validation_failed`, issue codes `disallowedCharacters`, `tooLong`, `impersonation`) business strings that: contain any Unicode control, format, line/paragraph separator, private-use or unassigned scalar (this covers U+202A–202E, U+2066–2069, U+200E/F, U+061C, U+180E, U+200B–200D, U+2060, U+FEFF, U+00AD, U+2028/2029, U+0085, tag characters) or a known invisible filler (U+034F, U+115F/1160, U+17B4/5, U+180B–D, U+2800, U+3164, U+FFA0, variation selectors other than FE0E/FE0F); contain a line feed (allowed only in free-text fields of ≥ 1000 characters; CR and tab never); exceed the field's grapheme limit, `2×` that many unicode scalars, or `4×` that many UTF-8 bytes; or, after NFKD, lower-casing, combining-mark removal, homoglyph mapping and the handle confusable skeleton, start with "viadere" (every field) or contain it (name fields: service, merchant, titles, labels, action description, holder, venue). `DisplayTextSanitizer` (ViadereCore) is the shared definition; clients additionally `sanitize` before display.

### 2.20 Account deletion and retention
`DELETE /v1/account` revokes every session and device, blanks device names, deletes passkeys, and erases: phone numbers (`phone_links`, queued/sent `sms_outbound`, `channel_outbound`, `link_tokens`, found by phone hash before the hash is replaced), SMS thread state (an opted-out number keeps a fresh thread holding only the suppression), message bodies, interaction payloads and the `reply`/selection in stored outcomes, delegation labels, loyalty member references, and webhook delivery bodies for message/decision events that mention the consumer. `decisions` is append-only with exactly one permitted edit: `signed_payload` may be replaced by `[erased]` (database trigger `decisions_guard`). Deletion applies it **only to decisions whose payload contains a free-text `reply`**; decisions without one (ids, challenge, context digest, timestamps: no personal data) are kept whole so they stay verifiable and `export-dispute` keeps working. Retention basis: legitimate interest of Viadere and the businesses in proving what a device signed (non-repudiation) for the dispute period; a longer or shorter period is a deployment policy decision. Signature, decision, assurance, channel and ids always remain. Retention (background sweep): finished `sms_outbound`/`channel_outbound` rows 30 days (`OUTBOUND_RETENTION_DAYS`), link tokens 7 days after expiry (`LINK_TOKEN_RETENTION_DAYS`), succeeded/dead webhook deliveries and their attempts 30 days (`WEBHOOK_RETENTION_DAYS`), devices past their `expiresAt` are revoked.

### 2.21 Field encryption
Wire form `v2.` ‖ base64url(nonce ‖ ciphertext ‖ tag), AES-256-GCM, additional data = UTF-8 of `"{table.column}#{rowId lowercase uuid}"`. The legacy `v1.` form (additional data = the column only) is still read; `ViadereServer reencrypt-fields` rewrites it (idempotent) encrypts webhook delivery bodies written in plaintext and strips `data.signedDecision` from queued `interaction.decided` bodies (also stripped on read before sending). A grant's label shares the id of the invitation it came from, so its ciphertext is valid on both rows.

### 2.22 Audit chain
Event hash version 2 = lowercase hex `HMAC-SHA256(AUDIT_CHAIN_KEY, canonicalJSON({seq, at, actorKind, actorId?, action, outcome, consumerId?, businessId?, subjectType?, subjectId?, correlationId?, meta, prev, v: 2, id}))`; version 1 (legacy) is the unkeyed SHA-256 of the same object without `v`/`id`. `audit_events.chain_version` records which. Verification (`ViadereServer audit-verify [--head file]`) accepts version 1 only for `seq ≤ AUDIT_CHAIN_LEGACY_THROUGH_SEQ` (default 0) and never after a version 2 event. **Head export:** `ViadereServer audit-head` prints `{seq, hash, occurredAt, exportedAt, mac}` with `mac = HMAC(AUDIT_CHAIN_KEY, "VIADERE-AUDIT-HEAD-V1\n{seq}\n{hash}\n{occurredAt}\n{exportedAt}")`; store it hourly or daily in write-once (object-lock) storage. `audit-verify --head` checks that the event at `seq` still has that hash.

### 2.23 Rate limiting
Token buckets keyed by `name|key` (the namespace is the part before the first `|`). Client IPs are normalised by `ClientIP.normalize`: IPv6 → its `/64` (`2001:db8:1:2::/64`), IPv4-mapped IPv6 → IPv4; `X-Forwarded-For` is honoured only for `TRUSTED_PROXY_COUNT` hops.

**Stores** (`RATE_LIMIT_STORE`, default `database` in staging/production, `memory` otherwise):
* `database` (`DatabaseRateLimitStore`): table `rate_limit_buckets(key PK, namespace, tokens, updated_at, expires_at, last_allowed)`. One check is **one atomic statement**, `INSERT … ON CONFLICT (key) DO UPDATE SET tokens = <refill, then take>, last_allowed = <enough?> … RETURNING tokens, last_allowed`, portable `CASE` arithmetic over epoch seconds, identical on PostgreSQL and SQLite; the limit is therefore global across instances. The rule (capacity, refill) travels with each call. Rows whose bucket has fully refilled expire (`expires_at`) and are deleted by the job loop (at most once a minute). A negative cost returns tokens (never beyond capacity); the household budgets use it to refund successful lookups.
* If the database is unavailable (error; retried no sooner than 5 s later), namespaces for one-time codes and link redemption (`phonelink*`, `link-*`, `phone-confirm`), enrollment and device confirmation, household invitations, dashboard authentication (`dashboard-*`), `auth-*`, redemption codes, rewards and wallet authentication **fail closed** (refused, `Retry-After` 30 s); every other namespace, the global `ip` limiter included, degrades to the in-memory limiter of that instance with the same rule.
* `memory` (`InMemoryRateLimitStore`): per instance, **one capped table per namespace** (default 50 000 buckets, `ip` 200 000, `dashboard-signup-email` 10 000), so a flood of fresh keys in one namespace cannot exhaust another: in particular never the global per-IP limiter. A full table first sweeps fully-refilled buckets (at most once per second), then evicts its least recently used tenth; the global IP limiter therefore never fails closed. Evictions are counted (`evictions`) and logged as a warning; a namespace can opt into refusing new keys (`failClosedNamespaces`, counted as `refusedWhileFull`). Development and tests only: with several instances the effective limit is multiplied by the instance count.

`dashboard-signup-email` is keyed by IP and email; `dashboard-signup-address` by email only and `dashboard-signup-ip` by IP only, so one address cannot be mail-bombed from many IPs nor one IP spray many addresses.

### 2.24 Dashboard email verification
* **Sign-up:** passkey ceremony → `POST /dashboard/auth/signup/finish` creates a user with status `unverified` (passkey stored, **no session, no organization**) and emails a code; the sealed sign-up details live on the code row. `POST /dashboard/verify {email, code}` activates the user and creates the pending organization and application in one transaction; the user then signs in with the passkey. `POST /dashboard/verify/resend {email}` mails a new code.
* **Code:** 6 digits from the CSPRNG, stored as `HMAC-SHA256(serverPepper, "dashboard-email-code\n" + rowId + "|" + code)`, 15 minutes, single use, **5 attempts** (the attempt is reserved with an atomic `attempts = attempts + 1 … WHERE attempts < 5` *before* the comparison, so concurrent guesses cannot exceed it); a new code replaces the old one.
* **Non-enumeration:** unknown address, no pending sign-up, wrong, expired, locked and malformed input are one `422` with one message; resend answers the same page whether or not mail was sent; sign-up `begin` answers `200` for free, unverified and verified addresses alike. Limits are keyed by the submitted address and the IP, never by whether an account exists.
* **Daily guess cap:** at most **10** wrong or unanswered verification attempts per address per 24 h (a token bucket, `dashboard-verify-failures`, charged before the comparison and refunded on success); a new code does **not** reset it. Once spent the address answers `429` until it refills, so resending codes cannot be used to keep guessing.
* **Wipe protection:** sign-up `finish` for an address with an unverified sign-up whose newest code is **under 15 minutes old** answers as a success, creates nothing, sends nothing and wipes nothing, so an attacker cannot keep resetting a victim's in-progress sign-up. Such a request does not charge the address budgets (`dashboard-signup-email/address`; the per-IP budget still applies), and the owner's resend uses its own `dashboard-resend-address` bucket.
* **Purge race:** removing unverified users first *claims* them (`UPDATE … SET status = 'purging' WHERE status = 'unverified' RETURNING id`) and deletes children only for the claimed ids, in one transaction; an owner who verified in the meantime is skipped, and keeps their passkey.
* **Unverified accounts** cannot sign in, create an organization or accept an invitation (`DashboardActions.acceptInvite` also refuses them). After 24 h the job loop deletes them (with passkeys and codes). A later sign-up or an accepted invitation for the same address first deletes the unverified record, so the address is never held hostage.
* **Invitations:** the link (single-use token, `inviteTTL` 7 days) is emailed to the invited address and never shown to the inviter. A new person requests a code (`POST /dashboard/invite/{token}/code`, limited per invitation, per address and per IP) and sends it with `invite/begin`; accounts that already exist (verified) sign in and accept. If the email cannot be sent the invitation is withdrawn.
* **Email delivery:** `EmailSender` (`HTTPEmailSender`: `POST EMAIL_API_URL`, JSON `{from,to,subject,text}`, key in `EMAIL_API_AUTH_HEADER` (default `Authorization: Bearer`)). The development `LoggingEmailSender` prints the message; in staging and production it logs only the kind and the recipient's domain, never a code or link. Sign-up delivery failures are logged and not surfaced (the user resends).

### 2.25 Configuration
`ENVIRONMENT` (required): `development`, `test`, `staging`, `production`. `staging` and `production`: every secret mandatory and distinct (`CONNECT_LINK_SIGNING_KEY`, `SERVER_PEPPER`, `DATA_ENCRYPTION_KEY`, `AUDIT_CHAIN_KEY`), `DATABASE_URL`, https `PUBLIC_BASE_URL`, provider credentials, `seed` refused. Outside development `RP_ORIGIN` must be an https origin of `RP_ID`. With any `DATABASE_URL`, an unset secret is an error (ephemeral secrets only exist with the in-memory database). `APP_ATTEST_MODE` (`off`, `report`, `require`; default `require` in `production` and `staging`, `off` elsewhere; anything else refuses to boot) and `APP_ATTEST_ENVIRONMENT` (`development` or `production`, the AAGUID the app's builds attest with; default `production` in `production`, `development` elsewhere) configure App Attest (§2.5); the team id comes from `APPLE_TEAM_ID` (mandatory in staging and production) and the app ids are `com.viadere.app` and `com.viadere.app.Clip`.

### 2.26 Account recovery
**Codes.** At registration (`register/finish`, `AuthSession.recoveryCodes`) and on regeneration the server issues `RecoveryPolicy.codeCount` = **10** codes `XXXXX-XXXXX` (50 random bits each, Crockford alphabet `0-9 A-Z` without `I L O U`; input is upper-cased, spaces and dashes removed, `I`/`L` → `1`, `O` → `0`) and a **recovery ID** `XXXX-XXXX-XXXX` (60 bits) that names the account. They are shown **once** (`RecoveryCodeSet {recoveryId, codes, issuedAt}`); the server stores only `HMAC-SHA256(serverPepper, "recovery-code\n{consumerId}\n{normalizedCode}")` per code (`recovery_codes`, state `active` → `used` by compare-and-swap, or `invalidated`) and `HMAC-SHA256(serverPepper, "recovery-id\n{normalizedId}")` for the ID (`recovery_profiles`). A new set invalidates the old codes **and replaces the recovery ID**.

**Flow** (all public routes are rate-limited per IP, `recovery-begin` 20/h burst 8; `begin` adds a **per-recovery-ID** budget, 20/h burst 10 on the ID's hash, refunded on success, and a global guess budget, 300/h burst 60, charged only for well-formed requests that fail and **applied only to IDs that name no account**: a flood of made-up IDs from many addresses exhausts it for guessers (`429`) but never blocks a real ID, whose exposure is the per-ID budget, the per-IP budget and the 5-wrong-codes lock. Malformed input is rejected before any shared budget):
1. `POST /v1/recovery/begin {recoveryId, code}`: spends one code and opens the recovery in **one transaction**; the single open-recovery slot is a partial unique index on `account_recoveries(consumer_id) WHERE state IN ('awaiting_passkey','holding')` (migration `CreateRecoveryRound5Schema`), so concurrent begins with different codes yield one recovery and the losers burn no code (a recovery already awaiting a passkey or holding refuses) and returns `PasskeyRegistrationOptions` for a NEW passkey (`userId` = the account's WebAuthn user handle, so the authenticator replaces the old passkey; `ceremonyId` = the recovery id; valid 10 minutes). **Every** failure (unknown or malformed ID, wrong or used code, locked account, recovery in progress) is the same `401 unauthorized`. 5 wrong codes lock the account's recovery for 24 h (even for the right code); the account's devices get a notice (`recoveryAttemptsLocked`) and a push. Audited: `recovery.code_accepted`, `recovery.begin_failed`, `recovery.begin_denied`, `recovery.locked`.
2. `POST /v1/recovery/finish {ceremonyId, credential}` (`201`): verifies the new passkey registration (user verification required, the credential id unused), stores it **inactive** and starts the hold: `RecoveryStatus {id, state: holding, startedAt, activatesAt = now + 72 h, statusToken}`. The `statusToken` (256-bit; only its SHA-256 is stored) is returned once and stays with the recovering client. Every existing app device gets an in-app notice `recoveryStarted` (`action: cancelRecovery`, `subjectId` = the recovery id) and a push (category `viadere.security.cancel`) whatever its trust state. The notice is stored **in the same transaction** as the hold: if it cannot be stored the recovery does not start (the push is best effort). Audited `recovery.started`.
3. **During the 72 h** the new passkey cannot sign in; the old passkey, devices and sessions work as before. `POST /v1/recovery/{recoveryId}/cancel` (device-signed; **a trusted device** of the account) cancels (`state: cancelled`, idempotent) and also **invalidates every remaining code**, because whoever started it held at least one; the other devices get a `recoveryCancelled` notice. `GET /v1/recovery` (`RecoveryInfo`) shows the unused-code count, the earliest pending recovery (`pending`, kept for older clients) and **every** pending recovery (`pendingRecoveries`); Settings → Security → Recovery codes shows "Recovery in progress — Cancel" from it (one cancel per pending recovery), so the owner does not depend on the Home notice. Cancelling closes **all** of the account's open recoveries in its transaction, and so does regenerating the codes.
4. **Activation**, after the hold without cancellation (by the background sweep, or by the recovering client's `complete` call, whichever comes first; one compare-and-swap `holding → activated`): in one transaction every device is revoked (with their push tokens and sessions), every session of the account is revoked, all old passkeys are deleted, the new passkey becomes the account's passkey, the remaining codes are invalidated (`recovery.activated`). The same transaction **ends every household grant the account gave or received** (and cancels its open invitations), stores a `delegationEnded` notice for each counterpart and a `recoveryCompleted` notice for the account, and puts **every verified phone link back into cool-down** (`usableFrom` = activation + 72 h, `confirmedAt` cleared; a trusted device confirms it with Face ID as for any new link): possession of a code is not proof that the person is who the household and the phone numbers were trusted for.
5. `POST /v1/recovery/complete {recoveryId, statusToken}` (public, rate-limited; a wrong token is `401`) polls: `holding` while waiting; `activated` afterwards, and the **first** call after activation also returns the replacement `RecoveryCodeSet` (exactly once: a compare-and-swap on `codes_issued_at`; within 7 days of activation, after which the token stops working). The client then signs in with the new passkey (`login`) and enrolls a device as for any lapsed account: it cools down for 24 h (72 h unattested in `report`), must attest in `require` mode, and is not a trusted device until then.

**Regenerating codes.** `POST /v1/recovery/codes/begin` (device-signed, **trusted device**) returns `PasskeyAssertionOptions` over a fresh single-use challenge (5 min); `POST /v1/recovery/codes/regenerate {ceremonyId, assertion}` (`201`) verifies a **fresh user-verified passkey assertion** of the calling account's credential over it (`401 passkey_assertion_required` otherwise; a failed attempt consumes the challenge) and returns a new `RecoveryCodeSet`. This is also how an account that predates recovery codes gets its first set. Both calls are limited to 20/hour (burst 10) per account.

**What recovery does not give back.** Household grants (both directions) and phone-link trust are not inherited (see activation above): grants must be re-created by invitation, phone links work again after 72 h or on confirmation. A recovery that completes also ends everything that needs a device or the old passkey.

### 2.27 Business idempotency (webhook create, secret rotation, interaction cancel)
`POST /v1/business/webhooks`, `POST /v1/business/webhooks/{id}/rotate-secret` and `POST /v1/business/interactions/{id}/cancel` **require** an `Idempotency-Key` header (1-128 of `A-Za-z0-9_.-:`; missing or invalid is `422 validation_failed`). There is no body key to match, so the header alone identifies the operation. One row per `(business, operation, key)` (unique) records the SHA-256 of the operation and its request (`webhook.create` + the request body, `webhook.rotate` + the webhook id, `interaction.cancel` + the interaction id): the same key and request replays the original result (`200` instead of `201`), the same key with a different request is `409 idempotency_conflict`, and keys are per business. A cancel checks that the interaction belongs to the business (`404` otherwise) before a key is recorded. Create and rotate return a **one-time secret**: the response is kept AES-GCM-sealed (row-bound) for replay and wiped after 24 hours; a later replay is `410 gone` (rotate for a new secret). A concurrent duplicate loses on the unique key and replays the winner, so one subscription and one rotation exist whatever the retries.

### 2.29 Business entitlements and the policy decision (`PolicyService`)

**Risk tiers (spec §8.2).** A business holds a set of tiers M, A, V, E. Every verified business holds **Tier M and the three messaging capabilities only**, implicitly. Everything else is a row in `business_entitlements` created by an operator: `kind` tier or capability, `granted_by`, a purpose `justification` (at least 20 characters; the recorded purpose, AGE-007), `review_reference` (required for `identity.name` / `identity.address`: the heightened-review record), optional expiry. A capability can be granted only while its minimum tier is held, only to a verified business, and never by category: no code path reads the business category. Revocation stamps `revoked_at`, `revoked_by`, `revoke_justification` (rows are never deleted); revoking a tier revokes the capabilities that need it. Operator console: `/operator/businesses/{id}/entitlements` (grant, revoke, history). Every change needs a **fresh passkey assertion** (like suspend/approve), CSRF, a justification, and writes `entitlement.tier_granted`, `entitlement.capability_granted`, `entitlement.tier_revoked` or `entitlement.capability_revoked` with the operator as actor.

**Decision.** `PolicyEngine.evaluate` (pure, in Core) computes `entitlement ∩ key scope ∩ customer consent ∩ evidence sufficiency ∩ law/policy` from facts the server loads **fresh on every request** (so entitlements are a ceiling at use time):

1. unknown capability; business not verified;
2. **key scope** (`insufficient_scope`), **entitlement** (`not_entitled`), **tier** (`tier_required`), **environment** (the key's live/test equals the request's);
3. **operator switches** (`capability_disabled`; `policy_unavailable` for sensitivity high or critical when the table cannot be read);
4. **typed parameters** and `purpose` (`invalid_parameters`, `purpose_required`);
5. **law/policy rules** (`jurisdiction_blocked`): `jurisdiction_block` (listed regions) and `jurisdiction_allow_only` (an unknown jurisdiction is denied);
6. only if all the above passed: **consent** (`consent_required`) and **evidence** (`evidence_insufficient`). A credential that may not use the capability never causes the subject's data to be read. For `authenticate` / `authorize` interactions the evidence is a registered authenticator: a customer with no enrolled, unrevoked, unexpired device answers `403 policy_denied` (`details.reason = evidence_insufficient`) instead of creating an interaction nobody can decide (a sandbox consumer counts as having one).

The result is `allow` or `deny` with every failed check (`reasons`, first = the one returned), details, and a `PolicyAuditRecord`. The server persists it: **every denial** is audited (`policy.denied`, actor = the API key, metadata: capability, reason, reasons, environment, subject_ref, purpose, request_id; no personal data), and an allowed decision when the capability's definition says so (`policy.allowed`). HTTP mapping: `403 insufficient_scope`, `403 not_entitled` (also `tier_required`), `403 capability_disabled`, `503 unavailable` (`policy_unavailable`), `403 consent_required` (unchanged shape for interactions), `422 validation_failed` (parameters, purpose), `403 policy_denied` (jurisdiction, evidence, unknown capability) with `details.capability` and `details.reason`.

**Kill switches and rules (ops gap G-2).** `capability_switches` (one row per capability and scope: `global` or a business id) and `policy_rules` are edited only through the operator console (`/operator/policy`): fresh passkey, CSRF, reason required, audit events `policy.capability_disabled`, `policy.capability_enabled`, `policy.rule_added`, `policy.rule_removed`. The platform-wide state is cached in memory for 5 seconds (`PolicyService.cacheTTL`), invalidated at once on the instance that changed it; per-business switches are read on every request.

**Per-request disclosure receipts (spec §6.4).** `DisclosureReceipt` (Core) / `disclosure_receipts`: `subjectRef`, `businessId` (recipient), `capability`, `purpose`, `fields` (exactly the claim fields the capability discloses, never more), `requestId`, `grantedAt`, `expiresAt` (at most 10 minutes after `grantedAt`), `revokedAt`, `consumedAt`. Unique per (business, capability, request id). `DisclosureReceiptService.grant` is called by the app-facing verification flow after the person confirmed with local authentication; the relationship must be the consumer's own, active, with a verified business. `PolicyService.authorizeDisclosure` looks up **the calling business's own** receipt, evaluates the policy and only on allow spends it by compare-and-swap (`consumed_at`): concurrent requests, one receipt, one winner. Audit: `consent.disclosure_granted` (actor consumer), `consent.disclosure_revoked`, `policy.allowed` / `policy.denied` (with `receipt_id` / `receipt_problem`). Receipt problems: `missing`, `wrong_recipient`, `wrong_subject`, `wrong_capability`, `wrong_purpose`, `wrong_request`, `revoked`, `already_used`, `expired`, `fields_mismatch`. Retention of receipts follows `docs/ops/DATA-INVENTORY.md` (consent evidence `[counsel]`).

### 2.30 Pairwise `subject_ref` (spec §3.2)

`subject_ref = "sub_" ‖ base64url(HMAC-SHA256(SUBJECT_REF_KEY, "VIADERE-SUBJECT-V1\n" ‖ businessId ‖ "\n" ‖ consumerId))`, UUIDs as lowercase canonical strings, base64url unpadded (47 characters in total; the parser accepts exactly `sub_` plus 43 base64url characters that decode to 32 bytes). `SUBJECT_REF_KEY` is a dedicated secret (>= 32 random bytes, base64url), **required in staging and production, distinct from `SERVER_PEPPER`, `DATA_ENCRYPTION_KEY`, `AUDIT_CHAIN_KEY` and `CONNECT_LINK_SIGNING_KEY`** (startup refuses reuse). Properties: stable per (business, customer); the same customer has unrelated values at two businesses; not computable, reversible or enumerable without the key; never contains an identifier. It is stored in `relationships.subject_ref` (unique per business; assigned on creation by a model hook, and by the background job for older rows) so business requests resolve it with an indexed, **business-scoped** lookup.

Business APIs accept it in place of `relationshipId` on interactions, messages, statuses, rewards and loyalty points (body field `subjectRef`; both may be sent and must then agree; one of them is required) and return it as `scope.subjectRef` on interactions, `subjectRef` on sandbox relationships, redemption receipts, loyalty results and the `relationship.*`, `consent.updated` and `message.received` webhook events. After resolution a request is normalized (the real `relationshipId`, no `subjectRef`) so it hashes, and replays, identically however it was addressed. `relationshipId` keeps working.

**Relation to `consumerReference` (`scope.consumerId`, `RedemptionReceipt.consumerReference`).** Not equivalent, so not unified: it is a UUID-shaped 128-bit pseudonym derived under `SERVER_PEPPER` with domain `ref`, `subject_ref` is a 256-bit value under its own key and domain. Both stay in responses for compatibility; **`subject_ref` is the canonical identifier going forward** and `consumerReference` is deprecated (to be removed with the next API version). Neither can be derived from the other. **Key rotation changes every `subject_ref`** (businesses that stored refs must re-fetch): clear `relationships.subject_ref` and let the job re-derive; do not rotate without telling businesses.

### 2.31 Migration notes (WP2, `CreatePolicyWP2Schema.v1`)

Adds `business_entitlements`, `capability_switches`, `policy_rules`, `disclosure_receipts`, `business_api_keys.capabilities` and `relationships.subject_ref` (+ unique index per business). Existing keys keep working for what they did: a key with any interaction, message or status scope becomes a **messaging key** (`message.send`, `contact.reachable`, `consent.request`). It also gets `auth.challenge` / `transaction.approve` **only if its business has already issued interactions of kind `authenticate` / `authorize`**, and those businesses are **grandfathered**: tier A and the matching capabilities are recorded as entitlements (`granted_by = system:wp2-migration`, justification "Grandfathered ..."), for an operator to review in the console. Keys with only webhook or reward scopes get no capability. Nothing else changes for existing integrations: legacy operational scopes are untouched, `relationshipId` still works. Deploy order: set `SUBJECT_REF_KEY` first (startup fails without it where a database is configured), run migrations, start; the background job assigns `subject_ref` to existing relationships within seconds (until then `subjectRef` addressing of an old relationship answers `404`, `relationshipId` is unaffected).

### 2.40 Credential vault (WP5: Authenticator passkeys, TOTP, optional end-to-end encrypted sync)

Spec: SEC-DEV-005, §5.1 (third-party passkey vault), §13 (passkey private keys: never server plaintext), Phase 4 gate, acceptance 7. Code: `ViadereCore/Vault/` (formats, crypto, protocol), `ViadereKit/Vault/` (engine, storage, sync client, view model), `Server/.../Vault/`, `App/ViadereCredentialProvider/`, `App/Viadere/Features/Authenticator/`.

**Release gate.** `VAULT_SYNC_ENABLED` (default **off** in every environment; only the literal `true` enables it) gates every `/v1/vault/**` route: with it off they answer `404` after authentication (`401` first for unauthenticated callers), so the surface does not exist. It is also the kill switch (ops gap G-4): turning it off stops sync; devices keep working from their local encrypted vaults and nothing is deleted. Production keeps it off until the independent vault cryptography and recovery review passes (§17 Phase 4 gate). Account deletion wipes the vault rows whether or not the gate is on. While enabled, `/v1/vault` routes accept bodies up to 4 MiB (a key rotation re-uploads every item in one atomic request); everything else keeps `MAX_BODY_BYTES`. A vault may hold at most **2 MiB of item ciphertext** (`VaultFormat.maxTotalBlobBytes`): re-encryption keeps every blob's size, so a vault inside the cap can always upload a full rotation inside the request ceiling (`VaultFormat.maxRotationRequestBytes`, pinned below the ceiling by a test and exercised with 2,000 items and with the largest items the cap allows). A write over the cap is refused: the client says "Your vault is full" before uploading, and the server refuses an upload over it with `422`.

**Algorithms (SEC-CR-007).** All structures carry `version = 1`. AEAD id `1` = AES-256-GCM, random 96-bit nonce, 128-bit tag. HPKE suite id `1` = RFC 9180 base mode, DHKEM(P-256, HKDF-SHA256) / HKDF-SHA256 / AES-256-GCM. Signatures: ECDSA P-256 / SHA-256, raw `r || s`, low-S. KDF: HKDF-SHA256 with a distinct `info` label per purpose (key separation): `viadere.vault.v1.` + `item-kek`, `label-key`, `key-check`, `recovery-signing`, `recovery-agreement`, `recovery-binding`, `join-id`, `join-request`, `join-approval`, `envelope`, `manifest`. A changed algorithm is a new version, never an in-place change.

**Nonces.** Every seal draws a fresh random 96-bit nonce from the system CSPRNG; nothing derives or counts nonces. Item keys are single use (a new key per revision), so an item key seals exactly one plaintext; the long-lived keys (vault key derivations) seal at most a few hundred messages in their life, far under NIST SP 800-38D's 2^32 bound. Tests assert 20,000 distinct nonces.

**Sealed box.** `version(1) | aead(1) | nonce(12) | ciphertext | tag(16)`. AAD is `"viadere.vault.v1" 0x00 purpose 0x00` followed by length-prefixed (u32 BE) fields, so `("ab","c")` and `("a","bc")` never collide.

**Keys.** `VK` (vault key): 256 random bits, in memory only while unlocked. `itemKey`: random per item revision. `KEK = HKDF(VK, salt = itemId, "item-kek")`. `labelKey = HKDF(VK, salt = vaultId, "label-key")` seals device names. `keyCheck(epoch) = HKDF(VK, salt = epoch, "key-check")` is a public, signed commitment to `VK`: HPKE base mode does not authenticate its sender, so a device compares the unsealed key's check value with the signed manifest, which stops a server from handing a device a key of its own.

**Item blob** (the server stores one per item): `version(1) | sealed(itemKey) under KEK (62 bytes) | sealed(padded payload) under itemKey`. AAD of both seals: `(vaultId, itemId, epoch, revision)`, with purposes `item-key` and `item`. The payload is CBOR (`{v, kind, created, updated, passkey{cred, rp, uh, user, key, at, display?} | totp{secret, alg, digits, period, account, issuer?}}`), prefixed with its length and zero-padded to a multiple of 256 bytes, so a blob's size reveals only a bucket. Maximum 32 KiB.

**Envelope** (HPKE, one per member per epoch): `version(1) | suite(1) | enc(65) | ciphertext(32) + tag(16)` = 115 bytes. `info` and `aad` bind `(vaultId, epoch, memberId)`. The plaintext is `VK`. The manifest commits to each envelope with its SHA-256.

**Member.** `memberId = base64url(SHA-256(signing key X9.63))`. A *device* member has a signing key and an agreement key held on that device (signing: Secure Enclave, `.privateKeyUsage + .userPresence`; agreement: Keychain item, `.biometryCurrentSet` **or** the device passcode, `WhenUnlockedThisDeviceOnly`, in the app/extension-only keychain group; changing the enrolled biometrics invalidates the biometric path and the passcode remains the documented fallback). The agreement key's private bytes are not kept in memory for the unlock session: the identity holds its public key and a handle that reads the bytes from the Keychain for each HPKE operation and overwrites them afterwards (best effort; the crypto library keeps its own copy for the operation). Every membership or recovery operation (approve or remove a device, replace the recovery key, turn sync on, restore) signs with a key bound to an `LAContext` evaluated **for that operation** (`freshIdentity(reason:)`, a new context with no reuse), so the unlock earlier in the session does not cover them. TODO(vault-se-dhkem): hold the agreement key in the Secure Enclave and decapsulate inside it (`SecureEnclaveVaultAgreementKey` is a refusing stub until that is validated on devices). The *recovery* member's two keys derive deterministically from the recovery key (HKDF with distinct labels and a rejection counter for valid scalars), so any device can re-seal to it at a rotation without holding the recovery key.

**Manifest** (deterministic CBOR, RFC 8949 §4.2.1; one manifest has one byte string): `{v, vault, ver, prev, epoch, check, members: [{role, sign, agree, env, at, label?, bind?}], items: [{id, rev, hash}], signer, at}`; members sorted by id, items by item id. Signature over `"viadere.vault.v1.manifest" 0x00 || bytes`; `hash = SHA-256("viadere.vault.v1.manifest-hash" 0x00 || bytes)`; the next manifest's `prev` is that hash (32 zero bytes at genesis). Device `label` is the device name sealed under `labelKey`: the server cannot read it. Limits: 16 devices + 1 recovery member, 2,000 items, 256 KiB. A user or display name stored with a passkey is cut to 64 UTF-8 bytes on a character boundary at registration (WebAuthn §4.4.3 lets an authenticator do this), so a hostile relying party cannot make an item as large as the 32 KiB item limit.

**Chain rules** (`VaultChainVerifier`, run by clients and by the server): decode strictly and require canonical bytes; version = previous + 1 and `prev` = previous hash (else rollback or fork); the signer is a member of the **previous** manifest (membership is granted only by an already-trusted member) and stays a member; at most one device is added per version; **a device that disappears from the member list requires the epoch to rotate** (otherwise its envelope would still open the current key and "removal" would be cosmetic); existing members keep their keys; epoch is unchanged (then `check` and every existing envelope hash are unchanged) or +1 (then `check` and every envelope hash change and every item revision increases); item revisions never decrease and content never changes without a new revision. A restore with the recovery key is the single exception to "signer is a previous member": the recovery member signs an *authorization* for exactly one new device and the previous hash, the device signs the manifest, the used recovery member must be absent from it, and the epoch must rotate.

**Anti-rollback.** A device keeps the newest manifest it verified against the server (its anchor) and its own on-disk head hash in the Keychain; sync verifies the server's chain onward from the anchor and refuses older, forked or gapped chains (`rollbackDetected`). A state file older than the Keychain's head is refused.

**Adding a device** (existing device A with Face ID, new device B). A generates a 128-bit pairing secret `ps` (QR payload, or 28 Crockford characters with a checksum) and opens a join whose id is `HKDF(ps, "join-id")[0..16]`. B (an account device, which may still be in its cool-down) sends `{signing key, agreement key, name}` sealed under `HKDF(ps, "join-request")`. A opens it, shows B's name and a fingerprint of B's keys (B shows the **same** fingerprint of its own keys while it waits, and the person compares the two screens before approving), signs the manifest that adds B, seals the vault key to B's agreement key and returns `{vaultId, A's signing key, manifest hash}` sealed under `HKDF(ps, "join-approval")`. B pins A's key and the manifest hash from that approval, verifies the chain onward, opens its envelope, checks `keyCheck`, and decrypts every item before accepting. The server only ever holds ciphertext keyed by a secret it never sees; one request per join, ten-minute lifetime, three open joins per account.

**Removing a device** rotates the vault key (epoch + 1, every item re-encrypted under a fresh item key, every kept envelope re-sealed); the chain rules refuse a manifest that drops a device without it, on the server and on every client. The server also ends the removed member's access at once and remembers which account device acted for it: that account device can never again request a recovery release, ask to join, or restore (it would otherwise get the rotated key back through the account). A removed device keeps whatever it already copied: the UI says to change the credentials stored on a lost or stolen device.

**Recovery key (separate from account recovery and identity proofing).** 256 random bits shown once as `VRK1-` + 11 groups of 5 Crockford base32 characters, the last two bytes being a checksum; it must be typed back before sync turns on. It is **not** an account recovery code and nothing about it is derived from identity verification. A restoring device authenticates the server's chain with only the key: the recovery member's `bind = HMAC(HKDF(RK, "recovery-binding"), vault, member, installing device key)` was computed by a genuine device while it held the key, so matching it against the signer of one manifest proves that signer's key is genuine, and the chain is verified onward from there. A server that does not know the key cannot forge this (it could seal a vault key of its own to the recovery member's *public* key, but cannot produce the binding). The restore then replaces the vault key, removes every other device and retires the used key; a new recovery key (shown and confirmed first) replaces it.

**Recovery release (M2: account access plus the recovery key must not decrypt silently).** The server withholds the recovery member's envelope and, for any account device that is not a vault member, every read of the history, blobs and device list. A trusted account device asks for a **release** (`POST /v1/vault/recovery-release`); nothing is released for **72 hours** (the same hold as account recovery, §2.26). At once, every other account device gets an in-app notice and a push (`vaultRecoveryRequested`, with a "Not you? Cancel" action), stored in the same transaction as the hold, so a hold nobody could be told about never starts. (Consumer accounts hold no e-mail address by design, so there is no e-mail leg; push plus the in-app notice are the channels.) A vault device or any trusted account device can cancel (`POST /v1/vault/recovery-release/{id}/cancel`, which closes every open release and tells the others). After the hold the envelope is released for **24 hours to the requesting device only**; the first time anyone sees the window open the account is told (`vaultRecoveryReleased`), every envelope fetch is announced and audited (`vaultRecoveryFetched`, `vault.recovery_envelope_fetched`), and the restore uses the window up and is announced (`vaultRestored`). The restore itself is refused unless the signing device holds the open window. On the device: ask, wait, **check** (the client authenticates the chain with the recovery key, decrypts the vault and shows when it last changed, on which device, the device names and the item counts, with nothing committed: no key made, no server write), then confirm the new recovery key and commit; the check expires after 15 minutes.

**Server** (`/v1/vault`, device-signed + bearer): `GET /` status; `PUT /` compare-and-swap of manifest + changed blobs + changed envelopes (`expectedVersion`, `0` creates); `DELETE /`; `GET /manifests?after=`; `POST /blobs`; `GET /envelope`; `GET /recovery-envelope`; `GET /devices`; `DELETE /devices/{memberId}`; `PUT|GET|DELETE /joins/{joinId}`, `PUT /joins/{joinId}/request`. Tables: `vault_vaults`, `vault_manifests` (append-only history), `vault_blobs` (newest revision), `vault_members` (public keys, envelope, bound account device, removal), `vault_joins`. It stores ciphertext, signed public structures and public keys only; request bodies are never logged. Writes need the calling account device to be bound to the signing member; creating a vault, restoring, deleting and removing a device need a **trusted** device (not in its new-device cool-down, §2.5); an unbound account device (account recovery, or an attacker with the account) reads **nothing** of the vault except `GET /` (status, including any open release) until a recovery release has held for 72 hours, and then only for 24 hours and only for the device that asked; it can never write or open anything. Rate limits are per account **and device** (one account device cannot use up another's budget), per hour: writes 120 (burst 30), bound reads 1,200, unbound reads and probes 60 (burst 20), joins 30, release requests / envelope fetches / restores 5 each. Security notices (§2.17-style, in-app plus push to other devices): `vaultDeviceAdded`, `vaultDeviceRemoved`, `vaultDeleted`, `vaultRecoveryRequested`, `vaultRecoveryCancelled`, `vaultRecoveryReleased`, `vaultRecoveryFetched`, `vaultRestored`. Audit events: `vault.created`, `vault.updated`, `vault.device_removed`, `vault.deleted`, `vault.recovery_release_requested`, `vault.recovery_release_cancelled`, `vault.recovery_envelope_fetched` (counts and ids only). Tables add `vault_recovery_releases` and `vault_members.former_device_id`. Routes add `POST /recovery-release` and `POST /recovery-release/{id}/cancel`.

**Passkey engine** (`WebAuthnAuthenticator`, ES256 only). `authenticatorData` = `SHA-256(rpId) | flags | signCount(4) [| AAGUID(16) | credIdLen(2) | credId | COSE key]`. Flags: UP always, UV only after verification, BE always 1 (every Viadere passkey may sync), BS = 1 only while the vault is synced, AT on registration. **signCount is always 0** (a synced passkey has no single counter; RPs treat 0 as "unsupported", WebAuthn §6.1.3). AAGUID all zero. Attestation `none` (the default, and the only format the extension requests) or `packed` self-attestation (`alg -7`; spec-conformant and verified by the Core tests, but `webauthn-swift`, the server's own library, does not accept `packed` yet, so do not rely on it for interoperability). Credential IDs are 32 random bytes; the operating system supplies the client-data hash, so the engine signs for the relying party it is given and never sees an origin. Relying-party IDs are validated (lowercase LDH hostname, no port or scheme, not an IP). User verification is required and enforced: nothing is created or signed without it.

**Credential-provider extension boundary.** `provideCredentialWithoutUserInteraction` always demands interaction. The extension builds its engine **without a sync client** (no network) and shares only the App Group container (ciphertext: manifest, blobs, envelopes, sync bookkeeping; excluded from backup) and the vault-only keychain group `$(AppIdentifierPrefix)com.viadere.vault`. The app and the extension write the container under an exclusive file lock with compare-and-swap on the manifest hash; each re-reads before changing anything. The system AutoFill identity store receives site, account name, credential id and user handle for passkeys (and, where a label is a domain, a label for one-time codes), never keys, secrets or codes, and "Suggest in AutoFill" turns even that off.

**Residual risks and review focus.**
- *A forked or stale chain during a recovery-key restore (integrity only).* The recovery binding authenticates one signer key at the manifest where the current recovery member was installed; from there the chain rules check only that each manifest is signed by a member of its predecessor. A device that was **removed** later still holds a genuine signing key and the old vault key, so a malicious server together with that removed device can serve a *different* continuation of the genuine prefix (a fork it signed while still a member) to a restoring device that has no anchor: dropped later changes, but also items the removed device chose. Both continuations verify, so no cryptographic check on the restoring device can tell them apart without the recovery key being online to sign each state, and the key does not sign later states. It cannot read anything that was not already readable to the removed device, and the restore replaces the vault key and removes every other device. Mitigations: the restore **preview** (last-change time and device, device names, item counts) before anything is committed; the 72-hour hold, during which the real owner is told and can cancel; removed devices' account devices are refused at the server; the rotation rule means a removal is always visible as a new epoch on the real chain.
- *Removed devices keep what they copied* (rotation protects only later writes).
- *The recovery key is a bearer secret.* Anyone holding it and an account session can restore the vault once the 72-hour hold passes uncancelled; there is no second factor on it by design (an independent factor must not be an identity check). The hold gives the real owner three days and notices on every device to cancel; an owner with no reachable device and no push would not see it (the in-app notice waits for the next open).
- *In-memory exposure while unlocked*: the vault key and item plaintext live in process memory for the unlock session. The agreement key's bytes do not (read per operation and overwritten), but the crypto library's own copy during an operation cannot be zeroized; moving the key into the Secure Enclave (`vault-se-dhkem`) is the fix.
- *Local file replacement* is detected only as a rollback (version below the Keychain head), not as a forged-but-newer state; a local attacker who can write the container and the Keychain has already won.
- *HPKE sender is unauthenticated* (base mode) and bound by the signed `keyCheck`; review the choice against HPKE auth mode.
- *Metadata exposure (what the server and the system see).* **Server:** the number of items; each item's stable id and revision (so which items change and how often); each blob's size in 256-byte buckets; the number of devices and each member's role and `addedAt`; whether a recovery key is set; the manifest times (signed `at` and server `created_at`) and the version/epoch history; which account device wrote each version (the bound device is known to the server and appears in audit events); when a key rotation, a join, a recovery release, an envelope fetch or a restore happened; request IPs as for any route. It never sees item contents, names, relying parties, device names or any key that opens the vault. **System AutoFill** (only with "Suggest in AutoFill" on): for passkeys the relying-party id, the user name, the credential id and the user handle; for one-time codes the label (issuer and account). Turning the toggle off removes them from the identity store.
- *Credential Exchange import* (iOS 26) is parsed and tested against CXF-shaped JSON but not yet connected to `ASCredentialImportManager`; export is not implemented. The file-picker stand-in is compiled into DEBUG builds only, because it encourages a plaintext credential file in Files.
- *One-time-code suggestions are filtered by the requesting site*, using the registrable label of the domain the system passes against the code's issuer or e-mail account (a heuristic: a code whose issuer does not name the site is not offered in AutoFill and has to be copied from the app). The extension keeps one engine, and so one biometric evaluation, per time it is on screen, and a user verification older than 60 seconds is repeated before a passkey signs.
- *Apple code paths* (Secure Enclave/Keychain provider, extension, scanner) cannot be built or run on Linux: they need device verification (App/README.md).

### 2.50 End-to-end encryption (WP1: `ViadereCore/E2EE`, HPKE RFC 9180)

Public API (stable; other work packages such as Verify call it to deliver identity results to businesses):

```swift
let envelope = try E2EE.seal(plaintext, to: recipientPublicKey,           // E2EEPublicKey (kid + X9.63)
                             context: E2EEContext(purpose:, requestId:, sender:, recipient:, expiresAt:))
let wire     = try envelope.serialized()                                  // canonical JSON bytes
let parsed   = try E2EEEnvelope.parse(wire)                               // strict; rejects unknown version/suite/members
let opened   = try E2EE.open(parsed, using: privateKey,                   // any E2EEPrivateKey (software, KMS, Keychain)
                             expecting: E2EEExpectation(purpose:, requestId:, sender:, recipient:), now: now)
```

**Suite.** `suite = "hpke-0010-0001-0002"`: base mode, KEM `DHKEM(P-256, HKDF-SHA256)` (0x0010), KDF `HKDF-SHA256` (0x0001), AEAD `AES-256-GCM` (0x0002), via CryptoKit / swift-crypto `HPKE`. Nothing is negotiated: an unknown `suite` or `v` is rejected (`E2EEError.unsupportedSuite` / `.unsupportedVersion`), as is every unknown or missing member.

**Envelope** (members exactly `v, suite, kid, enc, ct, ctx`; canonical JSON, section 2.2):

| Member | Meaning |
|---|---|
| `v` | `1` |
| `suite` | as above |
| `kid` | recipient key ID: `base64url(SHA-256(DER SubjectPublicKeyInfo of the recipient's P-256 key))`, **not truncated** (43 characters). A lookup handle only: verifiers compare the full public key. |
| `enc` | HPKE encapsulated key, base64url of 65 bytes (X9.63), validated as a curve point |
| `ct` | AEAD ciphertext plus 16-byte tag, base64url, at most 64 KiB plaintext |
| `ctx` | `{"exp": unix seconds, "purpose": [a-z0-9._-]{1,64}, "recipient": id, "request_id": id, "sender": id}` (ids `[A-Za-z0-9._:-]{1,128}`) |

**Binding (SEC-CR-001).** `header = canonicalJSON({v, suite, kid, ctx})`. HPKE `info = "VIADERE-E2EE-INFO-V1\n" ‖ header`; AEAD `aad = "VIADERE-E2EE-V1\n" ‖ header`. Changing the purpose, request, sender, recipient, expiry or recipient key makes opening fail with one error (`authenticationFailed`), so there is no decryption oracle. `open` additionally requires the caller's `purpose` (always) and `request_id`, `sender`, `recipient` when given, and refuses an expired envelope **before** decrypting.

**Nonces (SEC-CR-008).** One fresh HPKE sender context (fresh ephemeral key) per envelope and exactly one `seal` at sequence number 0, so an AEAD nonce is never reused under a key.

**Sender authentication.** HPKE base mode does not authenticate the sender (anyone with the public key can encrypt). Every protocol that uses an envelope therefore authenticates the sender **inside the plaintext** with a signature from a key published in the authenticated business key directory (section 2.51); for Approve, `ApprovalRequest` (section 2.54). A relay that holds a device's public key can produce an envelope that decrypts, but not one with a valid business signature.

**Keys.** A device keeps one HPKE key per business relationship in the Keychain (`WhenUnlockedThisDeviceOnly`; CryptoKit HPKE with Secure Enclave keys is OS-version dependent, so it is not relied on). A business keeps its HPKE key in its KMS; its public part is published as a root-signed directory statement (purpose `hpke-encryption`).

### 2.51 Authenticated business key directory (WP1: `ViadereCore/KeyDirectory`)

Purpose (SEC-CR-006): a device must never encrypt to, or accept a signed request from, a key that Viadere's relay merely asserts. Every key a business uses with Approve is **signed by the business's own root key** and **logged in an append-only Merkle transparency log**; devices pin the root and verify the log themselves.

**Key IDs.** `kid = base64url(SHA-256(DER SubjectPublicKeyInfo))`, 43 characters, for every P-256 key (`KeyIdentifier`). Display fingerprint: the same value in groups of five characters (`ABCDE-FGHIJ-...`), for people comparing a root key out of band.

**Statements.** Each is canonical JSON (section 2.2), wrapped as `SignedStatement {payload: base64url, signature: base64url raw r‖s, low-S}`, and signed over `domain ‖ payload` with a **per-type domain string** so a signature for one type never validates as another:

| Type | Domain | Payload members (all required, exactly these) | Signed by |
|---|---|---|---|
| `root` | `VIADERE-KD-ROOT-V1\n` | `v, type, business_id, root_kid, public_key, created_at` | the root key itself (self-signature) |
| `root-succession` | `VIADERE-KD-SUCC-V1\n` | `v, type, business_id, old_root_kid, new_root_kid, new_public_key, created_at` | **both** the old and the new root (two signatures) |
| `key` | `VIADERE-KD-KEY-V1\n` | `v, type, business_id, root_kid, purpose, alg, kid, public_key, not_before, not_after, serial` | the current root |
| `revoke` | `VIADERE-KD-REVOKE-V1\n` | `v, type, business_id, root_kid, kid, reason, revoked_at, serial` | the current root |

Purposes: `approval-enrollment-confirmation` (ES256), `approval-request-signing` (ES256), `hpke-encryption` (`hpke-0010-0001-0002`). A key is valid for its own purpose only. `not_after - not_before <= 400 days`. `serial` is a per-business counter that must be contiguous across `key` and `revoke` statements (rollback and gap detection); `kid` values are never reused.

**Replay rules (`BusinessKeyState.apply`, shared by the device, the SDK monitor and the server).** The first entry for a business must be `root`; a second `root` is refused. A `root-succession` needs the old root's current key **and** a signature by the new root; after it, **nothing is inherited**: the new root must republish every operational key, and statements signed by the old root are refused (`rootMismatch`). A statement must name the current root, carry the next serial, and its `kid` must be the key id of its `public_key`.

**Log entry (the Merkle leaf).** `canonical({"business_id", "sigs": [base64url r‖s, ...], "statement": base64url(payload), "type", "v": 1})`. Leaf hash `SHA-256(0x00 ‖ leaf)`, node hash `SHA-256(0x01 ‖ left ‖ right)` (RFC 6962 / RFC 9162 section 2.1). The server rebuilds the tree from the append-only table `kd_log_entries` (database triggers refuse `UPDATE` and `DELETE`) and appends under an advisory lock, **validating the whole business history inside the lock**, so concurrent publishers cannot interleave an invalid state.

**Signed tree head (STH).** `{"payload": b64url(canonical {v:1, log_id, tree_size, root_hash (hex), timestamp}), "signature": b64url raw r‖s}` signed over `"VIADERE-STH-V1\n" ‖ payload` by the Viadere log key (`KEY_DIRECTORY_LOG_KEY`, P-256; the public key is built into the app: Info.plist `ViadereKeyDirectoryLogKeys`, set from `VIADERE_KEY_DIRECTORY_LOG_KEYS`; `ViadereServer key-directory-log-key` prints it). A new head is signed when the latest is older than an hour. Devices refuse a head older than **7 days** (`treeHeadStale`) or from the future.

**What a device verifies (`KeyDirectoryVerifier.verify`).** In this order: (1) the STH signature against a pinned log key and the log id; (2) freshness; (3) **consistency with the last head this device accepted** (RFC 6962 consistency proof; a smaller tree is `treeShrank`, a different history is `forkDetected` or `consistencyFailed`, a missing proof is `consistencyProofMissing`); (4) for **every** returned entry, canonical form, and an **inclusion proof** to the head's root; (5) entries in strictly increasing log order; (6) the state machine above, producing the business's current root and its valid keys at `now`.

**Pinning and the root-change alert.** On first contact the device pins the business root `kid` (`firstUse`; or `verifiedOutOfBand` when the enrollment link or QR carried `rk=<root kid>` and it matched). Later: `unchanged`; `rotated` (a valid two-signature succession from the pinned root: the app **blocks that business's requests**, shows both fingerprints and asks the person to confirm); `conflict` (the pinned root is not in the history the log now shows: a different history; blocked, never cleared by the network, only by an explicit "forget" the person performs). The "pinned head" is global per device, so a relay cannot show one device a different log than another without the device noticing on its next fetch.

**Log monitor.** `viadere-key-monitor` (BusinessSDK executable) fetches the log for the business, runs the same verification, and reports any entry the business's own `BusinessKeyAuthority` did not create (an unexpected key, an unexpected revocation or succession), plus any inconsistency with the previously stored head. Usage: `VIADERE_API_KEY=... viadere-key-monitor --business <id> --log-key <base64url public key> --state <file> [--expect <leaf hash>]...`. Exit `0`: every new entry is one the business expected; `2`: an unexpected entry or a failed verification (treat as an incident; the alert repeats until handled); `64`: usage. Businesses should run it on a schedule (suggested: every 5 minutes).

**Endpoints.** `GET /v1/key-directory/sth`, `GET /v1/key-directory/consistency?first=&second=`, `GET /v1/key-directory/businesses/{id}?since=` (public, rate limited; the business page carries the STH, optional consistency proof from `since`, and every entry for that business with its inclusion proof); `POST /v1/business/key-directory/entries {"entry": b64url(canonical KeyLogEntry)}` and `GET /v1/business/key-directory/entries` (business API key with scope `keydirectory:manage`; the server verifies the signatures, the replay rules and that a root `created_at` is within a day of now; Viadere is a notary, not a key custodian, and it does not hold or generate any business key. Root registration and succession are audited (`keydirectory.root_registered`, `keydirectory.root_changed`)).

**Who may register or replace a root (condition 4 of the Phase 2 gate).** A `root` or `root-succession` entry is accepted by `POST /v1/business/key-directory/entries` only when (1) the business has a **verified domain** (WP6 onboarding) and (2) a dashboard user with `manageSecurity` (Owner, Security Admin) authorized exactly this root key id with a **fresh passkey step-up** (`POST /dashboard/approve/root-authorizations`; `kd_root_authorizations`: kind `register` while the business has no root, `succession` otherwise; bound to the key id (the new root's for a succession), single use, 15 minutes, consumed inside the same transaction that appends the entry so a rejected entry does not burn it). An API key with `keydirectory:manage` alone gets `403` (`dashboard_step_up_required` or `verified_domain_required`) and `keydirectory.root_refused` is audited. This closes root squatting: a stolen API key can no longer register its own root for a business that has none, which would have been permanent. It does not remove the need for the business's own monitor, and a business whose dashboard and API key are both compromised remains exposed (section 2.58).

### 2.52 Transparency log operations and limits

* The log key signs only tree heads. It never signs business statements, so a stolen log key can hide or fork history from devices that have not pinned a head (it cannot create a business key). Compromise response: publish a new `log_id` and key in an app release (two keys may be pinned during a rotation) and re-baseline; devices holding a head for the old log reject the new one until updated.
* Entries are never deleted. A business revoking a key appends `revoke`. Account deletion removes the account's device data, not the log (it holds business keys only, no personal data).
* Per-business pages hide other businesses' entries, but proofs are against the global tree. A relay that **omits trailing entries of one business** (for example a revocation) is detectable only by the business's monitor or by a device that saw the later head; short validity windows bound the exposure (residual risk 1 in section 2.58).

### 2.53 Business-authorized enrollment of a pairwise approval key (APP-001/002, ADR-06)

Actors: the customer's device D, the business B (its server, via BusinessSDK), and the relay R (Viadere). **R is not trusted to bind D's key to B.**

1. **B creates an enrollment** for a customer it already knows: `POST /v1/business/approve/enrollments {"subject_ref", "capability": "auth.challenge"|"transaction.approve", "expires_in_seconds"?}` (policy checked, section 2.29; the customer must be connected to B). The response has `enrollment_id`, a single-use 8-character `code` over `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (40 bits, shown `ABCD-EFGH`), and a `deep_link` that is only the relay's suggestion and **is never shown**. **The SDK builds the link B shows** (gate findings F1 and F3), see the link format below. B shows it in its own authenticated session (QR or button). Lifetime default 10 minutes, at most 15; at most 3 open enrollments per relationship.
2. **D looks up** the code (`POST /v1/approve/enrollments/lookup`; only the customer the enrollment was created for succeeds; wrong codes are rate limited per consumer and globally and all answer the same `404`). The reply names the verified business, the capability and the required assurance (`biometric` for high and critical). D then **verifies B's directory** (section 2.51) and requires a published `approval-enrollment-confirmation` key; if the link carried `rk`, it must equal the log's root key id (`rootMismatchWithLink`). **D creates no key unless it holds the link's secret `es` or the check code** (`enrollmentSecretRequired`).
3. **D creates a fresh Secure Enclave approval key and a fresh HPKE key for this relationship** (`.biometryCurrentSet` when biometric is required; if the phone cannot make such a key, enrollment stops and nothing is created) and signs an `approval-enrollment` statement with the **new approval key**, domain `VIADERE-APPROVAL-ENROLL-V1\n`: members `v, type, business_id, subject_ref, enrollment_id, kid, public_key, alg, hpke_kid, hpke_public_key, assurance, created_at`. Sent with `POST /v1/approve/enrollments/{id}/complete {"statement", "binding_tag"?}` (the tag is below). The key is **pending**: it cannot approve anything, and a key B does not confirm within the enrollment's expiry plus 5 minutes is revoked and alerted (below).
4. **B fetches** the statement (`GET /v1/business/approve/enrollments/{id}`), **verifies it itself** (signature by the statement's own key, `business_id`, `subject_ref`, `enrollment_id` match what B created, `assurance >= required`, kid matches key) **and authenticates its origin with the enrollment secret (binding tag or SAS, below)**, and, if satisfied, **confirms** with `POST .../confirm {"confirmation": BusinessSignedStatement}`: `{kid: confirm key id, payload, signature}` over domain `VIADERE-APPROVAL-CONFIRM-V1\n`, members `v, type: approval-enrollment-confirmation, business_id, subject_ref, enrollment_id, kid, statement_digest (hex SHA-256 of the canonical SignedStatement), confirm_kid, confirmed_at`, signed by a directory-published confirmation key. The relay checks the confirmation only for form; **it cannot forge it**.
5. **D activates the key only after verifying the confirmation against the directory**: signed by a currently valid published `approval-enrollment-confirmation` key, naming this business, this `subject_ref`, this enrollment, this `kid` and the **digest of the statement D itself signed**. A relay that substituted its own key in step 3 produces a confirmation (from B) over a different digest; D reports `substitutionDetected`, deletes its keys, revokes both the key it made and the one the relay reports, and shows the person a message. The enrollment is also refused if the relay returns a `kid` that is not D's.

**Who made the statement? The enrollment secret (gate finding F1, SEC-CR-006).** A statement that verifies proves only that *someone* holds the private half of the key inside it. R knows `enrollment_id`, `business_id` and `subject_ref`, can generate its own P-256 key and HPKE key, and can sign a flawless statement; B cannot tell it from D's. So B authenticates the statement over a channel R does not see, with a secret only B and D's app hold:

* **`es`**: 256 random bits from B's CSPRNG per enrollment (`ApprovalEnrollmentSecret`), kept by B (server side, with the enrollment id) until it confirms or cancels. Never sent to Viadere, never logged.
* **Link / QR (strong path).** `https://viadere.com/a/{CODE}?rk={B's own root kid}#es={base64url(es), 43 chars}`. The SDK builds it (`ApprovalEnrollmentInvitation.link`); `rk` is B's own root kid, and the SDK refuses a relay ticket whose `deep_link` names another root or none (`rootKeyMismatch`, gate finding F3; the enrollment is cancelled). A URL fragment is never sent in an HTTP request, so R sees neither the link's `es` nor a Referer containing it; the web fallback page for `/a/*` must not read, log or forward the fragment. The app parses the link strictly (exact host, path, at most one `rk`, a fragment that is exactly `es=` plus 43 characters; anything else is refused).
* **Binding tag.** D sends, with its statement, `binding_tag = base64url(HMAC-SHA256(key = es, "VIADERE-ENROLL-BIND-V1\n" ‖ statement.payload))` (43 chars; the payload is the base64url string exactly as signed). R stores and returns it (`binding_tag` in the business view) but cannot compute, check or move it to another statement (each statement has its own payload; each enrollment its own `es`). **B verifies it in constant time before signing anything** (`confirmApprovalEnrollment`): a missing or wrong tag is `verificationRequired` (typed path) or `bindingTagInvalid`; the latter **cancels the enrollment** (the relay-held pending key is revoked).
* **Typed code (no fragment).** The person types the code instead of scanning. B then also shows a 40-bit **check code**, `checkCode = base32(HMAC-SHA256(es, "VIADERE-ENROLL-CHECK-V1\n"))[0..<40 bits]` over the same alphabet (`ABCD-EFGH`), which the person types into the app **as well**. It is never sent to R. D computes the **SAS** and shows it: `SAS = decimal(uint32(HMAC-SHA256(key = SHA-256("VIADERE-ENROLL-SAS-KEY-V1\n" ‖ checkCode canonical), "VIADERE-ENROLL-SAS-V1\n" ‖ statement.payload))[0..<4]) mod 10^6`, six digits. The person types the SAS into B's own signed-in session; B recomputes it from `es` and the statement it received and compares in constant time. R never sees the check code, so it cannot compute the SAS of the statement it saw and cannot grind a forged statement to match one (a SAS keyed only by the statement would be grindable: about 10^6 key generations). A wrong SAS **cancels the enrollment** (one guess per enrollment, success probability about 10^-6). A tag-less statement with no SAS never confirms.
* No tag and no check code: D does not create a key at all.
* Residual: the typed path's root pinning is trust on first use (no `rk`), and a person who is shown both codes by a phisher gives the phisher the means to enroll (the codes belong to B's own signed-in session and must never be sent by SMS, email or read out on a call). The confirmation is not itself keyed by `es`; a relay that also forges a directory for a business D has never seen can still produce a confirmation D accepts at first contact (section 2.58, residuals 2 and 10).

**An unconfirmed key is ended and alerted.** R cannot hold a completed enrollment back and confirm later (a relay could otherwise wait for the business to look away): after `expires_at + 5 minutes` `POST .../confirm` answers `410`, and the sweep marks the enrollment `expired`, revokes the pending key (`revoked_by: system`), audits `approve.enrollment_unconfirmed`, sends B an `approve.key.revoked` webhook and the customer the notice `approvalKeyUnconfirmed`. D removes a pending key itself after `confirmBy` (enrollment expiry + 5 minutes) and reports it (`unconfirmedExpired`).

Unlinkability: the approval key, the HPKE key and the `subject_ref` exist for one relationship; no value is shared across businesses and none derives from a device or account key. Revocation: the customer (`POST /v1/approve/keys/{kid}/revoke`), the business (`POST /v1/business/approve/keys/{kid}/revoke`), device revocation, disconnecting the business, and account deletion all revoke keys server-side; devices reconcile on launch. A business can reject any request for a revoked key by checking its own store (section 2.54).

### 2.54 ApprovalResult v1 and ApprovalRequest v1 (acceptance 3, 4, 5, 7; `ViadereCore/Approve`)

**ApprovalResult** is a compact JWS (RFC 7515), `b64url(header).b64url(payload).b64url(signature)`, at most 2048 bytes, produced by the device's pairwise approval key. Header (canonical JSON): `{"alg":"ES256","kid":"<approval key id>","typ":"viadere-approval+jws"}`. **Only** `alg`, `kid`, `typ` are accepted; any other parameter is refused (no `jwk`, `jku`, `x5u`, `b64`, `zip`), and any `crit` is refused because this version defines no critical extensions. `alg` must be exactly `ES256` (`none`, `HS256`, `ES384`, ... are `unsupportedAlgorithm`). Payload (canonical JSON, byte for byte; the verifier re-serializes and rejects non-canonical input): `v` (1), `alg` and `kid` (repeated, must equal the header), `aud` (business id), `sub` (`subject_ref`), `request_id`, `challenge`, `cap`, `decision` (`approve`, `deny`, `report`), `amr` (`biometric`, `device_passcode`), `iat`, `exp` (`exp - iat <= 600 s`; devices sign 300 s), `txn_digest`. Signature: ECDSA P-256 / SHA-256, raw `r‖s`, low-S, over the ASCII `header64 + "." + payload64`. Canonicalization: sorted keys, no whitespace, integers only, UTF-8, NFC (section 2.2).

`txn_digest = hex(SHA-256("VIADERE-TXN-V1\n" ‖ canonical(displayed details)))` where the details are exactly the displayed object: `transaction {currency (an ISO 4217 code from the allow-list in `ISO4217`, with its minor-unit exponent: JPY/KRW and the other zero-decimal currencies 0, BHD/KWD/OMR/TND/JOD/IQD/LYD 3, CLF 4, otherwise 2; any other three-letter code, funds and metals codes and withdrawn codes such as BGN are refused), amount_minor, payee_display, transaction_reference}` (spec 14.2) or `authentication {action_display, reference?}`, validated (lengths, NFC, no control or bidi characters, currency-aware amounts).

**What a business verifies (`ApprovalVerifier`, BusinessSDK), all against its own records, never against relay status.** (1) Strict parse. (2) `kid` is an active key it enrolled and confirmed for exactly this `sub` (`unknownKey`, `keyRevoked`). (3) Signature with the key it recorded (the enrollment statement), not a key supplied with the result. (4) `aud` is itself; `sub`, `request_id`, `challenge`, `cap` equal the pending request it created; `txn_digest` equals the digest of the transaction **it** holds (`transactionMismatch`, so a changed amount, payee, currency or reference fails). (5) `iat`/`exp` within bounds and not after the request's expiry. (6) `decision == approve`. (7) `amr` meets its minimum and does not exceed what the enrolled key can provide (`amrExceedsKey`). (8) **Replay**: the verifier consumes `aud ‖ kid ‖ challenge` in a `ReplayGuard` (`registerIfFresh`, expiring at the result's `exp` plus skew) **after** all other checks pass, so a forged result cannot burn a real challenge; a second presentation is `replayed`. A business that persists its replay cache must make the insert atomic (unique constraint). Only then does it act.

**ApprovalRequest** (end-to-end requests). The business signs, per device, the exact content the person will see, with a directory-published `approval-request-signing` key, domain `VIADERE-APPROVAL-REQUEST-V1\n`: members `v, type: approval-request, business_id, subject_ref, request_id, capability, challenge, transaction|authentication, to_kid, iat, exp` (`exp - iat <= 600`). The signed statement `{kid, payload, signature}` is the plaintext of an E2EE envelope (section 2.50), `ctx = {purpose: "approve.request", request_id, sender: "biz_<business id>", recipient: "ak_<approval kid>", exp}`. The device decrypts, checks the signer is a **valid published key of that business**, the business, subject, `to_kid` and `request_id`, expiry, and only then shows it. Anything that fails is hidden and recorded (`signer_not_published`, `signature_or_binding_invalid`, `decryption_failed`, `misattributed`, `missing_envelope`).

**Server-visible requests** (`transaction`/`authentication` and `challenge` in the clear, the spec 14.2 body) work for businesses that cannot encrypt. They are marked `protection: "server_visible"`; the app labels them "Viadere passed this on and could read it. It is not signed by the business." A relay can invent such a request, but not an authorization: the result is still signed by the pairwise key and verified by the business against the pending request **it** created, so an injected prompt cannot yield an approval for something the business did not ask for. Prompt injection of this kind is a residual risk (section 2.58).

### 2.55 Requests, results and the relay (`Server/.../Approve`)

* `POST /v1/business/approve/requests` (`request_id` 1 to 128 chars `[A-Za-z0-9_.:-]`, idempotent per business; `capability` `auth.challenge` or `transaction.approve`, policy checked; `expires_in_seconds` 30 to 600). **End-to-end:** `envelopes: [{"kid": approval kid, "envelope": E2EEEnvelope}]` (1 to 8; every `kid` must be an active key of this customer and business, and the envelope's `ctx` must be bound to this request, business and key; no plaintext fields allowed). **Server-visible:** `challenge` (base64url, 22 to 128) plus `transaction` or `authentication`. A customer with no active key gets `409` with `details.reason = "no_active_key"`. The server never needs to read an end-to-end request.
* Devices `GET /v1/approve/requests` and `POST /v1/approve/requests/{id}/result {"result": JWS}` (the relay's delivery id, per device and key). The relay verifies the JWS with the stored public key (key active, `kid` equals the delivery's, signature, audience, subject, request, expiry, challenge for server-visible requests; for end-to-end requests it cannot read the content, so the transaction digest check is the **business's**), the device is an `app` device and not inside its new-device cool-down for a high or critical request, the customer is not frozen (`409 approvals_frozen`), and the request is still pending; the state change is a compare-and-swap (`replay_detected` on a second answer). Rejections are audited with a reason code.
* `GET /v1/business/approve/results/{result_ref}` returns the stored JWS and `kid`. **The relay's `status` field is never sufficient to act**: it is information for UX; the business verifies the JWS (section 2.54).
* Retention: the displayed details and the challenge are cleared at the terminal state; requests are purged after 400 days; the result JWS (no personal data beyond the subject reference) is kept for dispute evidence.
* Counters and prompt-fatigue (SEC-DEV-008): per relationship, window 1 hour; the device is told to warn from 3 requests (`show_fatigue_warning`); more than 6 an hour are refused (`429` with `Retry-After`); 3 denials or reports in the window pause the business's requests for that customer (`approvals_paused`); at most 3 requests pending at once. The count is taken **inside the transaction that inserts the request, after locking the relationship row** (`SELECT ... FOR UPDATE` on PostgreSQL; SQLite serializes writers), so a concurrent burst cannot all pass a count none of them has changed (gate finding F5). The app also counts the person's own answers locally and shows the warning regardless of what the relay says.

### 2.56 Webhook v2: the opaque envelope (spec 14.3)

Opt-in per subscription (`CreateWebhookRequest.envelope_version = "2026-10-27"`; default stays v1). The opaque events are the six `approve.*` events, `interaction.decided`, `interaction.expired`, `interaction.cancelled` and `verification.completed`; a v2 subscription cannot subscribe to any other type. The body is **only**:

```json
{"id":"evt_...","type":"approve.request.decided","version":"2026-10-27","tenant_id":"<business id>","request_id":"req_...","occurred_at":"2026-10-27T10:15:00Z","result_ref":"res_..."}
```

No customer data, amounts, names, subject references or decisions. The business fetches `GET /v1/business/approve/results/{result_ref}` and verifies the JWS. Types: `approve.enrollment.device_completed`, `approve.enrollment.confirmed`, `approve.key.revoked`, `approve.request.decided`, `approve.request.expired`, `approve.frozen`. Decoding is strict (unknown or missing members are rejected). For `approve.frozen`, `request_id` is an **opaque random per-business reference** `frz_` + 22 base64url characters (`approve_freeze_events`), never the `subject_ref` and never the same for two businesses (it would otherwise link a customer across them); the business resolves it with `GET /v1/business/approve/freezes/{ref}` using its own key (another business's reference is a `404`).

Headers: `Viadere-Signature` (existing HMAC scheme, section 2.6, over `timestamp.body`), **`Viadere-Delivery-Id`** (unique per attempt series; retries keep it, so receivers deduplicate on `id` and delivery), **`Viadere-Key-Id`** = `whk_<subscription prefix>_v<secret version>` (the secret version increments on rotation; receivers pick the secret by key id, which allows overlap during rotation), `Viadere-Webhook-Version`. The SDK's `verifyEnvelope` checks signature, timestamp tolerance, key id format and strict body, and exposes ids only. A v1 verifier given a v2 body fails closed.

### 2.57 Freeze, prompt-fatigue, suspicious-request reporting (APP-007, SEC-DEV-008)

* **Freeze.** `POST /v1/approve/freeze {"scope": "account"|"relationship", "relationship_id"?, "frozen": bool, "proof"?}`. Freezing needs only the signed device request (it only ever reduces access). Lifting needs a **trusted device** (cool-down passed) and a fresh `ApproveFreezeProof`: a `SignedStatement` by the device's `approvalBiometric` key, domain `VIADERE-APPROVE-FREEZE-V1\n`, members `v, action: "unfreeze", device_id, scope, relationship_id?, signed_at` (accepted when signed at most 300 s ago and at most 60 s in the future; single use, keyed on the signed payload). While frozen, every result submission is `409 approvals_frozen`, new requests are accepted but marked paused, and the business gets `approve.frozen`. A **business** may freeze a `subject_ref` (`POST /v1/business/approve/freeze`), and may lift only its own freeze, never the customer's. Frozen state is audited and creates a security notice.
* **Report.** The device can answer a request with `decision: "report"` (a signed denial). It counts as a denial for the pause rule, creates a security notice for the customer and an operator-visible event, and the business sees `report` in the verified result.
* **Lifecycle.** Revoking a device revokes its keys; disconnecting a business revokes that relationship's keys; deleting the account wipes keys, requests and freeze state.

### 2.58 Approve v2 threats, release gate, migration notes

Threat rows are in section 1 (Approve v2 and key directory). **Release gate:** `APPROVE_V2_ENABLED` (default **off** in staging and production, on in development and tests); off is also the kill switch (all Approve and key-directory routes answer `404`; keys and log untouched). `KEY_DIRECTORY_LOG_KEY` (base64url 32-byte P-256 scalar) is required when Approve is enabled with a database; `KEY_DIRECTORY_LOG_ID` optional. The app ships with no pinned log key unless `VIADERE_KEY_DIRECTORY_LOG_KEYS` is set, in which case Approve v2 is closed (fail closed). Phase 2 assessment focus: key substitution at enrollment, directory consistency and rollback, algorithm confusion, replay under concurrency, E2EE binding, freeze bypass, enumeration of enrollment codes and `subject_ref`s.

Residual risks: (1) a relay can omit trailing entries of a single business's history (per-business view) until the business's monitor or the device sees a later head; (2) a root is registered or replaced only after a dashboard passkey step-up for a business with a verified domain (section 2.51); the root is still not tied to a reviewed legal entity, and an attacker who controls both a Security Admin's passkey session and an API key can register one for a business that has none (the business's monitor and the device's first-use fingerprint are the remaining controls); (3) the log key is an environment secret until KMS (ADR-03); (4) the Secure Enclave key origin is not attested to the business (a business trusts the device statement and `assurance`); (5) no gossip between devices, only per-device consistency; (6) server-visible mode lets the relay inject a prompt (never an authorization); (7) the device HPKE key is a software Keychain key; (8) the Merkle tree is rebuilt in memory per process (a scaling item); (9) the legacy `authorize` / `authenticate` interaction path is decided on relay status alone (the signed decision is stripped for businesses) and is **not independently verifiable**; while Approve v2 exists it is refused for live traffic (`403 legacy_approval_not_entitled`) unless an operator granted the business the explicit, audited **legacy approval entitlement** (kind `legacy`, justification of 20+ characters naming the migration plan, at most 180 days, no grant or use after the platform sunset **2027-06-30**; sandbox traffic is unaffected; refusals are audited as `interaction.legacy_approval_refused`), and it is never documented as verifiable; (10) enrollment is authenticated by the enrollment secret (section 2.53): the typed path rests on 20 bits of SAS with one guess per enrollment and on the person entering both codes only into the real app, and trust on first use for the root; (11) the device's last seen tree head is advanced monotonically (a late, older refresh cannot roll it back; two trees of one size are a fork and fail closed), and trusting a changed business root needs a fresh Face ID / Touch ID proof from the device's biometric key (a tap on an unlocked phone is not enough).

Migration (`CreateApproveGateSchema.v1`, after the gate review): `approve_enrollments.binding_tag`, `approve_freeze_events`, `kd_root_authorizations`; entitlement kind `legacy` (no schema change). Migration (`CreateApproveWP1Schema.v1`): new tables `kd_log_entries` and `kd_tree_heads` (append-only triggers), `approve_enrollments`, `approve_keys`, `approve_requests`, `approve_deliveries`, `approve_freezes`; `webhook_subscriptions` gains `envelope_version` (default `v1`) and `secret_version` (default 1). No existing row changes meaning. Rollback: set `APPROVE_V2_ENABLED=false`; tables can stay.


### 2.60 Verify (WP3: Apple Wallet IDs and Didit; `ViadereCore/Verify`, `Server/.../Verify`)

Spec: §2, §6 (VER-001..009, AGE-001..007, §6.4), §11.1 LEG-PR-003/008, §11.3, §13, §14.1, §14.3, acceptance 1, 2, 6, 10. **Release gate:** `VERIFY_ENABLED` (default **off** in every environment; staging and production also need `VERIFY_GATE_REFERENCE`, the recorded Phase 3 gate decision). Off: all Verify routes `404`, nothing is disclosed (in-flight requests end `not_verified`), provider sessions are still purged.

**Assurance taxonomy (§6.1, VER-005/007/009).** Dimensions are recorded separately (`AssuranceDimensions`): evidence (`none`, `simulated`, `self_asserted`, `biometric_estimate`, `document_with_biometric_match`, `issuer_signed_credential`), authenticator (`none`, `device_bound`, `device_bound_user_verified`), issuer trust (`none`, `configured_trust_anchor`, `provider_attested`), freshness (`verifiedAt`, `validUntil`), presentation binding (`none`, `provider_session`, `device_signature_over_transcript`) and transaction risk (the capability's sensitivity). Result labels (`VerificationLabel`) are distinct: `verified_identity`, `verified_age_threshold`, `registered_authenticator`, `reachable_contact`, and `estimated_age` which is **never** "verified". `VerificationMethod.establishes` is the ceiling per method: Wallet mdoc and Didit document+liveness+face match may establish `verified_age_threshold` and `verified_identity`; a Didit selfie age estimate establishes only `estimated_age`; a device key only `registered_authenticator`; a contact code only `reachable_contact`. `RequiredEvidence.isSatisfied(by:)` accepts exactly one label per requirement (no promotion), and a Wallet `age_over_NN` result is age evidence, not identity evidence. The provenance record (`VerificationProvenance`, in `verification_results.provenance`) holds method, verifier, issuer (`<16 hex of the trust anchor>` or `didit:<ISO>`), label, the dimensions, expiry, revocation state (`not_checked` for mdoc, `not_applicable` for a provider session) and `policy_version` (`verify-2026-10-27.1`); no personal data. The assurance string a business sees is `issuer_signed_credential_device_bound`, `document_and_biometric_match` or `sandbox_simulated`. Viadere makes no NIST SP 800-63 IAL/AAL/FAL equivalence claim.

**Requests (§14.1).** `POST /v1/verification-requests` body (snake_case): `subject_ref`, `capability` (`age.minimum`, `identity.name`, `identity.address`, `identity.verified`), `parameters` (`{"years": 13|16|18|21|25}` for age; none otherwise; unknown parameters rejected), `purpose_code` (snake_case), `callback_id` (the UUID of one of the business's **registered, active** webhook subscriptions that subscribes to `verification.completed`; a URL is never accepted), `expires_in_seconds` (30...600, default 300). Idempotent on `Idempotency-Key` (same key and body: the original, `200`; another body: `409`). Order of checks: capability policy at the business level (key scope, entitlement, tier, kill switch, typed parameters, purpose, law/policy) **before** the customer is resolved; envelope; callback; idempotency; the customer (a foreign or unknown `subject_ref`, or one in the other environment, is a plain 404); at most 3 open requests per business and customer. `GET /v1/verification-requests/{id}` (tenant-scoped, capability-gated) returns `pending` or `completed` + `result_ref`; nothing distinguishes why a request ended.

**Consent and receipt.** The app shows the verified business, the purpose, exactly the disclosed fields, what is not disclosed, the recipient and the expiry. `displayDigest = "sha256:" + SHA-256("VIADERE-VERIFY-CONSENT-V2\n" ‖ canonicalJSON({v:2, requestId, businessId, recipient:{name, handle, verified}, capability, parameters, purpose, disclosure:[{field,title,detail}], notDisclosed:[...], metadata:[...], expiresAt}))`, computed by the shared Core function `VerificationPrompt.renderedDigest()` **in the app from the fields it renders** (the app never echoes a digest the server supplied, and refuses a prompt whose carried digest disagrees with its own content), and recomputed by the server from its record; `POST /v1/verifications/{id}/consent` must quote it (recomputed from the server's record; a mismatch is `409`) and is device-signed. It creates a `DisclosureReceipt` (WP2) for exactly the capability's claim fields, expiring with the request (at most 600 s). The receipt is consumed by the disclosure (`PolicyService.authorizeDisclosure`: policy re-evaluated with the **creating key's current** capabilities and entitlements; a lost race denies the loser). A receipt can be withdrawn until then (`POST .../revoke`).

**Result (AGE-004, acceptance 6).** The disclosure is built by `ClaimsBuilder` from in-memory `EvidenceClaims` (never `Codable`, never stored) and projected through `CapabilityDefinition.project`; `violations(in:)` must be empty before anything is stored **and** again before it is returned. `age.minimum`: `meets_threshold` (only ever `true`), `assurance`, `issued_at`, `expires_at`, `audience` (the business id). A non-positive end is `outcome: not_verified` with `result: {}`. `GET /v1/verification-results/{result_ref}` (`result_ref = "res_" + base64url(HMAC-SHA256(SERVER_PEPPER, "verify-result-ref\n" ‖ request_id))`, 256 bits, derived so the request resource can show it again): business credential and capability required; the result's business must be the caller's (else `404`); `retrieved_at` is set by compare-and-swap (the loser, and anyone later, gets `410`); the payload is erased at once and at expiry (15 minutes); `Cache-Control: no-store`. Webhook `verification.completed`: v1 body `data = {request_id, result_ref}`; the `2026-10-27` envelope (`WebhookEnvelopeV2`: `id`, `type`, `version`, `tenant_id`, `request_id`, `occurred_at`, `result_ref`) for opted-in subscriptions. It fires for every end, including an expiry. **E2EE:** for `identity.name`/`identity.address`, if the business has a valid `hpke-encryption` key in the authenticated key directory, the personal-data fields are sealed to it (`E2EE.seal`, purpose `verify.result`, request id, sender `viadere`, recipient `biz_<business id>`, expiry = result expiry) and returned as `encrypted_result` + `encrypted_result_kid`; Viadere stores only that ciphertext (plus the non-personal fields sealed with the row key). `VERIFY_REQUIRE_E2EE_IDENTITY=true` refuses such requests for businesses without a key.

**Apple Wallet (ADR-05).** Envelope (CBOR, strict, ≤ 128 KiB, exactly these members): `{"algorithm": "APPLE-HPKE-v1", "params": {"mode": 0, "pkEm": bstr(65, uncompressed P-256), "pkRHash": bstr(32), "infoHash": bstr(32)}, "data": bstr}`. HPKE: RFC 9180 base mode, DHKEM(P-256, HKDF-SHA256) / HKDF-SHA256 / AES-128-GCM, `info` = the session transcript, empty AAD. `SessionTranscript = [nil, nil, ["AppleIdentityPresentment_1.0", nonce (bstr), merchantId (tstr), teamID (tstr), pkRHash (bstr)]]`. Checks in order: `pkRHash` equals SHA-256 of one of the server's current/previous encryption public keys (X9.63; SPKI also accepted), `SHA-256(transcript) == infoHash`, HPKE open. Plaintext `{"identity": DeviceResponse}` (exactly one topic). `DeviceResponse`: `version "1.0"`, `status 0`, exactly one document, no `documentErrors`; `docType` `org.iso.18013.5.1.mDL`. Issuer authentication: `issuerAuth` `COSE_Sign1` with `alg` in the **protected** header only (ES256 -7, ES384 -35, ES512 -36; the curve must match the key; EdDSA, RSA and everything else are refused), `x5chain` (33, unprotected, ≤ 3 certificates) validated with RFC 5280 rules at the current time to a configured IACA, then the mdoc profile on the leaf. MSO (`#6.24(bstr)`): `version "1.0"`, `digestAlgorithm` SHA-256/384/512, `docType` equal to the document's, `validityInfo` (`signed`, `validFrom`, `validUntil` as `tdate`; skew 300 s; the document-signer certificate must cover `signed`), `valueDigests`, `deviceKeyInfo.deviceKey` (EC2 COSE_Key). Every `IssuerSignedItemBytes` in the namespaces `org.iso.18013.5.1` and `org.iso.18013.5.1.aamva` must hash (over its exact encoded bytes, tag 24 included) to the listed digest, with unique `digestID`s and element identifiers and `random` ≥ 16 bytes; other namespaces are dropped unread. Device authentication: `deviceSignature` `COSE_Sign1` (detached) over `["Signature1", protected, h'', DeviceAuthenticationBytes]` with `DeviceAuthentication = ["DeviceAuthentication", SessionTranscript, DocType, DeviceNameSpacesBytes]` (empty device namespaces only; MAC is refused). Only the elements the capability's plan names are extracted (age: `age_over_NN`, with `age_in_years` and `birth_date` as in-memory fallbacks; name; `resident_*` address; `issuing_authority` for "has a verified ID"). The merchant encryption key is loaded through `WalletEncryptionKeySource` (KMS-wrapped in staging/production via the `WalletKeyUnwrapper` integration point, a key file for development) and held in memory.

**IACA trust store.** `WALLET_IACA_DIR` (public certificates, `.pem/.crt/.cer/.der`, ≤ 16 KiB, ≤ 512 files, regular files only) filtered by: self-signed, `cA`, `keyCertSign`, EC P-256/384/521, valid now and, when `WALLET_IACA_SHA256` is set (required in staging/production), a pinned fingerprint. Rejections are logged by file name and reason. Optional AAMVA VICAL import is not implemented (it would feed the same directory after its own signature check).

**Didit (ADR-05).** `POST {base}/v3/session/` `{workflow_id, vendor_data}` where `vendor_data` is the attempt id (opaque); the response's `session_id` and `session_token` are kept (the hosted `url` is dropped). Webhook `POST /v1/providers/didit/webhook`: `X-Timestamp` within 300 s; `X-Signature-V2` = hex HMAC-SHA256(secret, canonical JSON: sorted keys by code point, `,`/`:` separators, unescaped Unicode, whole floats as integers) or `X-Signature` = HMAC over the raw body; `X-Signature-V2-Previous`/`X-Signature-Previous` accepted with any configured secret for the rotation overlap; `event_id` deduplicated for 7 days (recorded after successful handling). Handling re-fetches `GET /v3/session/{id}/decision/` and maps it (`DiditDecisionMapper`): approved session whose `session_id` and `vendor_data` are ours, an approved **id verification** (not expired), an approved **liveness** and an approved **face match**; the document's birth date answers the threshold in memory; anything less is not verified, and a liveness `age_estimation` without the rest is recorded as `estimate_only` and never a verified age. Then, always: `DELETE /v3/session/{id}/delete/` with `{"deletion_instruction": "privacy_erasure", "instruction_id": "viadere-<attempt id>"}` and `POST /v3/users/delete/` `{vendor_data_list: [<attempt id>]}`; the result is recorded on the attempt (`purge_status`, `purged_at`) and audited. A provider outage while creating a session fails the attempt (`503` to the app); while fetching it answers `503` to the webhook (Didit retries) and leaves the attempt open.

**Data handling.** `verification_requests`, `verification_attempts`, `verification_results`, `verification_provider_events` (`docs/ops/DATA-INVENTORY.md`): no document data, name, birth date, image, score or provider URL in any table, log or audit event (tests scan all of them after a flow). Audit events are split in two trails (Phase 3 gate F1, below): the business-scoped trail holds only `verification.requested`, `.completed` (capability and `verified`/`not_verified`; nothing else) and `.result_retrieved`; the platform-only trail (no business id) holds `.attempt_started`, `.wallet_verified`/`.wallet_rejected`, `.document_verified`/`.document_rejected`, `.attempt_replayed`, `.provider_unavailable`, `.provider_purged`/`.provider_purge_failed`, `.webhook_rejected`, `.concluded` (outcome, status, reason, label, method, policy version), `consent.disclosure_granted`/`_revoked` and the disclosure-stage `policy.denied`. Maintenance (`VerifyService.runMaintenance`, every tick, also while the gate is off): expiry of open requests, failure of abandoned attempts and deletion of their sessions, purge retries, payload erasure, 400-day record retention. Account deletion removes the person's requests and results.

**Phase 3 (Verify) gate hardening.** Each item below has an exploit-reproducing test (`VerifyGate*Tests`, `MDocVerifierTests`, Core `VerifyTests`/`PolicyTests`).

* **F1, no oracle through the business audit log (AGE-005).** The business-scoped trail carries the same three events for every end of the same polarity (`requested`, `completed` with only `capability` and `outcome`, `result_retrieved`). Attempt, reason, method, consent and policy-denial detail is written **without a business id** (`VerifyService.platformAudit`, `PolicyService.platformOnlyDenials`). An under-age Wallet answer (a verified presentment whose claim is false) used to show as `wallet_verified` next to `completed failure attempts_exhausted`, distinguishable from a decline or an expiry; that is now platform-only. Rows written before the split are hidden or reduced by the projection below. Test: the business audit projection and the tenant export are identical across under-age, declined and expired.
* **F2, no global consumer identifier in any business view.** `BusinessAuditProjection` is the one projection used by the dashboard audit page and the tenant export. A consumer actor is rendered as **that business's `subject_ref`**; a device actor shows no id; the consumer's id wherever else it occurs (subject, metadata) is replaced the same way and `consumer_id`/`device_id`-style metadata keys are dropped. Every current and future event is covered because the projection, not each call site, decides. Test: two businesses' exports for one person share no identifier. Timing remains: a business can see when a request ended (it also sees it in the result's `created_at`); that is not a reason, and is accepted.
* **F3, the Didit purge never gives up silently.** Retries use time-based exponential backoff (30 s doubling to a 24 h cap, `purge_next_at`) and have no attempt cap. A purge still failing an hour after the session ended raises `viadere_verify_provider_purge_overdue` (also `_pending`, `_oldest_seconds` and the counter `viadere_security_events_total{event="verify_purge_failed"}`); alert when the overdue gauge is above 0 for 10 minutes. `DIDIT_NEW_SESSIONS_ENABLED=false` stops new document sessions while the purge client (which needs only `DIDIT_API_KEY`) keeps erasing; removing the key is **not** a switch. **Didit's own retention backstop:** set Didit's data-retention window for the application to the shortest period the account allows, so that if our purge cannot run (key revoked, prolonged outage) Didit still deletes the images, selfie and template itself; record the configured window in the vendor register.
* **F4, jurisdiction rules apply to Verify.** The business's legal-entity jurisdiction (approved onboarding review) is evaluated when a request is created, read and retrieved; the document issuer's country (Wallet: the IACA / document-signer `countryName`; Didit: `issuing_state` mapped from alpha-3 by `CountryCodes`) is evaluated again at disclosure with the business's. `jurisdiction_block` rules **fail closed** for high-sensitivity capabilities (`age.minimum`, `identity.*`) when a jurisdiction is unknown; allow-only rules deny unless every involved jurisdiction is listed. The disclosure-stage denial reason is platform-only (F1).
* **F5, truthful Wallet storage intent.** `identity.name` / `identity.address` are declared to Wallet as `mayStore` (the business receives and may keep them); age thresholds and `identity.verified` stay `willNotStore` (only a boolean is kept). `WalletElementPlan.storageIntent` is the single source. For counsel: Apple's entitlement terms on relaying identity data to third parties.
* **F6, consent bound to what was rendered.** See "Consent and receipt": the digest now covers `recipientVerified` and the disclosure and not-disclosed texts and is computed by the app.
* **F7, conservative age date.** Threshold arithmetic uses the earliest calendar date anywhere (UTC-12, `AgeThreshold.Day(earliestLocal:)`), so nobody is reported as of age while it is still the day before their birthday in some zone. Cost: up to 12 hours of delay for a person in an early time zone. Counsel to confirm for each regulated use.
* **F8, issuer profile.** ISO 18013-5 Annex B: the validated path is exactly IACA → document signer (no intermediates; `issuer_chain_not_direct`); the document signer's `countryName` equals the IACA's, which equals the `issuing_country` element when present (`issuer_country_mismatch`). Apple's Wallet cannot be asked for `issuing_country`, so its absence is accepted.
* **CBOR parser differential.** mdoc CBOR is decoded in strict mode (shortest-form heads only) and duplicate keys are found on the **decoded** key (so a key repeated under a second encoding is a duplicate); the raw-slice reader (`RawCBOR.mapValue`) rejects the same, and the verifier reads every member from one decoded view whose raw and decoded forms must be equal. "First match" and "last match" can therefore not differ.
* **Residual risk: Wallet credential revocation is not checked.** The MSO status list ("where available", ISO 18013-5 §9.1.2.6 / 18013-5 status) is **not** consulted: a credential revoked by its issuer but still within its validity window verifies. Validity windows are short for Wallet IDs but this is a decision, not an oversight: `revocation: notChecked` is recorded in the result's provenance. TODO: fetch and verify the issuer's status list when issuers publish one and Wallet exposes it; until then, regulated uses must not rely on a Wallet result as proof the credential is unrevoked.
* **AGE-007 operator process.** Granting any `identity.*` capability requires a justification (20+ characters) **and** the reference of the documented heightened review (`review_reference`, 4-120 characters), a fresh passkey assertion and an audit event (`EntitlementService.grant`; enforced for `identity.verified` as well as name and address).


### 2.70 Business onboarding and ongoing assurance (WP6, spec §8.1; `Server/.../Platform`)

**State machine.** `OnboardingStateMachine` (pure, `Platform/Onboarding.swift`) takes events and refuses any that is not valid from the current facts, so no client can skip a stage by calling a later action first. Facts: `domainVerified`, `legalEntity` (`none|submitted|approved|rejected`), `enhanced` (`not_required|pending|approved|rejected`, sensitive categories `banking`, `healthcare`, `government` start `pending`), `identityVerified` (the operator's approval of the application: handle and permanent code), `contractsCurrent`, `sandboxKey`, `testCustomer`, `testEvent`, `securityContact`, `goLive` (`none|requested|approved|rejected`). Stage = first incomplete of `control, identity, contracts, integration, goLive, live`. A go-live **request** is blocked until control, contracts, a sandbox key, a test customer, a test event and a security contact all exist; an operator's **approval** additionally needs the approved application and a request. Access is decided by `OnboardingGate`, never by the stage name: a *pending* business may hold **test** keys once its domain control is verified and never live keys; a *verified* business may hold live keys only after the go-live approval (businesses that predate WP6 are grandfathered with go-live recorded as approved by `system:wp6-migration`); suspended and revoked businesses have no key access. A category label is never the sole access decision (spec 8.2): the legal-entity review is required of everybody and the extra review of the sensitive categories adds to it.

**Control of the domain.** The business adds a domain; the server gives it a random token. Proof is either a DNS TXT record at `_viadere-verify.<domain>` with value `viadere-verification=<token>` or the same value at `https://<domain>/.well-known/viadere-verification.txt`. The DNS lookup is DNS-over-HTTPS to a fixed DNSSEC-validating resolver; the file fetch uses the webhook SSRF defences (https only, no redirects, address vetted and pinned, 4 KiB body cap, short timeouts). A domain already verified by another business is refused (the answer does not say who). **A resolver outage is never evidence**: `unavailable` is a different outcome from `notFound`. Verified domains are re-checked every `DOMAIN_RECHECK_DAYS`.

**Legal entity.** The business submits a registry number, jurisdiction, registry name and one to five references to its evidence (a registry URL or record id). **No document is uploaded or stored.** An operator records approve or reject with a note; the evidence stays where it was checked.

**Ongoing assurance (`OnboardingAssurance`).** For every business with an approved go-live: domain control is re-checked and every required contract must be accepted at its current material version. A failure starts a grace period (`ASSURANCE_GRACE_DAYS`, default 14; the owners are mailed with the deadline); if it is not fixed by then the system suspends the business (`business.suspended` by `system:assurance`). Fixing it lifts **only** a suspension the assurance itself caused; an operator's suspension stays until an operator lifts it.

**Audit.** Every transition is `onboarding.<event>` with the actor (business user, operator or system) and the stage reached.

### 2.71 Contract acceptance (WP6, spec §8.1 step 4, §9.3)

`LegalCatalog` lists the documents a business accepts, each tied to a public page of `Site/content/legal/<slug>/` by **slug and version** (a test compares the catalog with the page front matter, so the catalog cannot drift from what is published). Required of every business: Business Services Agreement, Data Processing Addendum, Acceptable Use Policy, Messaging Consent and Content Policy Addendum; the MFA and Approval Services Addendum for Tier A, the Verification Services Addendum for Tier V. Acceptance (`POST /dashboard/compliance/accept`) needs the right `acceptContracts` (Owner, Organization Admin), an explicit confirmation, and the **current catalog version** (a stale form is `409`; "latest" is never recorded). The record holds who, when, which version, and **versioned-pepper hashes** of the client address and agent string (the raw values are never stored); it is created once per (business, slug, version) and audited `contract.accepted`. **Re-acceptance on material change:** a document has `version` and `materialSince`; an acceptance of `materialSince` or later stays valid across editorial bumps, an older one no longer counts, the business drops out of `contractsCurrent` and, once live, gets the assurance grace period. Customer-consent language and verification purposes are versioned and re-approved the same way (WP2/WP3).

### 2.72 API keys (WP6, SEC-API-001..003; `Security/Tokens.swift`, `Security/APIKeyLifecycle.swift`)

**Format.** `vdk_<test|live>_<kid>.<secret>`: `kid` is 16 lowercase hex characters (64 random bits, **non-secret**, unique, indexed, shown in the console, logs and audit trail); `secret` is 43 base64url characters = **256 bits** from the system CSPRNG. The environment is in the prefix **and** in the stored record, and the prefix is part of the verifier, so relabelling a test secret as live finds nothing. Keys issued before WP6 (`vdk_<env>_<43 chars>`, no dot) keep working and are looked up by their hash; they have no `kid` (shown as prefix and last four).
**Storage and verification.** The server stores `SHA-256(whole key)` (a fast hash is sound for a 256-bit random secret) and the `kid`. Lookup is by `kid`, then a **constant-time** comparison of the hash. An unknown `kid`, a wrong secret, a revoked or expired key, an out-of-range address and a missing certificate all give the same `401`.
**Shown once.** The secret appears only on the creation or rotation page (`Cache-Control: no-store`), after a fresh passkey assertion (SEC-API-004). It is never in the listing, the audit trail, a mail, a log or an export.
**Properties.** Scopes and capabilities (bounded at use time by entitlements); tenant and environment binding; optional expiry (30, 90 or 365 days; any other value is refused, never treated as "no expiry"); `last_used_at` and a hash of the last caller's address (updated at most every 5 minutes); immediate revocation (compare-and-swap, idempotent); an **IP allow-list** (up to 20 addresses or CIDR blocks, IPv4 and IPv6; the client address is the hop the trusted proxies appended, never the one the client wrote; denials are audited at most once per key per 5 minutes without the address); optional **certificate binding** (section 2.74); at most 25 active keys per business.
**Overlap rotation.** `Rotate` issues a replacement with the **same** scopes, capabilities, restrictions and expiry (it never widens anything) and ends the old key after the chosen overlap (none, 1 hour, 1 day, 7 days or 30 days, capped by `API_KEY_MAX_OVERLAP_DAYS`). Both work during the overlap; the old key is refused from the instant `auto_revoke_at` passes (checked on every request) and the job stamps `revoked_at` (`apikey.auto_revoked`). A key that is already rotating cannot be rotated again.
**Who.** `manageAPIKeys` (Owner, Organization Admin, Developer, Security Admin) creates and rotates within the messaging baseline; a scope or capability beyond it needs `elevateKeyScope` (Owner, Security Admin) (section 2.75). Revoking needs no step-up (it is protective). **Operators** can revoke one key or all keys of a business **without suspending it** (G-3, `apikey.revoked_by_operator`; the organization is mailed, the mail names no secret).
**Audit.** `apikey.created|rotated|revoked|revoked_by_operator|auto_revoked|ip_denied|mtls_denied`, each with the `kid`, never the secret.

### 2.73 Webhook endpoints (WP6, SEC-API-006, spec §9.3; `Services/WebhookOwnership.swift`)

**Ownership before activation.** In staging and production (`WEBHOOK_OWNERSHIP_VERIFICATION` cannot be `off` there) a new endpoint receives **no event** until it proves it controls the URL: the server POSTs a signed `webhook.verification` request whose body holds a fresh random single-use `challenge` (256 bits; only its hash is stored; valid 10 minutes) and the endpoint must answer 2xx with `{"challenge_response": hex(HMAC-SHA256(signing secret, "viadere.webhook.verification.v1:" + challenge))}`. A plain echo of the challenge (or of the request) is refused: only a receiver holding the endpoint's signing secret can answer (L4 of the platform gate). Every attempt uses a new challenge and spends it, so a stale proof can never verify a later attempt; attempts are limited to 6 per endpoint per hour. Failures are reported as `no_echo`, `http_<status>` or `unreachable`. This stops a registrant pointing events at a third party's URL. Console: Verify; API: `POST /v1/business/webhooks/{id}/verify` → `{verified, failure?}`.
**Headers on every delivery** (verification and test included): `Viadere-Signature` (as section 2.6), `Viadere-Event-Type`, **`Viadere-Delivery-Id`** (the delivery's own id; unique per delivery and stable across retries, the receiver's de-duplication key), **`Viadere-Key-Id`** (`whk_<first 8 hex of the endpoint id>_v<secret version>`; the version increments at each secret rotation, during the 24-hour overlap the signature header carries both secrets' `v1=` entries), `Viadere-Webhook-Version` (`v1` full body, `v2` opaque envelope, section 2.56).
**Tools.** `POST .../test` queues a signed `webhook.test` event through the normal worker (rate limited, refused for an unverified or paused endpoint); the console's retry simulator shows the real backoff table (30 s, 2 min, 10 min, 1 h, 6 h, 12 h, 24 h, then dead letter) without sending; the schema preview shows a sample of every event, built from the real types, with no customer data.
**Pause (G-5).** `POST .../pause {reason?}` and `.../resume` per endpoint (scope `webhooks:manage`); an operator can pause one business or everyone (`platform_flags`). Queued deliveries stay queued, are neither sent nor dead-lettered, go out after a resume, and expire with the retention period.

### 2.74 Origin lock and Tier E client certificates (WP6, SEC-TR-005, ops G-10)

**Origin lock.** `EDGE_TOKEN` (required in staging and production; `EDGE_TOKEN_PREVIOUS` during rotation; at least 32 printable characters) is the value Cloudflare adds as `X-Viadere-Edge-Token`. `EdgeLockMiddleware` sits before routing, authentication and any database access: a request without it, or with a value that is not equal in constant time to a configured token, gets `421`. The only exemption is `GET`/`HEAD` of `/healthz` and `/readyz` from Fly's private network with **no** proxy header (a request through Cloudflare or Fly's proxy always carries one), so a public request can never use it. Configuration refuses to boot staging or production without the token.
**Trust follows the lock.** Headers Cloudflare sets (`CF-IPCountry`, the client-certificate headers below) are believed **only on a request that passed the lock**. Where no lock is configured (development, tests) none of them is trusted.
**Client certificates.** Cloudflare API Shield mTLS on the enterprise API hostname verifies the certificate and forwards `X-Viadere-Client-Cert-Verified: true`, `X-Viadere-Client-Cert-Sha256` (64 hex) and optionally `X-Viadere-Client-Cert-Issuer-Ski` (the Cloudflare rule is in `Infra/terraform/cloudflare.tf`). A tenant with Tier E binds **leaf fingerprints** or **CA subject key identifiers** (`business_mtls_certs`; one fingerprint belongs to one tenant, the answer for a duplicate does not say whose; expired or revoked entries are ignored). A key with `requires_mtls` (or any key of a tenant that turned the requirement on) is refused unless the request passed the lock **and** presents a verified certificate bound to **that tenant**; a key bound to one certificate (`cert_binding`) refuses every other certificate of the same tenant. mTLS adds a factor: the API key still authenticates and every authorization check still applies; private networking does not bypass application authorization (SEC-TR-005). Requiring mTLS for a key needs Tier E and an active bound certificate (a key nobody can use is a mistake).
**Not done in code.** Fly's proxy cannot verify client certificates, so the Cloudflare → origin leg is protected by the edge token, not by Authenticated Origin Pulls at the origin; the alternatives (a raw-TCP Fly service with app-terminated TLS, or Cloudflare Tunnel) are documented in `Infra/fly/README.md` and tracked as G-11.

### 2.75 Console roles, step-up and separation of duties (WP6, spec §9.2; `Dashboard/DashboardRoles.swift`, `docs/ops/CONSOLE-ROLES.md`)

Nine roles (`owner, org_admin, developer, messaging_operator, verification_admin, security_admin, analyst, billing_admin, auditor`) over the permissions of `DashboardPermission`; the matrix in code is the single source and is embedded in `docs/ops/CONSOLE-ROLES.md` by a test that fails on drift. Permissions are checked server-side on every request against the **current** membership (a demotion or removal acts on the next request). Existing `admin` becomes `org_admin` and `support` becomes `messaging_operator` in the data migration; old names are still accepted from stale forms. **Separation of duties:** nobody grants a role to themselves; only an Owner creates Owners, Organization Admins or Security Admins; widening a credential's scope (`elevateKeyScope`) is Owner or Security Admin, and those two coincide with the people-managers only in the Owner; the last Owner cannot leave. **Step-up:** creating or rotating a key, granting roles, going live, retention, deletion, mTLS, IP lists, two-person settings need a passkey assertion from the last few minutes **and** the organization's privileged-inactivity limit (default 5 minutes, 1 to 15) not exceeded since the last request (`ReauthRequired`). **Two-person approval** (optional): key creation, key rotation and role grants wait as a pending change (sealed payload, no secret) until a *different* member with `approveChanges` approves (a request that widens scope needs an Owner or Security Admin); only the requester completes an approved key request and sees the secret; the stored request is what is issued; single use; expires after 24 hours. **Sessions:** the console lists sessions (masked address, device label, country; hashes only), revokes one or all others, alerts the person (and subscribed security contacts) when the device, network or country is new, enforces an optional IP allow-list that cannot exclude the administrator who sets it, and ends sessions after the idle and absolute limits.

### 2.76 Operator switches and notices (WP6, OPS-006; `Operations/PlatformFlags.swift`, `docs/ops/KILL-SWITCHES.md`)

`platform_flags` holds maintenance mode, sign-up stops, webhook pause, the emergency messaging restriction and runtime abuse thresholds; each change needs a fresh passkey assertion and a recorded reason and is audited with the operator as actor. Values are validated when set (a message restriction cannot name an unknown channel, cover the security purpose or clamp above 600 per minute; abuse thresholds stay inside fixed bounds, so the checks can be tightened but never disabled). The emergency messaging restriction never covers security-purpose traffic (sign-in and payment approvals), which is stopped with a capability switch or a suspension. Consumer freeze (G-7) revokes every token and device in one transaction after the person has been notified, and unfreezing restores the status only. Operator notices are queued and delivered in batches by the job.

### 2.77 Retention, legal holds, the append-only gate and the audit-head export (WP6, LEG-PR-006, OPS-004)

**Retention by class** (`docs/ops/DATA-INVENTORY.md` section 7): 14 classes with a default and hard bounds; the purge is idempotent, batched and independent per class. A business may only *shorten* adjustable classes for its own data; an operator moves the platform value inside the bounds with a reason. A **legal hold** (global, one business or one consumer) suspends every holdable class for its scope.
**Append-only tables.** `audit_events`, `decisions` and `consent_grants` refuse UPDATE and DELETE at the database. The retention job deletes through `RetentionDeleteGate`, a transaction-scoped exception for DELETE on those three tables only (`SET LOCAL viadere.retention = 'on'` in PostgreSQL; a one-row gate closed again by the same transaction in SQLite). UPDATE is refused everywhere. A process that can run arbitrary SQL as the runtime role can open the gate; protection against that is the write-once head export below, and the role split (the runtime role holds DML only, `REVOKE UPDATE ON audit_events`).
**Audit retention** deletes only events older than the period **and** covered by an exported signed head; the last removed event's sequence and hash stay in `audit_checkpoints`, and `verifyChain` continues from there. Without an export target nothing is purged.
**Audit-head export** (`AuditHeadExporter`): on a schedule (`AUDIT_HEAD_EXPORT_INTERVAL_HOURS`) the signed head (`{seq, hash, occurredAt, exportedAt, keyEpoch, mac}`, MAC under the chain key epoch) is written, with an HSM signature over its SHA-256 (`AUDIT_HEAD_KMS_KEY`, **required in production**: the server refuses to start there without the export and the key; optional in staging; workload identity federation: the Fly OIDC token is exchanged at Google STS, impersonates a service account that can sign and create objects, nothing more; no key file exists), to a **create-only** object (`ifGenerationMatch=0` / `If-None-Match: *`) in a bucket with a **locked retention policy** (`Infra/terraform/audit_bucket.tf`; `is_locked` defaults to true for production) or an R2 object-lock bucket. The mark of the last success is stored only after the upload succeeded, and the export-age gauge alerts when it is old.
**Database roles.** `DATABASE_MIGRATION_URL` (the schema owner) is used only by `ViadereServer migrate` (the Fly release command); the serving processes use `DATABASE_URL`, a role with DML only (`GRANT` to `DATABASE_APP_ROLE`, `REVOKE CREATE ON SCHEMA public`). With the migration URL configured, a staging/production process whose runtime role can create objects or owns tables refuses to start.

### 2.78 Rights workflows (WP6, LEG-PR-004; `Operations/ConsumerExport.swift`, `Operations/TenantRights.swift`)

**Consumer export.** `POST /v1/account/exports {recipientKey}` (device-signed, a trusted app device: not an App Clip, not inside its cool-down) creates a job; `recipientKey` is a **fresh P-256 key-agreement public key the app generated for this export** (the private key stays in the device's Keychain until the file is read). The job builds the account's data as one JSON document (`viadere-export-v1`: account, devices, masked phone numbers, relationships, consents, interactions, decisions summary, messages, loyalty, security notices; **no secrets, no hashes, no signatures, nothing about other people**), splits it into 48 kB chunks and seals each to the key with HPKE (section 2.50, purpose `account-export`, request id = export id, sender `viadere`, recipient `device-<device id>`, 7-day expiry). The server stores ciphertext only; the device is told by a generic push; **nothing is sent by e-mail** (accounts have no address). Only the requesting device of the same account can read the status or download (any other caller: `404`), at most 5 downloads, 3 exports per day, one at a time; the bundle is erased at expiry. Audit: `account.export_requested|ready|downloaded`.
**Tenant export and deletion.** An Owner or Organization Admin asks for an export (after a fresh passkey): profile, team, credential *metadata*, webhooks, domains, agreements, settings, audit events and usage totals; **never a secret and never customer-level data**; sealed at rest, downloadable for 24 hours with `Content-Disposition: attachment` and a sandboxing CSP, then erased. Deletion is requested by an Owner by typing `DELETE`, reviewed by an operator, and on completion revokes the keys, deletes webhooks and deliveries, removes and signs out the team, deletes domains, certificates, contacts and support text, and ends the business; handles and codes stay reserved. Distinction (LEG-PR-004): deleting server data is not the revocation of a credential held by a third party.

### 2.79 Key rotation (WP6, ops G-8; `docs/ops/KEY-ROTATION.md`)

Ciphertexts and exported heads name their key (`v3.<id>.`; the audit epoch is inside the chain MAC; connect-link context names its key id). Configuration: one current key plus previous keys by id, validated at start. `rotate-data-key` re-seals every registered column under the current key (a test keeps the registry complete); `verify-data-key --require-current` proves nothing remains under another key; both are idempotent and safe while serving.

### 2.80 WP6 residual risks and limits

1. **Pepper rotation.** `SERVER_PEPPER` is versioned, but the existing lookup hashes (`hmacHex`: phone, dashboard e-mail, recovery, OTP, codes) are single-valued indexes: rotating the pepper invalidates them and there is no automatic re-hash; the webhook `tenantId`, the CSRF derivation and Wallet pass tokens also derive from the pepper and change with it, and a rotation does not protect hashes created before it (KEY-ROTATION.md section 3, RISK-REGISTER R-043). New hashes that must survive a rotation use `versionedHex`.
2. **Retention gate.** Anyone who can run SQL as the runtime role can open the append-only gate; the head export and the DML-only role bound the damage, and the export detects it.
3. **Origin lock is a shared secret** (G-11 open): it proves the request came through *a* Cloudflare configuration holding our token, not that the TLS peer was Cloudflare. Rotate it (`EDGE_TOKEN_PREVIOUS`) after any suspected disclosure.
4. **Migration URL on Fly.** Fly secrets are app-wide, so `DATABASE_MIGRATION_URL` is present in the serving machines' environment; the server reads it only in the `migrate` command, but a code-execution compromise of a serving machine could read it. Mitigation: `migrate` now refuses to run without the URL and serving processes refuse to start if their login can change the schema (the split is mandatory), and Infra/fly/README.md 1a describes the separate release app that keeps the secret off the serving machines; until an app is moved to it, this risk stands for that app.
5. **Domain control is weak evidence** for a shared or compromised domain; it is one factor beside the legal-entity review and the go-live review, not a replacement for them.
6. **Legal-entity evidence is by reference.** An operator checks a registry, nothing is stored; the quality of the check is a process control (RB-2), not a technical one.
7. **Operator notices** to all consumers are generic pushes to devices that have a token; a person without the app is not reached (accounts have no address).
8. The consumer export file, once the person saves it, is plaintext in their hands; the screen says so.
9. **Not built in code (needs real infrastructure):** the Cloudflare API Shield mTLS rule and certificates, the locked audit bucket and the HSM key (Terraform in `Infra/terraform`, not applied), the Fly secrets, Authenticated Origin Pulls at the origin (G-11), alert rules on the metrics and a monitoring destination for them.
