# ADR-0022: Push MFA — number matching, transaction binding, fatigue controls, passkey bias and the watch tier

- **Status:** proposed (2026-11-02); revision 3 (2026-11-02): grouping with number-selected requests and `session_handle`-only supersession (S2-A2-9, §5.2); destination failures excluded from the pause (S2-A2-10, §5.4); revision 2 (2026-11-02): budgets limit alerting, not availability (S1-A2-6); `ApprovalResult` v2 member set and downgrade-proof verifier (S1-A3-08, -09); number-field and prominence rules (S1-A9-3, -4); notification actions, offline, Android, watch and Live Activity rules (A6/A7 findings 1-4, 7-11, 15)
- **Spec reference:** §3, §5.2, §7, §7.2, §8 (watchOS, Wear OS), §14.1 (watch tier), §18, §20, §26 (replay, flooding); owner decision 4
- **Related:** ADR-0006 (pairwise keys), ADR-0007 (E2EE), SECURITY §2.53-§2.58 (Approve v2), ADR-0020, ADR-0023; findings F-05, F-12, F-14, F-15, F-16, F-25
- **Review:** A1, A2, A3 (JWS change), A6/A7 (feasibility), A9 (copy and layout)

## Context

Approve v2 already gives a device-signed, transaction-bound, pairwise `ApprovalResult` JWS that the business verifies against a key it enrolled (SECURITY §2.54), plus fatigue counters, freeze and report (§2.57). It is gated off in staging. There is no number matching (F-05). The legacy `authenticate`/`authorize` interaction path is decided on relay status and is not independently verifiable (SECURITY §2.58 residual 9). The approve push uses an unregistered category and no request id (F-15); the low-assurance approve action can dead-end (F-14); Deny is visually weaker (F-16). Decision 4: pilot is passkey-biased, with transaction-bound push MFA with number matching and payment step-up.

## Decision

### 1. Push MFA is Approve v2

`POST /v1/business/auth-approvals` creates an Approve v2 request (existing semantics, SECURITY §2.55) and an auth-delivery record of method `push_approval` for unified status and events. The business verifies the `ApprovalResult` JWS itself; the relay's status never suffices. This keeps F-12's privacy rule (the business never receives the global device id) because pairwise keys are per business (ADR-0006).

### 2. Number matching

1. **Code.** The business generates `match_code`: 2 decimal digits (`10`-`99`) for `capability = auth.challenge` at risk `low`/`medium`; 3 digits (`100`-`999`) for `transaction.approve` and any `high`/`critical` request. CSPRNG with uniform rejection sampling (no modulo bias; SDK vectors); never `00`-`09`-style leading zero to avoid entry ambiguity.
2. **Carriage.** In E2EE requests, `number_match: {digits, code}` is a member of the business-signed `ApprovalRequest` (inside the envelope; the relay cannot read or change it). In server-visible requests it is a request field; the relay can read it, which is acceptable because number matching defends against fatigue, not against the relay (THREAT_MODEL T-MFA-1, R-12).
3. **Display.** The business shows the code on the screen where the sign-in or payment started (its web page or app). The phone **never displays the code**: the approval screen asks for the number with a field labelled "Number on {Business}" and the helper "No number there, or someone gave it to you? Tap Deny." (UX_COPY S-MFA-01). Approve is disabled (not hidden) until the field has the right length. Field behavior (S1-A9-3, A6/A7 finding 15): numeric keypad; `textContentType` unset and no `oneTimeCode` suggestions; AutoFill and paste disabled (the field refuses pasted text); never prefilled; Android screen `FLAG_SECURE` and `setHideOverlayWindows(true)` (API 31+); a wrong entry is announced to VoiceOver/TalkBack as an accessibility announcement, not by color only; focus lands on the title when the sheet opens and the number field is the first control.
4. **Check.** The device compares the entry with the code in constant time. Up to 3 wrong entries per request (local counter, also reported as `invalid_match_attempts` in the result); the third makes the device submit a signed `decision: "deny"` with `deny_reason: "number_mismatch"`, which counts toward the pause rule (§5). The JWS carries `match` (the entered string) so the business verifies it against its own record. The local counter is a usability control; the business verifier accepts at most one result per challenge (the existing `aud‖kid‖challenge` consumption) and treats `invalid_match_attempts` as advisory. For authority flows (link service, OIDC app path) the authority counts signature-valid wrong-`match` assertions itself (ADR-0023 §3 step 6, S1-A3-05). Lock Screen and notification never show the code, amount or payee.
5. **Equal-prominence Deny (testable definition, S1-A9-4).** Deny and Approve are one design-system component with identical height, width, type size, weight and contrast ratio, in a neutral palette (no red or "destructive" style on Deny, no filled Approve); **Deny first** in layout and reading order; side by side until text would truncate, then stacked with Deny on top; Approve disabled (not hidden) until the number is complete. "This wasn't me" is a full-width secondary button (minimum 44 pt) inside the pinned footer, not a link, with the line "Deny says no. This wasn't me also reports it." Brand kits cannot restyle any of them (existing rule). **No slide-to-approve** (or any single-gesture approve) for any flow in this program; the existing `ApprovalSheet` slider is removed for auth and payment items in Stage 4. Unique Voice Control names "Deny", "Approve", "This wasn't me"; Switch Control works without gestures (spec §7.2, §20; fixes F-16).
6. **Same-device sign-in** (business app on the same phone): the person switches apps to read the number. This is a known usability cost; the SDK recommends passkeys for same-device flows (§6).

### 3. Transaction binding: `ApprovalResult` v2

Additive version bump of SECURITY §2.54 (Core change with the SDK verifier updated in the same change):

- **Exact member set (S1-A3-09).** Required: every v1 member, with `v = 2`. Optional, each with its format and presence rule: `match` (decimal string of 2 or 3 digits; present **iff** the request carried `number_match`), `deny_reason` (`number_mismatch` \| `not_me` \| `destination_unverified`; present only when `decision ∈ {deny, report}`), `invalid_match_attempts` (integer 0-3; advisory). The verifier checks `keys ⊆ required ∪ optional`, `required ⊆ keys` and the presence rules; anything else is refused. Canonicalization, header allow-list and `exp − iat ≤ 600` (devices sign 300) are unchanged.
- `authentication` details gain `match_digits` (2 or 3) so `txn_digest` covers that a number match was required (a relay cannot strip the requirement in server-visible mode without breaking the business's digest check).
- **Downgrade-proof verifier API (S1-A3-08).** `ApprovalExpectation` (Swift, TypeScript, Kotlin) gains a **non-optional** `numberMatch: .notRequested | .required(code)` with no default value; every initializer requires it. `.required` means `v == 2`, `match` present, constant-time equality; `.notRequested` means `match` absent, v1 or v2 accepted. Cross-language vectors include "number-matched request, v1 result" and "v2 result without `match`" as refusals.
- Replay: unchanged (`aud‖kid‖challenge` consumed once by the business; relay CAS).

### 4. Payment and high-value step-up

1. `capability = transaction.approve`, displayed `transaction {currency, amount_minor, payee_display, transaction_reference}` (existing), 3-digit number matching, `amr = biometric` (key `approvalBiometric`, `.biometryCurrentSet`), D1 device not in cool-down (existing).
2. `txn_digest` binds amount, currency, payee and reference (existing); any change fails the business's check.
3. **High and critical requests must be E2EE** (business-signed, ADR-0007) in the pilot configuration; server-visible high/critical requests are refused with `422 e2ee_required`. This removes relay prompt injection for payments (SECURITY §2.58 residual 6).
4. Secure Payment Confirmation (W3C) is not adopted in the pilot; recorded as a Phase B option for businesses with WebAuthn.

### 5. Fatigue and bombing controls

1. **Budgets limit alerting, not availability (S1-A2-6).** Per-relationship counters (window 1 h) and the per-subject budgets of ADR-0020 §8: from 3 requests the app shows the fatigue warning (S-MFA-08) and keeps the existing "I started this myself" acknowledgement before Approve is enabled; **above 6 per hour (or over any per-subject budget) the newest request is still created and collapsed, but delivered silently** (no alert push; inbox only, with the inbox line "You have a pending sign-in from {Business}"), so a person who is actively signing in opens the app and finds it. `429` is reserved for per-tenant aggregate floods (ADR-0020 §8). Nothing is refused or cancelled because of a per-subject count (revision 3 removes revision 2's "oldest is superseded" rule, S2-A2-9). Pause after 3 denials, reports or number-mismatch denials is unchanged (§5.4); a request that arrives while paused is not alerted and leaves an inbox item S-MFA-13.
2. **Grouping, not supersession (S2-A2-9).** Revision 2 let a new request for the same (tenant, subject) cancel the open one, so an attacker who triggered sign-ins at the business's throttle rate kept cancelling the victim's genuine prompt. Revision 3:
   1. **Supersession only within one initiating session.** The business may send an optional `session_handle` (1-64 characters `[A-Za-z0-9_-]`, an opaque value the business derives from its own initiating session, for example an HMAC of its session id; never shown to the person; class T). A new request supersedes an open one **only** if both carry the same `session_handle` for the same (tenant, subject). A request without `session_handle` never supersedes and is never superseded. An attacker cannot know the victim's session handle, so it cannot cancel the victim's request.
   2. **The typed number selects the request.** All open approval requests of one business for this person form one **group**. The app shows one approval screen per group ("Sign-in request from {Business}", plus "{n} open requests from {Business}" when n > 1, UX_COPY S-MFA-14) with one number field. The device compares the typed number in constant time with the code of **every** open request in the group: exactly one match → that request is the one approved and signed; the relay then cancels the group's other open requests (`superseded`) after it accepted the signed result. Zero matches → a wrong entry (3 per group, then a signed `number_mismatch` deny of every open request in the group, counted as **one** denial). Two or more matches → nothing is signed; the app shows S-MFA-15 ("This number matches more than one request. Start again on {Business} to get a new number."). Deny or This wasn't me on the group screen answers every open request in the group and counts as **one** denial or report toward the pause.
   3. **Alerts.** A request that joins a group that already has an open request does not alert again (the existing notification is updated with the count), and over-budget requests are silent as in §5.1.
   4. **Bound.** With k attacker requests open in the group, a victim's number collides with probability about k/90 for 2-digit codes (k/900 for 3-digit); a collision costs a retry and never approves the attacker's request. Residual R-20 is narrowed to that: an attacker can make the victim retry, not cancel the victim's prompt. The business's own trigger throttling (per client IP and per account, business guidance and SDK helper) and the per-tenant limit still bound k.
   5. ST-MFA-10 (A2): while an attacker creates a request every N seconds at the business's throttle rate (no `session_handle`, or a different one), the victim's own sign-in is still completable within its expiry, and no attacker request is ever approved.
3. **"This wasn't me"** = signed `decision: report` with `deny_reason: not_me`: counts as a denial, creates a security notice, an operator-visible event, and the business sees `report` in the verified result.
4. **No indefinite attacker-controlled lockout:** denials with `reason: destination_unverified` (ADR-0031 §4) and destination checks that end without a server call never count toward the pause. A pause applies only to that business and that customer, lasts at most 1 h, and the customer can lift it at once in the app with a biometric proof (existing `ApproveFreezeProof` pattern, action `unpause`). Other businesses and the customer's own app sign-in are never affected.
5. **Push (A6/A7 findings 1, 9, 11; S1-A9-8).** Category `viadere.approve` registered at launch with actions **Review** (`.foreground`; iOS unlocks first, so Review always needs unlock) and **Deny** (no `.authenticationRequired`, no `.foreground`: works on a locked device after first unlock and signs a reduce-only deny with the `request` key). There is no Approve action and no Report action on approval notifications (report is on the screen). A Core test asserts the option set per action. The payload carries the request id `req` (fixes F-15); approve always foregrounds the app (fixes F-14); `apns-push-type: alert`, `mutable-content: 1`, `apns-collapse-id` = request id. Interruption level **`active`** for every auth and payment notification; `timeSensitive` is never used. `hiddenPreviewsBodyPlaceholder` = "You have a security item." for all auth categories; `.hiddenPreviewsShowTitle` is not set. A Settings option "Show business names on the Lock Screen" (default: follow the system setting) makes the NSE keep the generic N-01 text when off. No flow depends on silent (`content-available`) pushes.
6. **Offline Deny (A6/A7 finding 2).** No queued security decision exists. A Deny from a notification is attempted once within the action's background window; if it cannot be sent, the app posts a local notification "Deny not sent yet. Open Viadere." and keeps the item in the inbox; the business sees `pending` until expiry. Approve needs the network at the screen and is never queued; the app shows "Approved" only after the relay accepted the signed result (S1-A9-2). Before first unlock after a reboot the `request` key is unavailable; the action then fails the same way.
7. **Live Activities (A6/A7 finding 10).** No Live Activity is started for `push_approval`, `payment`, link or code deliveries; a Core test asserts `LiveActivityPolicy` returns not eligible for every method kind in the auth taxonomy (ST-UX-05).

### 6. Passkey bias

- Viadere does not replace the business's passkeys. The business SDKs' `recommendStepUp(context)` helper returns, in order: (1) the business's own WebAuthn passkey when the customer has one on this device or via hybrid transport (origin-bound, phishing resistant); (2) Viadere push with number matching; (3) delivery-only methods (link, code) only when the business's policy allows, with the downgrade recorded in the business's own audit and in `auth.delivery.fallback_used`.
- For Viadere's own OIDC provider, passkey is offered first and is the only method that yields `urn:viadere:acr:passkey` (ADR-0024 §5).
- Copy and docs never call push approval phishing resistant (spec §6.5, §18).

### 7. Legacy interaction path

From pilot start: no new legacy approval entitlements (SECURITY §2.58 residual 9) may be granted; existing ones keep their expiry (sunset 2027-06-30). The pilot release gate requires zero active legacy entitlements in staging (THREAT_MODEL ST-GW-08) so no ordinary workload can produce an authentication success that a business accepts on relay status alone (§27).

### 8. Watch tier (spec §14.1 open question, decided here)

| Surface | Allowed for auth/payment items | Why |
|---|---|---|
| watchOS (phone-mediated, no keys on the watch; existing `WatchSync`) | view business and purpose; **Deny**; **This wasn't me** (report, signed on the phone with `deny_reason: not_me`). No Approve. Shows "Approve on your iPhone." | The watch holds no key; any watch approve would be signed by the phone's `request` key without user verification (assurance `none`), below every auth requirement; number entry and Face ID live on the phone. Fixes F-25 (watch sends deny where report is meant). |
| Wear OS (bridged notifications only) | same rule; bridged notifications use the phone's Deny action (no `setAuthenticationRequired`), `setLocalOnly(false)` explicitly, and never define an Approve action, including as a wearable extension | Device capabilities and biometric policies vary (spec §8); standalone Wear needs a new ADR |
| Non-security items (confirm/choose, low) | unchanged existing behavior | not in scope |

Watch routing (A6/A7 finding 7): a mirrored iPhone notification's action may be delivered to the watch app once a watchOS app is installed (**verify on device, Stage 4**). The watch app therefore implements `UNUserNotificationCenterDelegate`, forwards Deny/Report to the phone with `WCSession.sendMessageData` (needs a reachable iPhone) and never signs locally; if the phone is unreachable it shows W-05 ("Couldn't reach your iPhone. Open Viadere on your iPhone to deny."). "Review" on a mirrored notification opens the watch app, not the phone app, so the watch long-look shows W-02 as its first line. A test asserts `WatchSync.handle` refuses approve for `authenticate`/`authorize`.

Classification: watch = **W0 "notification surface"**, never an authenticator; it can only reduce (deny/report). This is stricter than spec §8's "low- to medium-risk with paired-device trust" (allowed, not required) and is recorded as a deliberate choice; revisiting it needs a new ADR with a watch-resident key design.

### 9. Android notification and key design (A6/A7 findings 3, 4, 13)

1. **FCM data-only, high priority.** The server sends data-only FCM messages (`android.priority = high`, payload `{adl}` or `{req}` only, no `notification` block). In `onMessageReceived` (about 10 s) the app immediately posts the generic N-01 notification, then fetches the display object with expedited WorkManager and updates the **same notification id** with the enriched content; if the fetch fails, N-08 stays. Every high-priority message produces a visible notification (avoids deprioritization). Data messages are not delivered to force-stopped apps and OEM battery managers can delay them: the inbox and the E-06 banner are the fallback, and Help gains a "battery optimization" item.
2. **Permission and channel.** `POST_NOTIFICATIONS` (Android 13+) is requested with the same priming screen as iOS. A dedicated channel `security` with importance HIGH is created at first launch (channel importance cannot be raised later). Notifications use `setVisibility(VISIBILITY_PRIVATE)` with a generic `setPublicVersion` (N-01).
3. **PendingIntent rules.** Review/Open/Continue = `PendingIntent.getActivity(… FLAG_IMMUTABLE | FLAG_UPDATE_CURRENT)` to an `exported="false"` activity with an explicit component and only the opaque id as extra; Deny/This wasn't me = immutable `getBroadcast` to an `exported="false"` receiver that signs in `goAsync()` or expedited work and starts no activity (no notification trampoline, Android 12+). Deny never sets `setAuthenticationRequired(true)`. The business URL is opened only by `startActivity(ACTION_VIEW)` from the foreground link activity after the tap. CI lint refuses `FLAG_MUTABLE` and exported components.
4. **Keys.** Minimum Android API 30. Approval keys: Android Keystore, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL)` (per-use, `BiometricPrompt.CryptoObject`); the payment key uses `AUTH_BIOMETRIC_STRONG` only and `setInvalidatedByBiometricEnrollment(true)`; StrongBox when available; keys are created with `setAttestationChallenge` and the chain is sent at enrollment so the server records the security level (equivalent of the Secure Enclave fact). Play Integrity is the App Attest equivalent (ADR-0030).
5. **Matrix.** FLOW_MATRIX §3a adds the Android conditions "force-stopped" and "Doze / restricted standby bucket".

## Consequences

- Businesses must display the code on their own screen; the SDKs return it from the create call.
- `ApprovalResult` v2 is a Core wire change; old devices that cannot do number matching get requests without it only if the business did not require it; `AUTH_NUMBER_MATCHING_REQUIRED` makes the server refuse approvals without `number_match` for auth capabilities.
- Opening Approve v2 in staging still needs the Phase 2 gate evidence in SECURITY §2.58.

## Threat assumptions changed

- Fatigue approvals of attacker-initiated prompts now need the attacker's number to reach the victim (T-MFA-1); real-time phishing relay remains (R-12).
- Relay prompt injection is removed for payments (E2EE required) and remains a labelled residual for low/medium server-visible requests.
- The watch can no longer be argued to be an authenticator.
