# ADR-0034: Sealed recovery envelopes to the authority (`recovery-seal`, HPKE)

- **Status:** proposed (2026-11-02, Stage 1 revision 3); revision 3.1 (2026-11-02): custody gaps closed (creation identity and grants, standby in a separate run, `seal_kid` per set, seal-key exposure procedure, unwrap reconciliation test; S3-A2-3), R-23 restated with a lifetime cap and a production design (S3-A3-02, conditions C-15 and C-16; §8-§10), specification loose ends (S3-A3-05), audit reasons (S3-A3-06)
- **Spec reference:** §4.3 invariants 1 and 5, §23, §26 (gateway compromise, recovery), §27 stop-ship 1 and 6
- **Related:** ADR-0007 (HPKE suite and Core implementation), ADR-0023 §2-§4 (JOSE profile, factor JWS, key log), ADR-0028 §1-§2, §5 (custody, roles, policy rules), ADR-0032 §3 (recovery flow that uses these envelopes), ADR-0033 §3 (pinned keys and revocation); SECURITY §2.2 (canonical JSON), §2.26 (code alphabet); reviews S2-A2-1, S1-A3-R01, S2-A2-5, S1-A3-R02
- **Review:** A3 and A2 (both required), A6/A7 (device sealing), A11 (custody runbook)

## Context

Every device → authority request is relayed by the api (B4 → B5). Revision 2 sent recovery codes to the authority in that relay as plaintext, both when a set was registered and when a recovery started, and the authority set was the same set the api hashes with `SERVER_PEPPER`. A compromised api (AS-1) could therefore record codes at registration, search them offline from its own database, or swap the new key at recovery start. In each case it ends with an authority-verified recovery and grant-capable keys (S2-A2-1 Critical, S1-A3-R01 High). Both reviewers require the codes and the new recovery keys to be confidential to the authority and bound to each other, with a code set the api cannot hash.

## Decision

### 1. Construction

- **HPKE, RFC 9180, mode_base, single-shot.** Suite: **KEM `DHKEM(P-256, HKDF-SHA256)` (0x0010), KDF `HKDF-SHA256` (0x0001), AEAD `AES-256-GCM` (0x0002)**. This is the ADR-0007 suite (CryptoKit `HPKE.Ciphersuite.P256_SHA256_AES_GCM_256`; swift-crypto's HPKE on Linux), so the app and the authority reuse one Core implementation and its RFC 9180 test vectors. No new primitive (F-23).
- `info` is fixed per purpose: `"VIADERE-RECOVERY-SET-V1\n" ‖ env` and `"VIADERE-RECOVERY-START-V1\n" ‖ env` (`env` = `stg` or `prod`). An envelope sealed for one purpose or environment cannot be opened as another.
- `aad` = the ASCII bytes of `ach ‖ "\n" ‖ nonce` of the authority challenge that the envelope answers (both from the authority-signed `viadere-challenge+jws`, ADR-0033 §2). The authority opens an envelope only with the `aad` of the challenge named in the request; a replay against another challenge fails AEAD authentication.
- **Wire form** (JSON, strict, ≤ 4096 bytes): `{"v":1, "kid":<RFC 7638 thumbprint of the seal public key>, "enc":<base64url, 65 bytes uncompressed point>, "ct":<base64url>}`. Nothing else.
- **Commitment.** `envelope_digest = base64url(SHA-256(enc ‖ ct))` (no padding). The device puts it into the signed object that authorizes the envelope (the factor JWS for a set, every new key's PoP for a start; ADR-0032 §3). The api cannot replace an envelope without breaking a device signature.

### 2. Plaintexts (canonical JSON, SECURITY §2.2; exact member sets; duplicates refused)

| Purpose | Members |
|---|---|
| `recovery_codes_set` | `v` (1), `purpose`, `account_ref`, `set_id` (`rcs_` + 22 base64url, device CSPRNG), `nonce`, `codes` (exactly 10 normalized codes, pairwise distinct) |
| `recovery_started` | `v` (1), `purpose`, `recovery_id` (the api recovery id the start answers), `nonce`, `code` (one normalized code), `new_kids` (the `kid` of **every** key the recovery will add, ADR-0023 §2 device-key definition, sorted ascending, no duplicates, 1-4 entries) |

**Codes (A3 item 4).** Generated **on the device** by the platform CSPRNG, 10 per set, each 10 symbols of the Crockford alphabet of SECURITY §2.26 (50 bits). Normalization before sealing and before hashing: upper-case; remove spaces and `-`; map `I`, `L` → `1` and `O` → `0`; refuse anything else or any length other than 10. The device shows codes as `XXXXX-XXXXX`.

### 3. Separate code sets (A3 item 1)

The authority set is **not** the api's set. It is generated on the device and leaves it only inside an envelope. The api never receives a code, a hash of a code, or any value derived from a code in a form it can test. When the authority confirms a registered set (signed head entry `recovery_codes_set`), the app calls the api to **invalidate the api's legacy set** for the account (`recovery_codes` → `invalidated`), so the person holds one set. The recovery **ID** stays an api locator (SECURITY §2.26); it names an account but is not a secret against AS-1, and nothing at the authority depends on it being secret.

### 4. Authority processing

1. Refuse unless `kid` is the active seal key the authority holds (§5), that key is inside its lifetime (§8.1), and the request names a pending challenge of the matching purpose.
2. Open with the purpose's `info` and the challenge's `aad`; any HPKE failure is `401 evidence_invalid` and counts as a failed attempt for that account (start) or is refused without effect (set). The audit reason tells an envelope that does not open (`envelope_open_failed`) apart from a wrong or used code (`code_mismatch`), so operators can see an api that burns the attempt budget with garbage envelopes (revision 3.1, S3-A3-06).
3. Strict parse; exact members; `nonce` equals the challenge nonce; `purpose` equals the challenge purpose. For a **set**: `account_ref` equals the account of the authorizing key, and `set_id` equals the `set_id` that the challenge request named and the authority-built display shows (revision 3.1, S3-A3-05 item 1; the device generates `set_id` before it asks for the challenge). For a **start**: the account is the one the authority bound to the challenge when it created it (from the recovery id), never a value in the request; the verifier is computed with that account's **single active** authority set's `set_id`; an account with no active set has nothing to verify against, and the start is refused (S3-A3-05 item 2).
4. Recompute `envelope_digest` and require it to equal the value in the authorizing device signature.
5. Use the plaintext only in memory: compute verifiers (set) or verify one code (start, ADR-0032 §3.2), then overwrite the buffers (best effort). Plaintext and envelopes are **never stored or logged**; the authority's log allow-list contains no envelope member. Envelopes are not retained (they are processed in the request; nothing to classify under ADR-0026).
6. **Verifier** = `HMAC-SHA256(RECOVERY_VERIFIER_KEY, "recovery-code-v2\n" ‖ account_ref ‖ "\n" ‖ set_id ‖ "\n" ‖ normalized_code)`, stored in `authority_recovery_codes {account_ref, set_id, seal_kid, verifier (unique per account_ref), state}`. `seal_kid` is the `kid` of the seal key that opened the set envelope (revision 3.1, S3-A2-3 item 3, S3-A3-02 item 2); `state` ∈ `active`, `used`, `superseded`, `invalidated`. Verification computes the HMAC of the presented code and looks it up by value; the lookup, the attempt counter and the transition `active → used` are one transaction (compare-and-swap). Argon2id is not needed: the key lives only in `kv-vdr-auth` and the codes are uniformly random (A3 item 4).

### 5. `recovery-seal` keys and custody

Key Vault has no ECDH (key-agreement) data-plane operation, so an HPKE KEM private key cannot stay inside Key Vault. Custody is therefore:

1. **Creation** by the authority admin job (`ViadereAuthority admin seal-key create --role active|standby`, reviewer-gated, ADR-0019 §5), run as `id-viadere-authority-admin` (revision 3.1, S3-A2-3 item 1). It generates the P-256 KEM key pair in memory, wraps the private scalar **locally** with the public half of a dedicated non-exportable Key Vault key (`recovery-seal-kek` for the active role, `recovery-seal-kek-standby` for the standby; RSA 3072, RSA-OAEP-256 with MGF1-SHA-256; key operations `wrapKey`/`unwrapKey` only), stores `{kid, public_jwk, wrapped_private, kek_name, kek_version, role: active|standby, created_at, not_after, state, job_execution_id}` in `authority_seal_keys`, prints the public JWK and thumbprint into the attested key inventory (ADR-0024 §7.3), and discards the private key.
   - **Grants (revision 3.1).** The admin identity still holds **no Key Vault role** and gains only DB grants (TRUST_BOUNDARIES §4.2): INSERT on `authority_seal_keys`, UPDATE of `role` and `state` there, and UPDATE of `authority_recovery_codes.state` to `invalidated` (§8.2). Wrapping uses only a **public** key, so no Key Vault access is needed.
   - **KEK public halves are attested inputs.** The public JWK of each KEK (`name/version`, RSA 3072, `e = 65537`) is read once by the authority crypto-officer group through PIM (the only identity that `AUTH-STANDBY-ROLE` allows on a standby key, so the rule stays as it is) and committed to the admin change file on protected `main` (CODEOWNERS). Its RFC 7638 thumbprint is recorded in the key inventory. The job refuses a KEK input whose thumbprint is not that inventory row, or that is not RSA 3072. The officer's `GetKey` appears in the Key Vault `AuditEvent` log and is reconciled against the change file. Defence in depth: a blob wrapped under a substituted key cannot be unwrapped by the real KEK, so the authority fails closed at the first start (active) or at rollover (standby), before it opens any envelope sealed to that key.
   - **Separate runs (revision 3.1, S3-A2-3 item 2).** The active and the standby key pairs are created in **two separate** reviewer-gated job executions, each from its own change-file commit. The job refuses a second `seal-key create` in an execution that already created one, and records the execution id with the row; ST-AUTH-25 checks that the two rows carry different execution ids. A compromised single admin run therefore exposes at most one of the two.
   - **Hygiene (S3-A3-05 item 4).** The job's log allow-list contains only the public JWK, the thumbprint, `kek_name/version` and the row id; that log feeds the attested inventory. The private scalar lives in one heap buffer that the job overwrites with zeros after wrapping (best effort in Swift: the buffer is never copied into a `String`, a `Data` description or an error value), and the job process exits right after.
2. **Use.** At startup the authority unwraps the **active** seal key with Key Vault (`keys/unwrapKey/action`) and holds it only in process memory. Key Vault `AuditEvent` reconciliation (ADR-0028 §2) expects exactly one `unwrapKey` per authority replica start, matched against a start record the authority writes before it calls Key Vault; any unmatched unwrap alerts at high priority (test ST-AUTH-25; revision 3.1, S3-A2-3 item 4).
3. **Standby.** A second seal key pair is created in a separate admin run (§5.1, revision 3.1) and wrapped under a **separate** Key Vault key `recovery-seal-kek-standby`, on which `id-viadere-authority` has **no role** until rollover; the role is granted through `id-gh-infra-auth-apply-<env>` (reviewer-gated). Authority code execution before rollover therefore cannot open envelopes sealed to the standby (same pattern as ADR-0033 §3 for signing keys, S1-A3-R02 item 3).
4. **Pinning.** The app pins both public keys, `VIADERE_AUTHORITY_SEAL_KEYS = [active, standby]`, next to `VIADERE_AUTHORITY_DEVICE_KEYS`, as constants in Core for each environment. The device seals only to the active entry unless a verified revocation has retired it (ADR-0033 §3), then to the standby. Seal keys are never fetched from the network: no statement can substitute them.
5. **Rotation and revocation** follow ADR-0033 §3 (same list, `key_family: "recovery-seal"`). A retired seal private key is destroyed (wrapped blob deleted, KEK version disabled) once no supported app version pins it, so recorded envelopes cannot be opened afterwards, even by a later authority compromise. Seal keys have a maximum active lifetime (§8.1).

Roles and policy: `id-viadere-authority` gets the custom role "Viadere Authority Unwrapper" (`keys/read`, `keys/unwrapKey/action`) on `recovery-seal-kek` only; `AUTH-SIGNER-ROLE` (ADR-0028 §5) allows exactly that addition, and the new rule `AUTH-STANDBY-ROLE` fails while any identity other than the authority crypto-officer group holds a data role on `recovery-seal-kek-standby` (or `device-statement-signing-standby`) outside a recorded rollover.

### 6. What the api still sees

Ciphertext, `kid`, `enc`, the recovery id, the new keys' public halves and PoPs (all public), and timing. It cannot: learn a code (HPKE confidentiality under the pinned key), search one offline (it holds no hash of an authority code), substitute its own key at start (the code is sealed together with `new_kids`, and every new key's PoP commits to `envelope_digest`), or replay a set or start against another challenge or account (`aad`, `nonce`, `account_ref`).

### 7. Vectors and tests

- Vectors `docs/protocol/vectors/recovery-seal-v1.json`: RFC 9180 suite vectors re-run in Core; valid set and start envelopes with fixed ephemeral keys; wrong `info` (env, purpose); wrong `aad`; tampered `ct`; extra or missing plaintext members; non-normalized code; `envelope_digest` mismatch.
- ST-REC-14 (A, A2 and A3): AS-1 records every byte relayed at registration and start (simulated api with full DB and `SERVER_PEPPER`); it then cannot start a non-legacy recovery: a replayed envelope against another challenge or account, or with a substituted nonce or `new_kids`, is refused.
- ST-REC-15 (A): a start whose PoP keys differ from the sealed `new_kids` is refused; an api-substituted key never becomes active.
- ST-REC-21 (S, A): after registration, the api database and `SERVER_PEPPER` contain no value that verifies an authority code (the api's legacy rows for the account are `invalidated`; no authority code or derivative appears in any api table or log).
- ST-REC-19 (K) covers the seal-key revocation rules with the device-statement rules (ADR-0033 §6).
- ST-REC-23 (A, revision 3.1; S3-A2-3 item 3, S3-A3-02 item 2): `admin seal-key exposed <kid>` invalidates every authority set whose `seal_kid` is that key and no other set; a start against an invalidated set is refused; the affected heads carry `recovery_set: invalidated`; the affected accounts keep their grant capability; a set registered afterwards under the standby works.
- ST-AUTH-25 (A, I; revision 3.1, S3-A2-3 item 4): an injected `unwrapKey` (lean) or `decrypt` (production, §9) without a matching authority record raises the high-priority alert; the admin job refuses a second `seal-key create` in one execution; the authority refuses to open envelopes for a seal key past `not_after`.
- Vectors added in revision 3.1 (S3-A3-05 item 5): a set envelope whose `account_ref` differs from the authorizing key's account; a set whose sealed `set_id` differs from the challenge's; a start whose PoP set is a strict superset or subset of `new_kids`; the passkey COSE → SPKI → `kid` conversion (ADR-0032 §3.2); for §9, JWE vectors with RSA-OAEP-256 (one sealed with MGF1-SHA-1 must fail), wrong `typ`, `env`, `ach` or `nonce` in the protected header, an extra header member, a 16-byte content key and a truncated tag.

### 8. Seal-key lifetime and exposure (revision 3.1; S3-A2-3 items 3-4, S3-A3-02 items 2-3)

1. **Lifetime.** A seal key is active for at most **6 months** (`not_after` = activation + 6 months). A3 asked for at most 12 months in staging and 6 in production; one value is used for both. The limit is **90 days** if production ever runs under the owner exception of §9.4. The authority alerts 30 days before `not_after` and refuses to open envelopes for a key past it (fail closed: registration and sealed starts wait for the rollover). The routine sequence (ADR-0033 §3.5) pins `[current, next]` one app release ahead, so the cap follows the pinned-release cadence. When a set's seal key retires, the head shows `recovery_set: refresh_suggested` (ADR-0033 §2) and the app offers S-REC-05; the set stays valid. Once no supported app pins the retired key, it is destroyed (§5.5), and envelopes recorded under it can no longer be opened by anyone.
2. **Exposure procedure** (`ViadereAuthority admin seal-key exposed <kid>`, reviewer-gated). It is written into `docs/ops/KEY-ROTATION.md` with the rest of ledger L-2 before Stage 4 pins any key, and **drilled once in staging** before any authority flag in the pilot (C-15). Triggers: a suspected authority process or memory compromise; an unmatched `unwrapKey` or `decrypt` alert; a crash dump or diagnostic capture of the authority found anywhere; a suspected leak of a wrapped blob together with KEK access. Steps, in this order:
   1. Sign a seal-family revocation list naming the exposed active key (ADR-0033 §3.3). A crypto officer grants the authority its role on the standby KEK through `id-gh-infra-auth-apply-<env>` (reviewer-gated), and the authority switches sealing to the standby.
   2. In one transaction, set `state = invalidated` on **every** `authority_recovery_codes` row whose `seal_kid` is the exposed key, and only on those, and set each affected account's head to `recovery_set: invalidated`. Audit one event per account.
   3. On its next head the app shows S-REC-05 as a required step, and the person makes a new set, sealed to the standby. **The account keeps its grant capability**: an enforced code refresh is not a downgrade (S3-A2-3 item 3).
   4. Destroy the exposed seal key at once (blob deleted, KEK version disabled), without waiting for app releases, because it is revoked.
   5. A person who has **no device left** and holds only codes from an invalidated set cannot recover on their own; that person uses the admin-job support path of ADR-0032 §3.3 (b). This is the availability cost of the invalidation; A9 checks that S-REC-04's support wording covers it (ledger L-16).
3. **Scale.** The invalidation is one indexed update by `seal_kid` plus the head flags in the same transaction. The C-15 drill measures it on the pilot data set.

### 9. Production construction: decryption inside the HSM (revision 3.1; condition C-16, S3-A3-02 item 5 option (a))

Chosen for production: **compact JWE (RFC 7516) with `alg: RSA-OAEP-256` and `enc: A256GCM` (RFC 7518 §4.3, §5.3) to a non-exportable RSA-HSM key.** The private key never leaves the HSM boundary, and every decryption is a logged Key Vault operation.

1. **Key.** `recovery-seal-rsa` (active) and `recovery-seal-rsa-standby` (a separate key object, created disabled, with no role until rollover, as in ADR-0033 §3.2): `RSA-HSM` 3072 in Key Vault Premium (standard profile) or Managed HSM, key operations `decrypt` only. The authority gets a custom role "Viadere Authority Decrypter" (`keys/read`, `keys/decrypt/action`) on the active key only (`AUTH-SIGNER-ROLE`, ADR-0028 §5). The app pins the two public JWKs (`kty: RSA`) as the production `VIADERE_AUTHORITY_SEAL_KEYS`, with the same index and revocation rules. Production has no KEK, no wrapped blob and no `unwrapKey` role.
2. **Envelope.** The protected header is exactly `{alg: "RSA-OAEP-256", enc: "A256GCM", kid, typ, env, ach, nonce}`. `typ` is `viadere-recovery-set+jwe` or `viadere-recovery-start+jwe`, which gives the purpose separation that `info` gives in HPKE; `ach` and `nonce` come from the answered challenge, which is the role of the HPKE `aad`. The JWE AAD is the ASCII of the base64url protected header (RFC 7516 §5.1 step 14), so every header member is authenticated. The content key is 32 bytes from the device CSPRNG, the IV 12 bytes and the tag 16 bytes. No `zip`, no unprotected header, no JWE AAD member; compact form only; at most 4096 bytes. The plaintext is the §2 object, unchanged. RSA-OAEP-256 means SHA-256 for both the hash and MGF1: on iOS `SecKeyAlgorithm.rsaEncryptionOAEPSHA256`; on Android `RSA/ECB/OAEPPadding` with an explicit `OAEPParameterSpec("SHA-256", "MGF1", MGF1ParameterSpec.SHA256, PSource.PSpecified.DEFAULT)`, because the provider default uses MGF1-SHA-1, which the HSM would not decrypt (a vector catches it). `envelope_digest = base64url(SHA-256(ASCII of the compact serialization))`, committed exactly as in §1.
3. **Authority processing.** Before any Key Vault call, the authority checks: strict compact parse (5 parts; encrypted key exactly 384 bytes; IV 12 bytes; tag 16 bytes); exact header members; `kid` is the active seal key; `typ` matches the challenge purpose; `env`, `ach` and `nonce` equal those of the pending challenge named in the request; and the `envelope_digest` check of §4 step 4. It then makes one Key Vault `decrypt` (RSA-OAEP-256) of the encrypted key, **at most one per challenge**: the challenge moves `pending → opening` by compare-and-swap before the call, a second envelope for it is refused, and a decrypt record `{ach, kid, requested_at}` is written before the call. A content key that is not 32 bytes, or an AES-GCM failure, is `401 evidence_invalid` with the same generic answer as any other failure. No padding-oracle distinction reaches the caller, and the per-challenge limit removes adaptive queries. Steps 3-6 of §4 then apply unchanged. Key Vault `AuditEvent` reconciliation expects exactly one `decrypt` per decrypt record; any other alerts at high priority (ST-AUTH-25).
4. **Production gate and exception.** No production authority environment and no real-customer recovery set exist until §9 is implemented and its vectors and ST-REC-14, -15, -21, -23 and ST-AUTH-25 pass on this construction, **or** until the owner signs an exception, countersigned by A2 and A3, that records R-23 as a production residual and names the compensating controls (§8 and §10, with a seal-key lifetime of 90 days or less) and a review date. Without one of the two, production is **blocked** (ledger L-13).
5. **What changes for R-23.** A process compromise can still call `decrypt` while it lasts, so it can open envelopes that the api recorded and presents **during that window**. Each such call is a Key Vault operation without a matching decrypt record, so the reconciliation alerts and the §8.2 procedure invalidates every set under the key. After the compromise ends, no key material has left the HSM, and recorded envelopes stay sealed. The exposure becomes detectable and bounded in time instead of silent and permanent.
6. **Alternatives.** Key Vault and Managed HSM have no key-agreement data-plane operation as far as both reviewers and the author know; the L-12 re-check in Stage 6 confirms this on Microsoft Learn. If such an operation exists, HPKE with an HSM-resident KEM key (option (b)) is an acceptable alternative, subject to an A3 re-check. **Staging:** Stage 6 may move lean staging to this construction as well (Key Vault Standard offers the same `decrypt` operation on software-protected RSA keys, ADR-0012). This is recommended, because it leaves one code path and drills the production path before production; it needs an A3 delta check only. Until then, lean staging uses HPKE with §8 and §10.

### 10. Lean-pilot mitigations for R-23 (revision 3.1; condition C-15)

Required before `RECOVERY_REFRESH_PROMPT_ENABLED` or any authority flag in the pilot, in addition to §8:

1. The S3-A2-3 items: creation identity and grants and the standby in a separate run (§5.1), `seal_kid` per set and the exposure procedure (§4.6, §8.2), and the reconciliation test ST-AUTH-25.
2. The §8.2 procedure in `docs/ops/KEY-ROTATION.md`, **drilled once in staging**.
3. **Memory hygiene in the authority container.** The process sets `RLIMIT_CORE` to 0 and `PR_SET_DUMPABLE` to 0 at start, before it unwraps the seal key. The authority build has no debug, diagnostics, profiling or heap-dump endpoint (a test lists its routes). The runtime image has no shell and no package manager (removed in the `ubuntu:26.04` runtime stage, checked by an image test). `ptrace` is unavailable to the container (no `CAP_SYS_PTRACE`; verified in Stage 6), and no identity holds the Container Apps console or exec permission on the authority app (a policy check; Stage 6 names the exact action from Microsoft Learn).
4. **Per-environment keys.** Seal keys are created per environment. A release-build test refuses a production build whose pinned seal or statement constants contain a staging thumbprint, and lean (pilot) seal keys are never pinned in a production build or reused in the standard profile (CLAUDE.md lean-profile rule).
5. Unwrap reconciliation alerting is in place and drilled together with C-11.
6. No real customer data in lean staging (CLAUDE.md exception rows), so the pilot population is small and known.

## Consequences

- The app needs the seal key pair constants and a Core HPKE call before it may offer "Make new recovery codes" (decision 16 OQ-2 is gated on this ADR; ADR-0032 §3.5).
- Lean staging: one Key Vault `unwrapKey` per authority start and no per-request Key Vault call for recovery. Production (§9): one Key Vault `decrypt` per envelope; recovery events are rare, so the cost is small.
- An exposed seal key forces the affected people to make new codes (§8.2); a person with no device left then needs the support path.
- The api's legacy set disappears for every account that registers an authority set; legacy recovery remains only for accounts that never registered one, and it is never grant-capable (ADR-0032 §3.3).

## Threat assumptions changed

- AS-1 can no longer harvest, search or swap authority recovery codes or the keys they authorize. AT-1 1.3.3 becomes [C] when this ADR and ADR-0032 §3 ship and ST-REC-14, -15, -16, -21 pass.
- New residual **R-23** (owner A3; restated in revision 3.1 per S3-A3-02 item 1): an authority **process** compromise (T-AUTH-12 class), or any read of authority memory (memory disclosure, crash dump, debug session, compromised sidecar), yields the in-memory active seal private key. Together with envelopes that the api recorded, it **opens recorded set envelopes and so learns the live recovery codes of every account whose current set was sealed to that key; the codes remain valid after the incident until those sets are invalidated.** Unlike the signing-oracle exposure of T-AUTH-12, this outlasts the compromise. Bounded in lean staging by §8 (sets carry `seal_kid`; the exposure procedure invalidates exactly those sets; active lifetime ≤ 6 months) and §10 (C-15). **Removal (C-16):** the production construction of §9, which keeps decryption inside the HSM. Until it ships, production is blocked unless the owner signs the exception of §9.4.
